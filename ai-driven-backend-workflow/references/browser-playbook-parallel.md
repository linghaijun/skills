## 11. 提速：不降质量

慢的大头通常不是页面本身，而是**返工**（证据被验收打回）、**一步一个工具调用**、**在大列表里翻页找对象**、
**等用户**（切窗口、换账号）。下面每条都只改「怎么做」，不减少任何检查。

1. 🔴 **证据在截图当时就采齐，别等验收来要**：每次截图同时落一条记录 —— 拍摄时间、页面上看得到的登录身份、URL、
   本次相关接口的请求体 + **HTTP 状态码**（`xhr.status`，别拿响应体里的业务 `code` 冒充）、当前筛选 / 日期 / 页码。
   `RESULT.md` / `REPLAY.md` / 取证上下文文件直接从这些记录生成，不靠事后回忆。身份读数（userId ↔ 登录名 ↔ client）
   取一次就写进上下文文件。判据：证据验收专员的 C4（可追溯）与 C5（时效）清单，开测前就能逐项勾掉
   - 后端进程启动时间、前端被测文件最后修改时间，进场时就记下来（「跑的是当前代码」要有证据）
   - 自己脚本里的副作用（如清理脚本里的 `body.click()`）要么去掉，要么在记录里写明用途；漏报一次就是一次退回
2. 🔴 **请用户登录前，先在库里预演这个账号会看到什么**：用该账号的 client、授权 profile、页面会带的平台筛选，
   把页面背后那条查询（从 mapper 推导，见 `data-reconciliation.md`）跑一遍，确认目标数据**会出行**；
   顺带确认该账号的平台 / profile 配置不为空。预演不出行就换账号，不要让用户白登一次。**项目默认测试账号**写在 cdp skill `projects/<项目>/PAGE-NOTES.md`「默认测试账号」节（creative-management：yinzixin / clientId 62），优先用它；缺样本的 AC 提前一次性列出候选账号，别让用户反复登录
   （实测：一个账号库里数据齐全，但 client 没有平台配置，页面请求的 `platformFilters` 为空，任何日期都 0 行）
3. **一条路径写成一个带断言的脚本**：进场检查（身份、`visibilityState`、请求拦截已装）→ 导航 → 筛选 → 定位对象 →
   打开 → 取证，一次调用跑完；每一步后用页面状态做断言，不符就 `exit` 并打印现场，**不带着错状态往下走**。
   点击仍逐个走落点核对（§3 第 4 条），只是不再一步一个来回。脚本放 scratchpad，复跑说明里写清入口
4. **别在大列表里逐页翻找对象**：先在库里按列表的排序规则算出目标在第几页（同时确认同名对象有几个、怎么区分），
   用页码直接跳过去；能用筛选收窄的先收窄。**数据层断言**（每页几行、各类型计数、字段有没有值）从接口响应读，
   **界面只截判定点**，不必每页都靠肉眼看
5. **别让用户切窗口**：新拉起的 Chrome 带 §2.1 的防节流开关；已在跑的实例被遮挡时，用 §3 第 5 条的
   「最小化再恢复」把它拉到前台
6. **验收与下一条测试并行**：一条 AC 的证据落盘后，立刻起独立 subagent 做证据验收（`evidence-acceptance.md`），
   主会话同时去测下一条；验收结果回来再处理退回项。主会话仍不得代判

7. 🔴 **尽可能多开子 agent 并行**（用户约定，不必每次提醒）：开测前出并行分组表（§12、cdp skill §2.6），能独立的组全部派后台子 agent（一组一个窗口 / targetId），主会话只领一组 + 汇总；子 agent 边做边落盘，中断后主会话按文件续做
8. **测完不恢复浏览器现场**（用户约定：偏好 / 日期 / 分组 / 列配置都不还原，浪费时间）；只关自己开的窗口。用户明确要求时才用 cdp skill `storage-restore.mjs`

## 12. 多会话 / 多浏览器并行：用例状态登记与窗口归属

🔴 **开测前必须先出「并行分组表」再动手**（用户约定，不必每次提醒）：按页面状态分组 → 判断组间能否并行
（写 localStorage 偏好 / 写业务数据 / 前后依赖 三类不能与别组并行）→ `cdp-drive-real-chrome/scripts/tab-open.mjs --open` 一组开一个窗口拿 `targetId` →
`verify_state.py claim --window cdp:<port>/<targetId>` 登记 → 各组脚本只带自己的 `CDP_TARGET`。完整规则与模板见 cdp skill 的 §2.6。
⚠️ **同一 Chrome 实例的所有标签共享 localStorage**：列配置、KPI 卡片、Group by 记忆、日期范围这类偏好是跨标签串的 —— 两组都要改偏好就别并行，或用不同 `--user-data-dir` 的实例。

§11 第 6 条的「并行」是**一条测试 + 一个验收 subagent**。再上一个量级：**多个会话**（主会话 + 若干子 agent）/ **多个浏览器实例**同时验不同 AC。此时新增两个只会**静默发生**的事故：

- **重复验**：两个会话不知道对方在验哪条，同一条 AC 验两遍，证据互相覆盖；
- **窗口串扰**：会话 A 的工具调用打到会话 B 的标签页（并行下工具默认作用于**前台标签**）。

这两件事靠「注意一下」防不住。用一份**共享登记文件** `tests/.verify-state.json` 把它们变成可查事实，认领 / 收尾 / 回收走 `scripts/verify_state.py`（锁文件 + 读-改-写，避免并发丢更新）。

### 12.0 同一浏览器内并行：一 AC 一 tab（默认就并行）

🔴 **默认就要并行**；只有并行分组表写明了「为什么只能串行」才串行。

> **为什么值得做**：列表类接口常常很慢（本工作区实测单次数十秒，项目数据见项目 `AGENTS.md`），串行 20 条 AC 光等待就十几分钟。
> 并行的收益**不是 CPU 并行**（工具调用本身串行，`browser_batch` 也是顺序执行），而是**消除等待** —— A 标签等接口时去操作 B 标签。

**实测能力边界（内置浏览器，2026-09-29 实测）**：

| 能力 | 结论 |
|---|---|
| 多标签共存、`tabId` 定向 | ✅ `read_page` / `computer` / `javascript_tool` / `read_network_requests` 全支持 |
| **网络流水按 tab 隔离** | ✅ 各 tab 只看到自己的请求，**互不串** |
| 后台标签截图 | ✅ 不用 `tabs_select` 切前台即可取证 |
| **cookie / 登录态** | ❌ **同一浏览器所有 tab 共享** —— 同一时刻**只能一个账号** |

**分组规则（组内并行、组间串行）**：按「账号 + 是否写操作 + 有无依赖」分组

| 分组 | 并行方式 | 并发度 |
|---|---|---|
| 同账号 + 只读 AC（绝大多数） | 同一浏览器**一 AC 一 tab** | **2–4** |
| 不同账号（如否定型 AC 要用受限账号） | **CDP 隔离登录态**，两条路二选一（§2.4） | 按账号数 |
| **写操作 AC** | 🔴 **一律串行** | 1 |
| **有前后依赖的 AC**（A 造的数据给 B 用） | 🔴 **一律串行** | 1 |

- 写操作与依赖链必须串行，理由是**脏数据归因**：并行跑写操作出了问题，没法判断是哪条 AC 造的，验证报告的「遗留脏数据」表就废了
- 并发度**不要超过 4**：再高会把后端拖慢（本就慢的接口更慢），且截图时机更难控，得不偿失
- 🔴 **每次工具调用必须显式带 `tabId`** —— 不带时 `computer` 作用于**前台标签**，并行下必然互相抢焦点，产生极难排查的串扰。这条不遵守，并行就是负收益
- 子 agent 并行时同理：**每个子任务独占一个 `tabId`**，并在任务描述里写死它；子 agent 共享同一个浏览器（session 级资源），组内仍必须同账号

**取证在并行下的简化**：既然流水按 tab 隔离，**一 AC 一 tab 时不再需要 marker** —— 该 tab 的全量流水就是这条 AC 的。`RESULT.md` 记 `tabId` 替代 marker 值即可。串行复用同一个 tab 时，marker 规则照旧。

**并行时的收尾**：每条 AC 走完**立即关掉它的 tab**（`tabs_close`），避免标签堆积导致 `tabId` 混淆和内存膨胀；验证报告中注明每条 AC 用的 tabId / CDP 实例，便于复核。

### 12.1 状态枚举与 Checklist 的对应

| 状态 | 含义 | Checklist |
|---|---|---|
| `待验证` | 还没人动 | `[open]` |
| `验证中` | 已被某会话认领，正在验（**带会话 + 窗口标识**） | `[open]` |
| `修复中` | 验出问题、正在修（**仍归原会话**，别人不许抢） | `[open]` |
| `通过` | 实测通过 | `[done]` |
| `阻塞` | 验不了 / 卡在外部依赖，需人工介入（`verify_state.py finish` 会提示回写 `[blocked]`） | `[blocked]` |
| `失败` / `部分` / `走读证据` / `跳过` | 口径见 §6、§6.1 | `[open]` |

🔴 只有 `通过` 回写 `[done]`。**`验证中` 不是通过**，任何时候都保持 `[open]`。
🔴 **`[open]` 与 `[blocked]` 在交付门禁里同等拦截**（`validate_step.py` 的交付门禁两者都判 FAIL）——
「放着不管」和「我卡住了」都不是放行；要放行只有一条路：`[waived]` + 证据验收报告里点名该 AC 的「风险接受记录」。

### 12.2 认领 / 收尾 / 回收

```bash
py scripts/verify_state.py init    --dir docs/develop/{...}
py scripts/verify_state.py list    --dir docs/develop/{...}    # 认领前先看
py scripts/verify_state.py claim   --dir docs/develop/{...} --ac AC-03 --session s2 --window tab:1234
py scripts/verify_state.py fix     --dir docs/develop/{...} --ac AC-03 --session s2 --note "问题摘要"   # 验证中 -> 修复中
py scripts/verify_state.py mine    --dir docs/develop/{...} --session s2   # 本会话占用的 AC 与窗口
py scripts/verify_state.py finish  --dir docs/develop/{...} --ac AC-03 --session s2 --status 通过
py scripts/verify_state.py reclaim --dir docs/develop/{...} --ac AC-07 --session s3 --window tab:9999 --ttl 20
py scripts/verify_state.py invalidate --dir docs/develop/{...} --acs AC-03,AC-07 --reason "16:20 改 Foo.vue"   # 改代码后作废受影响 AC
py scripts/verify_state.py backfill-duration --dir docs/develop/{...} --dry-run   # 漏计时：按 NOTES 用时 / 证据时间回填耗时
```

- 🔴 **开始前 claim，收尾 finish**；禁止「跑完再补登记」（中间那段时间别人无法判断这条是否在验）
- 🔴 **边验边修**：验出问题用 `fix` 置「修复中」（**仍归本会话，占用不放**），修完再 `claim` 回「验证中」复验 → `finish`。生命周期 `待验证 → 验证中 → 修复中 → 验证中 → 通过/失败`；**禁止攒到最后统一修**
- 🔴 **一条 AC 同时只能一个会话占用**（`验证中` 或 `修复中`）。被占用且未超时 → 换一条；确认僵死（> TTL 无更新，默认 20 分钟）才 `reclaim`，note 记下「回收自谁」
- 会话崩溃 / 被中断 → 状态停在 `验证中`（或 `修复中`）。**这不是脏数据，是待回收**，下一个来的会话按 TTL 回收即可；收尾时 `list` 若仍有 `验证中` / `修复中`，必须在报告里说明是中断还是漏收尾

### 12.3 窗口标识：每个会话认自己开的那个

🔴 **登记里必须写清窗口标识，且每个会话只用自己那一个**；工具调用**每次显式带自己的 `tabId`**（不带 = 作用于前台标签 = 并行串扰）。

| 引擎 | 窗口标识写法 | 备注 |
|---|---|---|
| 内置浏览器 | `tab:<tabId>` | 一 AC 一 tab；`tabs_close` 后该标识即失效 |
| 自拉 Chrome + CDP（单实例） | `cdp:9222/<targetId>` | `targetId` 从 `/json/list` 取；同实例内多 tab 各一个 targetId |
| 自拉 Chrome + CDP（多实例，方案 A） | `cdp:<port>/<targetId>@profile:<简写>` | 端口、账号、`--user-data-dir` **一一对应**（见 §2.1；多实例 vs 多 context 两条路对比见 §2.4） |

- 🔴 **端口、账号、profile 的映射要写进登记或项目笔记**：只记住 `9222/9223` 很容易混 —— 你以为是受限账号、实际点的是超管窗口，否定型 AC 直接假绿灯（§8）
- 会话结束：`finish` 时**保留** session/window（便于复核「这条是谁、在哪个窗口验的」）；对应窗口该关就关（内置 `tabs_close`；自拉实例统一收尾，见 §2.1 ⑤）
- 🔴 **不借用别人的窗口**：同一账号要验第二条 AC，开自己的另一个 tab（自己的 tabId），不要切到别人登记的 tab 上

### 12.4 与写操作 / 依赖链的关系

并行只用在「**同账号 + 只读**」的 AC 上（并发度 ≤ 4）。**写操作 AC、有前后依赖的 AC 一律串行，且各自单独 `claim`** —— 否则出问题时无法归因是哪条 AC 造的脏数据（分组规则见 §12.0）。

🔴 **修一处、验一片：每次改代码当场作废受影响 AC（改动登记与作废一步完成）**：修复、口径变更、动公共代码（组件 / 接口 / 工具函数 / Mapper）之后，立刻
`verify_state.py invalidate --dir <需求目录> --acs <受影响 AC 列表> --reason "<HH:MM 文件 改了什么>"` ——
已完结的打回「待验证」、终验一并作废、看板立刻变色，之后按正常流程 `claim` 重验（无需 `--force`）；
`finish` 时证据目录里没有晚于作废时间的文件会告警（旧证据不能证明新代码）。
- 影响面按「被改文件出现在哪些 AC 的路径上」判，**拿不准就多作废**；修复引起的回归最容易在「只重验出事那条」时漏掉
- 维护了改动时间线（如 `CODE-CHANGE-TIMELINE.md`）的，登记时间线与 invalidate 同一步做，**只记时间线不算登记**
- 回归清单 `R-NN` 同此
- 实测：时效类退回曾达 41 行、占验收不通过的一半 —— 时间线手工维护、没人回头看；一次改动连时间线都没登记，又退 3 条

🔴 **并行验证轮开始后冻结代码（「边验边修」在并行下的例外）**：≥2 组同时在测时，只修**阻塞缺陷**（该组无法继续）；
非阻塞问题 `fix` 登记 + 留现场证据，攒到本轮所有组收尾后**一起改、一起 `invalidate`、一起重验**。
边测边改会让别组正在拍的证据随时过期，同一批 AC 反复重拍。口径变更（用户改需求）同样攒到轮次边界再落代码。
实测：第 1~3 轮边修边测 + 改动不作废，同一批 AC 反复重拍，4 轮验收才收敛。

### 12.5 证据终验（独立维度，不重跑浏览器）

跑完所有 AC、采完证据之后，还要过一遍**证据终验**：只核对**证据内容是否支撑它的结论**，不重跑浏览器。

- 状态：`未终验` → `终验中` → `终验通过` / `终验不通过` / `豁免`，**不改变 `status`**，也不改 Checklist 回写口径
  - `豁免` **仅限用户明确放行**（证据不足仍收口）：Checklist 置 `[waived]`（不是 `[done]`），`--note` 必写放行范围 + 用户原话 + 风险，证据验收报告要有点名该 AC 的「风险接受记录」（`evidence-acceptance.md`）；AI 不得自行豁免
- 只有**已完结**的 AC 可终验；批量只能置「终验中」，逐条结论必须一条条给（批量打钩等于没验）
- 改判已终验的结论要 `--force`；终验不通过按「发现问题」处理（必要时才重新实机复验）
- 看板：明细「终验」列 + 按终验筛选 + 总览卡片 + 风险（不通过=高，「已完结但未终验」聚合为低）

```bash
py scripts/verify_state.py final --dir <需求目录> --ac ALL  --session s1 --status 终验中
py scripts/verify_state.py final --dir <需求目录> --ac AC-01 --session s1 --status 终验通过 --note "证据支撑结论"
```

完整核对维度见测试步骤文件的「证据终验」节（全栈 `step-11` §11.6 / 后端 `step-10` §10.6）。

### 12.6 子 agent brief 必含项（派发即写进 brief，缺一项不派）

§4.0 / §4.1 / §4.2 的规则本来就有，但子 agent 只读 brief —— brief 不写，它就不知道。一次验收退回里
「断言只证一部分」11 行、「无反应没实点」5 行、「标注没目检」10 行，都是 brief 没要求；另有两个子 agent 因截图无超时卡死 10 分钟被看门狗终止、一个因登录过期空跑整组。
派发时把下面逐条写进 brief（可直接复制）：

1. **窗口归属**：`--session` / `--window` / `CDP_TARGET` 写死，只碰这一个窗口（§12.3）；会话之间靠登记文件协调，不靠共享上下文
2. **开测第一步跑 `chk401.mjs`**（cdp skill），退出码非 0 立即停下汇报，不自己重试；长流程每组开始前再跑一次
3. **连接一律 `sconn.mjs`**：所有 CDP 调用 ≤30s 超时 + 重试 + `Page.bringToFront` + screencast 兜底；不得自写无超时的 CDP 客户端
4. **每条 AC 开测前先写断言清单**（Then 逐句拆、每句标证据形式，写进 `case.md` / NOTES），验完逐句打勾（§4.0）
5. **「无反应 / 不能操作」必须真实点击** + 抓请求数为 0 + 前后状态一致（§4.0 #12）
6. **每张标注图出完用 Read 打开目检**：文字完整、标签没压住判定点、编号与说明对得上；瞬态元素先等稳定；录屏帧按画面选（§4.1）
7. **证据须晚于最后一次相关改动**：开拍前 `verify_state.py list` 看本 AC 有没有被 `invalidate`，有就整组重拍（§4.0 #7）
8. **构造证据走 `fetch-stub.mjs`**，标「构造（CDP Fetch）」，结束读回已失效（§4.2）
9. **补丁 / 采样 / 标注脚本放 `tests/AC-NN/script/`**，汇报前 `ls` 自检；scratchpad 不算存档（`evidence-acceptance.md` 测前动作）
10. **边做边落盘**（每条 AC 一个目录、NOTES 实时写）；只修阻塞问题（§12.4 冻结）；brief 没列明授权的写操作一律不做
11. **汇报末尾附「待回写清单」**：哪些 AC 结论变了（含接力补完别组登记过的 AC）、哪些 R-NN 有新结论、哪些 tasks 可勾 —— 子 agent 不动 verify_state 时，主会话照单回写（§12.7）

### 12.7 汇报回来之后：主会话负责回写，一次改全所有记录处

同一个事实常写在好几处：`verify_state` 状态、`RESULT.md` 结论、回归清单的行与汇总、`tasks.md` 勾选、交接文档、`.workflow-state.json`。
子 agent 的 brief 通常写「不动 verify_state」，于是**回写只能由主会话做** —— 主会话不做，就没人做，而且不报错：
CP-58118 一轮里连续出了 7 次（AC-90 接力验完状态停在「部分」、Step10 批量补登记时漏掉、复验报告放在 `tests/_acceptance/` 门禁读不到、
回归汇总停在旧数字、交接文档停在「前端未开发」、矩阵漏了后加的 AC-94、Step1 后补的问答格式不合规却一直显示绿灯）。

收到子 agent 汇报的**同一轮**，按下表逐项回写，不要留到「最后统一整理」：

| 汇报里有 | 回写到 |
|---|---|
| 某 AC 结论（含接力补完的另一半） | 状态以 RESULT 为准回写 `verify_state.py`：**当前是「验证中」** → `finish --dir <需求目录> --ac <AC> --session <自己> --status <结论>`；**已经完结（通过/失败/阻塞/部分/走读证据/跳过）** → 先 `claim --dir <需求目录> --ac <AC> --session <自己> --window <窗口> --force` 回到「验证中」，再 `finish`。🔴 **`finish --force` 改不了状态**（`finish` 要求当前是「验证中」，对已完结状态一律拒绝 exit 1）。同时 `RESULT.md` 顶层第一条写 `- 结论：<状态词>`（门禁按它比对，引用块里的历史结论不算；词表同 §12.1） |
| 回归项 R-NN 结论 | 回归清单该行**和**底部汇总的计数 / 豁免列表 |
| 一项任务完成 | `tasks.md` 勾选并注明证据位置 |
| 新增 / 改动 AC、Q&A | Checklist、矩阵对应小节、`case.md` 原文、Jira 纯净版；Q&A 按「状态 / 问题描述 / 已选 / 当前结论 / 来源」五项写 |
| 用户口径变化、观察项、存量问题 | 测试交接文档对应小节 |

**兜底**：`validate_step.py` 在测试步查「用例状态 vs RESULT」，交付门禁另查回归汇总一致性、交接文档时效，并**按当前产出物重跑 Step1~N-1**（旧绿灯过期即 FAIL）。
门禁报出来再改是兜底，不是流程 —— 每次都靠门禁兜，说明回写这一步被跳过了。
