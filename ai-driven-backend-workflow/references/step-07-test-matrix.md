# 第七步：测试用例矩阵

**输入**：Checklist + API 文档

**动作**：在编码前制定验证指标，作为编写单元测试的依据(TDD 思想)。

## 通用约束

🔴 **① 一条用例只验证一个测试点，严禁合并场景**
一条里塞多个断言，失败时定位不到是哪个点挂了；而且前一个 assert 一失败，后面的断言根本不会执行，**被掩盖的缺陷会一直躺到线上**。
- ❌ `验证列表筛选与排序均正常` —— 两个测试点
- ✅ 拆成 `按 Status 筛选返回预期条数` + `按 CreateTime 倒序排列`

🔴 **② 必须逐条完整输出，禁止省略**
写矩阵时禁止出现「其余 AC 同理」「参照上面」「…（略）」这类折叠写法。
矩阵的价值就在于**逐条可核对**，省略掉的那几条就是后面没人写测试的那几条。
编号连续、不跳号、不乱序（与 Checklist 的 `AC-NN` 逐字对应）。

🔴 **③ 每个分支标优先级 `P0/P1/P2`**
- **P0**：核心路径 + 数据正确性 + 权限边界 —— 挂了等于功能不可用或有安全问题
- **P1**：重要但有降级空间（次要字段、提示文案、非关键排序）
- **P2**：增强型（极端边界、可用性细节）

用途：回归时**按优先级选子集跑**（对应项目 AGENTS.md 的 L1/L2/L3 跑测分层），不必每次全量。

🔴 **④ 每个分支必须写「前置条件」**
只有分支和断言、没有前置条件的用例会**假通过** —— given 没构造对，then 碰巧也成立。
- ❌ `验证扣款成功` —— 账户余额是多少？有没有并发锁？
- ✅ `前置：账户余额 100、无冻结、无进行中的同笔订单 → 扣款 30 → 余额 70 且流水 +1 条`
- 前置条件要写到**能照着构造数据**的程度，不是「有一条数据」这种废话

🔴 **⑤ 预期结果必须具体，禁止模糊表述**
被禁的写法（出现即判不合格）：`显示正确` / `功能正常` / `符合预期` / `返回成功` / `数据无误` / `页面正常`
- ❌ `预期：列表显示正确`
- ✅ `预期：返回 2 条，按 createTime 倒序，第一条 status=APPROVED`
- 后端写到**字段名 + 具体值/条数 + 副作用**（DB 有无新增、状态如何流转）
- 前端写到**具体文案 + 具体状态**（Toast 文案原文、按钮是否置灰、跳转到哪个 URL）


## 🔴 矩阵自评（落盘前强制，Review 门控的输入）

> 矩阵是 AI 自己写的，**"每条 AC 都有分支"只证明格子填满了，不等于分支写得对**。
> Step11.3 治的是「代码侧的虚假安全感」，本节治的是「矩阵侧的」—— 两者是同一类问题的两端。
> 自评结论随矩阵一起提交人工 Review，让人从"通读一遍"变成"核对 AI 自己标出的问题"。

**三个维度逐条过**：

| 维度 | 自问 |
|---|---|
| **覆盖率** | 需求里的关键功能点有没有漏？异常场景够不够（断网 / 服务超时 / 下游返回脏数据）？边界条件够不够（最大长度 / 空值 / 特殊字符）？ |
| **逻辑性** | 前置条件够不够充分到能照着构造？预期结果是否具体到字段与值？ |
| **规范性** | 用例标题能不能一眼看出测什么？步骤是否可直接执行、无需再问人？ |

**判定：以下任一命中 → 本步未完成，修完再提交**

1. 存在**没有前置条件**的分支
2. 存在**模糊预期**（命中上面 ⑤ 的禁用词）
3. 有 `AC-NN` **缺「业务约束」分支**且未写明「无状态机/无数据依赖」
4. 存在**一条验多个测试点**的用例
5. 存在**未标优先级**的分支
6. 矩阵里出现「其余同理」「…（略）」这类省略

> 不打 0–100 的质量分：AI 给自己的产出打分永远是 85 上下，没有信息量，还会让人误以为"挺高的"就放过去。
> **上面 6 条是可判定、可复核的**，比一个数字有用。

**自评输出**（附在矩阵文件末尾）：

```
| # | 维度 | 问题定位(AC-NN + 分支号) | 问题描述 | 处理 |
|---|---|---|---|---|
| 1 | 逻辑性 | AC-07 分支2 | 预期写「筛选结果正确」，未给条数与排序 | 已改为「返回 2 条，按 createTime 倒序」 |
| 2 | 覆盖率 | AC-12 | 缺业务约束分支（该 AC 涉及审核状态流转） | 已补分支4 |

自评结论：6 条判定项全部不命中 → 可提交 Review
```

问题必须**精确到 `AC-NN` + 分支号**，不接受「整体覆盖不足」这类笼统结论。

**分支约束**：每个 Checklist 条目（按 `AC-NN` 编号）拆解至少 **4 个分支**，**每个分支必须标注来源 `AC-NN`** 与优先级：
1. **正向主流程**
2. **边界值校验**（数量 0 / 字符串超长 / null / 负数等）
3. **异常流阻断**（无权限 / 数据不存在 / 下游不可用等）
4. 🔴 **业务约束**（状态机流转 + 数据依赖）—— 例如「已审核的能否再提交」「主记录被软删后子记录怎么处理」「并发改同一条记录」
   - 这一类是**最容易漏**的：它不违反任何格式校验，走的是合法入参的非法状态组合，编译器和参数校验都拦不住
   - Step3 的「场景完备性自检」是**需求层**的提问，本条是**代码分支层**的清单，两者不能互相替代
   - 该 AC 确实不涉及状态流转与数据依赖时，写明「无状态机/无数据依赖」，不留空

必须写明断言预期结果（如返回404且数据库无新增）。

## 🔴 回归验证清单（第二份产出物，强制）

> **上面的矩阵只回答"新需求做对了吗"，不回答"有没有弄坏既有功能"** —— 它的分支全部按新 `AC-NN` 拆，既有功能一条都不在验证范围内。而"全局落点"规则鼓励改共享层，改共享层 = 影响全部调用方，**风险被放大了却没有对应验证**。这份清单专门堵这个洞。

**输入**：Step4「回归风险候选」表 + 影响面清单中判定"不需改"但走同一段共享代码的点 + Step6 破坏性变更表的「其他调用方」。

```
| # | 受影响的既有功能 | 因为改了什么 | 期望不变的行为 | 验证方式 | 谁来验 | 结论 |
|---|---|---|---|---|---|---|
| R-01 | Walmart 素材列表 | 共用 AssetQueryBuilder 注入权限 | 返回条数/字段与改动前一致 | 既有单测 XxxQueryTest | 单测 | |
| R-02 | xxx-provider Feign 调用 | 响应字段类型变了 | 反序列化不报错 | 10.4 实机打一次端点 | AI(10.4) | |
```

**硬约束**：

- **每条回归项必须有验证方式**，按成本从低到高选：①跑既有单测 ②10.4 实机打一次端点 ③人工回归（写进对应 `REPLAY.md`）
- 改了共享层 / 既有接口 / 公共 Service 却**清单为空 → 本步未完成**（确实零回归风险须写明依据）
- 回归项用 **`R-NN` 独立编号**，不占用 `AC-NN`（AC 是新需求的追溯主键，两者不混）
- 结论由 Step10.3 / 10.4 回填；Step11 A4、Step12 维度 C 按本清单核对，**存在未验证回归项不得判 PASS**
- 🔴 **结论有三态，不是两态**：**已验证**（有测试/实机证据）、**人工豁免 `WAIVED`**（知道没验，
  但决定放行）、**未闭环**（判 FAIL）。有些回归项**本流程无法自证** —— 典型是依赖仓库外资产
  （Loki/Grafana 告警规则、运维配置、第三方后台），代码侧 Grep 完也只能证一半。这类项要么去问到人，
  要么**显式豁免**，禁止硬凑成「通过」。
- 豁免的写法：该行标 `🟡 WAIVED`，并在文档内另起一段 **「R-NN 风险接受记录」**，写明四件事 ——
  ①**已做的**（做到哪一步、证据在哪）②**没做的**（哪部分无法自证，为什么）③**决策人与日期**
  ④**残余风险**（尤其「失效时是否有声音」——静默失效的风险必须写出来）。
  缺这段记录的 `WAIVED` 判 FAIL。
- 豁免**不计入已验证**，汇总口径写「N 项测试证实通过，M 项 WAIVED」，校验器也会单列一条 ⚠️ 始终显形。
  它是**待办**不是**完成**，上线后要保持关注。

**产出物**：
1. `.../Step 7-单元测试验证指标矩阵.md`
2. `.../Step 7-回归验证清单.md`（既有功能不被破坏的验证项，`R-NN` 编号）

**→门控**：🟡 **通知式** —— 两份文档落盘 → 汇报路径 + 矩阵自评结论（6 条判定项是否全不命中）→ 直接进入 Step8。

> 🟡 **通知式门控**：产出物落盘 → 跑 `validate_step.py`（FAIL 必须修到通过）→ **一句话汇报**（路径 + 校验结果 + 本步做的关键决策）→ **不等待，直接进入下一步**。
> 用户随时可提异议；收到异议必须**回退重做本步及其下游**，不得争辩已经过了。
> 之所以不阻塞：本步产出物是文档/任务清单，**改起来几分钟且未产生不可逆后果**；把人的注意力省给真正拦不可逆事项的那几道门。

> 🔴 **AC 编号逐条写，不用区间**：矩阵行首写 `AC-01 / AC-02 / … / AC-06`，不要写 `AC-01 ~ AC-06`。`validate_step.py` 不展开区间，会把区间内的 AC 判成「未覆盖」（CP-57189 实测：AC-02~05 被误报，Step 8 记录一直缺失，看板流程步骤显示未执行）。
