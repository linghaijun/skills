## 0. 红线：默认只读

允许：浏览、筛选、翻页、切账号、截图、抓包。
**禁止：删除、修改、上传、分发、改名、提交任何表单**，以及一切会写数据的点击。
唯一例外是用户对**该具体动作**单独授权，且授权**不跨条目、不跨会话继承**。
拿不准某个按钮会不会写数据时：**先问，别点**。

🔴 **「账号可用」不等于「写操作被授权」—— 每一次写/删都必须单独问。**

用户给了一个能登的测试账号，只代表**这个账号可以用来测**，**不代表**可以拿它去
删除、修改、上传、分发、提交。常见的错误推理，全部不成立：

| 错误推理 | 为什么不成立 |
|---|---|
| 「用户给了账号，就是让我去测」 | 给账号解决的是**能不能登进去**，不是**能不能写** |
| 「这是测试账号 / 测试环境，写坏了无所谓」 | 测试库里常有真实客户数据；写操作还会污染**其他人正在用的**验证基线 |
| 「这条 AC 本来就要写操作才能验」 | 那更要问 —— AC 需要写，不等于此刻可以写 |
| 「上一条写操作用户同意了」 | 授权**不跨条目**。上一条同意的是上一条 |
| 「用户说『帮我验证』就是默认授权了」 | 「验证」是目标，不是对具体写动作的授权 |

**正确做法**：读操作先做完（定位入口、确认数据现状、想清楚会写什么），
然后**带着具体信息问**，让用户一眼能判断风险：

> 要验 AC-NN 需要执行写操作：
> **动作**：点「X」按钮 ｜ **账号**：`<登录名>` ｜ **对象**：`<具体哪条数据>`
> **会产生什么**：`<新增/修改哪张表的什么记录>`
> **可逆吗**：`<能否撤销、怎么撤销>` ｜ **影响面**：`<是否影响其他人的数据或基线>`
> 确认执行吗？

用户明确说「可以」才动手。**只要对方没有明确说可以，就当作没授权。**
拿不准算不算写操作时，按写操作处理。

凭据永远由用户输入，AI 不代输、不读取凭据存储。

## 1. Step 0：两件事不做，后面所有证据作废

### (0) 🔴 动手前必读：脚本分层 + 坑清单 + 页面笔记（别现写、别重摸）

页面整体很少大变，**大多数操作路径可复用**。变了就更新资产，不要每次从零写探针。
开浏览器前按下面顺序读完再动手（跳过 = 白跑一轮的高发原因）：

| 顺序 | 读什么 | 放哪 | 解决什么 |
|---|---|---|---|
| **①** | **`cdp-drive-real-chrome` → `references/SCRIPTS.md`** | skill（跨项目） | 全局层脚本目录 + 选型决策树 + **坑清单**；**禁止先现写** |
| **②** | 同 skill → `projects/<项目>/README.md` + **`PAGE-NOTES.md`** | skill 内按项目分目录（不进项目 git） | 页面层脚本（如 Ads 布景）+ 该项目页面的事实 / 口径 / 坑；页面改版只改这里 |
| **③** | 新项目还没有 PAGE-NOTES 时：同 skill → `references/PAGE-NOTES-GUIDE.md` + `PAGE-NOTES-TEMPLATE.md` | skill | 记什么 / 不记什么 / 过期规则；按模板新建 `projects/<项目>/PAGE-NOTES.md`（**不放项目目录、不进 git**） |

**脚本分层判据**（写前先问「下次换个需求还能直接跑吗？」）：

| 层 | 位置 | 失效条件 | 回写时机 |
|---|---|---|---|
| **全局层** | `cdp-drive-real-chrome/scripts/` | 几乎不过期 | 新通用手法验证 ≥2 次 → 升入 + 更新 SCRIPTS.md |
| **页面层** | `cdp-drive-real-chrome/projects/<项目>/` | 该项目页面改版 | 布景/选择器变了 → 改脚本 + 刷 README「最后验证」 |
| **L2 一次性** | `.workbuddy/tmp/` 或 `docs/develop/<需求>/` | 当次 AC | **不沉淀**；复用第二次再升级 |

收尾回写（本轮新知道的必须落盘，否则下次还会重摸）：

1. **坑 / 通用手法** → CDP `references/SCRIPTS.md`（坑清单）或全局层脚本
2. **本项目页面操作 / 口径 / 坑** → CDP `projects/<项目>/`（脚本 + README + PAGE-NOTES.md）
3. **证据标注工具** → CDP 全局层 `scripts/`（`annotate-rects.py`（默认，吃页面导出的 rects）/ `annotate.py` / `compose.py`；`annotate-legend.py` 是图例版，不合 §4.1，验收证据别用）
4. **用到的笔记条目** → 刷新「最后验证」日期；走不通先怀疑过期

🔴 **笔记/说明书不是真源，是省时间的线索**：

- **按记录走不通 → 先怀疑记录过期，不是怀疑环境或代码**。UI 改版比什么都快
- 关键结论（页面背后是哪个库、数据指纹）**仍要按下面 (1)(2) 当场验一遍**
- 发现写错的当场改掉，不要留着「以后再说」

### (1) 扒清「页面背后是哪个后端、哪个库」

前端 dev server 的代理前缀会把真实后端地址挡住。逐层扒：
**代理配置（`.env` / vite config）→ 监听该端口的进程命令行（profile、额外配置文件）
→ 那份配置里的 jdbc/连接串**（只看地址行，跳过凭据行）。

### (2) 数据指纹比对

🔴 **别靠「用户说这是测试环境」就开工。** 域名可能起错名（实测遇到过 endpoint 叫
`common-prod-cluster` 的测试库），DNS 也定不了案（RDS 域名解析出公网 IP，
与库自报的内网 hostname 无法比对）。

做法：从**取证用的库**里捞几条**只有该库才有**的具体记录（名称 / 唯一尺寸 / 单号），
去页面上找。**连「该没有的那一类」也要对上**（如某类型应为 0 条）。
对上才说明页面证据与 SQL 证据同源；对不上就停 —— 互相打架的证据比没有更糟。

## 5. 判定失败归属：先怀疑自己的探测脚本

注入脚本的语法错误会以「页面报错」的形式返回。看到 `SyntaxError` 先复查自己写的表达式。
把 JS 写进**独立文件**再喂给驱动脚本，不要塞进命令行参数（引号/换行极易出错）。

同理，页面「看起来坏了」时，先按顺序排除：
**自己的脚本 → 自己刚才的误操作（如污染了筛选）→ HMR 残留 → 才是被测代码。**

## 6. 结论要分清三种「没通过」

| 判定 | 含义 |
| --- | --- |
| **FAIL** | 实现坏了 / 与 AC 不符 —— 要修 |
| **BLOCKED** | 实现没坏，但**验收条件在产品里构造不出来**（依赖不存在的入口/流程）—— 要改 AC，不是改代码 |
| **PARTIAL** | GWT 有多个断言，只证了一部分 —— 写清已证/未证与补法 |

把 BLOCKED 误记成 FAIL 会让人去改没坏的代码；误记成 PASS 则留下假绿灯。

落盘用中文状态词：FAIL → `失败`、BLOCKED → `阻塞`、PARTIAL → `部分`（另有 `通过` / `走读证据` / `跳过`）；`RESULT.md` 顶层 `- 结论：` 与 `verify_state.py finish --status` 用同一个词，门禁会比对（§12.1、§12.7）。

### 6.1 实测不了时：「走读证据」能用，但必须单独成类

代码走读证明的是「代码会走哪条路」，证明不了「运行时真的这样」。它是**降级证据**，
不等于实测通过，也不能让 AC 自动变成 `[done]`。

**只在这三种情况下可用：**

| 情况 | 用法 | 例 |
|---|---|---|
| ① 路径同一 | 待证场景与**已实测**场景走同一段代码，差别只在不影响结果的参数 | 「All Assets 作用域」与单素材同一接口、同一组件，作用域只进查询条件 |
| ② 入口不存在 | 代码证明用户点不到该入口 → **改写 AC 或标「不适用」**，不是「通过」 | 入口按钮被 `v-if` 隐藏，验收条件在产品里构造不出（即 §6 的 BLOCKED） |
| ③ 失败分支浏览器构造不了 | **以单测为主**（mock 失败 + 断言产出），走读只作补充说明 | 后端拉图失败仍出文件 |

**🔴 不能用走读代替的：**
- 依赖外部系统 / 真实数据的行为（上游会返回什么、某类数据是否存在）—— 代码只能说明「会去查」
- 视觉与布局（截断、列宽、换行、遮挡）—— 代码里写了截断 ≠ 显示正确
- 权限与否定型验收（「看不到」「不可见」）
- 无单测佐证的「自己写的代码」—— 走读者与作者同源，误解会被原样复述

**落盘格式（写进 `RESULT.md`）：**
- 状态写 `走读证据`，与 `实测通过` / `构造通过` / `NOT_RUN` 并列，**不混用**
- 逐条给 `file:line`，写明「与哪条已实测路径同一 / 差异是什么 / 为什么差异不影响结果」
- 写出**「若判断错了，会表现为什么现象」**—— 这一句同时就是给 QA 的回归点，要同步进交接文档「回归重点」
- 该 AC 在 Checklist 保持 `[open]`，**走读证据是交付门禁处给用户的放行依据**，放行与否由用户决定

## 7. UI 做不了的验收 → 走接口级，别硬找不存在的按钮

某条 AC 的操作入口在产品里不存在（开关只对部分平台渲染、该场景没有对应流程）时，
**先判 BLOCKED，再和用户确认是否改成接口级验收**，不要在页面上反复找。

接口级验收的四条凭据纪律：

1. **AI 不代输、不代跑远程服务的登录**。哪怕用户明确要求、哪怕密码 AI 看不见 ——
   能被「用户坚持」解除的边界就不是边界。本地开发应用（localhost）的测试凭据是唯一例外。
   正确姿势：把脚本写到只差一条命令，**用户自己跑**，结果落到证据目录由 AI 读。
2. **脚本零凭据**：密码放在被 `.gitignore` 覆盖的文件里，运行时才读。
   ⚠️ **脚本本身若被 git 跟踪，凭据文件不能与它同目录** —— 一次 `git add .` 就提上去了。
   最好在脚本启动时自查凭据文件是否真被忽略。
3. **token 不落盘、不打印、不写日志。**
4. 密码过期**只改凭据文件**，永远不要为省事写进代码。

### 发请求前先读 DTO

按常见写法猜字段名是高频翻车点（实测：分页猜成 `pageNum/pageSize`，
实际是 `pageInfo{pageIndex,pageSize}` → 500 且错误信息为空）。
**以后端 `*Req` 类为准**：必填注解、setter 里的归一化逻辑都要看。这是「零臆测」在接口调用上的落点。

### 脚本必须打印错误响应体

只打 `code`/`msg` 时，500 会显示成 `code=None msg=None`，等于把唯一线索吞掉，
再跑一轮才知道错在哪。失败分支一定要带上响应正文（截断即可）。

## 8. 权限类验收：页面现象推不出结论

**验「谁能看到什么」时，页面上的筛选项、计数、下拉内容都不能作为权限依据。**
必须读后端实际计算出的权限集（日志 / 接口返回），否则极易得出相反结论。

真实踩过的三个反例：

| 错误推断 | 为什么错 |
| --- | --- |
| 「筛选下拉是空的 → 该用户没权限」 | 下拉往往由**有数据的维度**派生（如"已投放平台"），不是**被授权的维度** |
| 「它看到 68 条、超管看到 220 条 → 它被限制了」 | 两数来自**不同环境 + 不同租户**，不可比 |
| 「无权限却看得到 → 越权泄漏」 | 建立在上面两条错误前提上；查日志后证伪 |

### 🔴 空集合陷阱

权限代码常见写法是「集合非空才拼 `IN (...)`」，于是**集合为空 = 不拼条件 = 不过滤**，
最窄的场景翻转成最宽。所以「看得到」要分两种：

- **过滤生效且放行** → 权限链路在工作，可判 PASS
- **过滤根本没生效** → 假绿灯，比 NOT_RUN 更危险

判据：看权限集的规模。为 0 / 空时必须追查是「真无权限」还是「退化成不过滤」。

### 先搞清数据是经哪条通路放行的

多维度权限（如"创建人维度 + 归属维度"）下，**系统生成/同步的数据往往没有创建人**，
创建人维度永远匹配不上，可见性完全由另一维度决定。
这决定了验收账号要按哪个维度去挑 —— 挑错维度，账号再多也验不出东西。

### 账号选择

- **肯定型**（有权限可见）：必须用**普通受限用户**，超管天然全可见 → 假阳性。
- **否定型**（无权限不可见）：需要目标资源**不在其授权集内**的普通用户，
  而不是"随便一个普通用户"（没配规则的用户可能反而全可见）。
- 去哪找这样的账号、内部没有时能不能用客户账号，见 §10。

## 9. 一组数据双向判定，比分别验证更强

验「A 可见 / B 不可见」这类成对的 AC 时，**一次抓取同时判两边**：
以 A 身份取数后，既检查"A 自己的资源在不在"，也检查"B 的资源在不在"。

单验一边可能是「恰好没数据」，双向都成立才排除这个可能。
（实测：跨租户隔离与共享可见两条 AC 用同一次抓取的 `ownHits` / `otherLeaks` 同时判定。）

## 10. 找账号：先定数据，再按平台查用户

缺数据的 AC（要翻页的行数、某种广告类型、某个平台）**不是去页面上碰运气**，而是反着找：

1. **写清这条 AC 要什么数据**：平台、广告类型、条数下限、日期范围、是否需要受限账号（否定型）
2. **在业务数据所在的库里找到满足条件的对象**，拿到它的 `profileId`（DSP 是 `advertiserId`）——
   业务库是哪个，看 Step 0 扒出来的「页面背后是哪个后端、哪个库」，别想当然
   - 业务大表若有门禁（如要求同时带 profile 维度 + 有界日期），就**倒过来**：先从账号库取候选用户的 profile 列表，
     再逐个带 profile + 日期去业务表点查，别想着先全表捞对象
3. **按平台的账号库把 profile 映射到用户**（下表），再按账号优先级挑人
4. **报给用户之前先预演**（§11 第 2 条）：按该账号的 client / profile / 平台配置，把页面会发的那条查询在库里跑一遍，确认会出行；平台配置为空、profile 不在授权内这类问题要在这一步发现，不要等用户登录后才发现
5. **报给用户**：建议账号（userId + 登录名 + client + 角色）、为什么是它（命中哪条 AC 的哪类数据）、
   内部还是客户账号；用户登录后再继续（§2.2）

### 账号优先级

1. **内部账号**（邮箱为公司域名、client 为内部 / 测试 / Sandbox 类）—— 默认只在这里找
2. **真实客户账号**：内部账号确实没有所需数据时，**须用户在本次任务里明确同意**才可使用（同意只对本次任务有效）。
   用了就必须：全程只读；截图只留判定点，裁掉无关客户数据；文档里标注「真实客户账号，用户 YYYY-MM-DD 同意」；
   证据不外传
3. 两类都找不到 → 记 `NOT_RUN` / `[open]`，写明**缺什么数据、查过哪些库表**，别拿超管或无关账号凑数

否定型 AC 仍然只能用受限普通账号（§8），优先级不改变这条。

### 各平台账号库表 → 见项目 `AGENTS.md`

库名、用户 → 权限 → 对象的链路、列名大小写因项目与平台而异，**写在项目 `AGENTS.md`**（creative-management 见「实机验证：按账号找数据」节），不在本 playbook 维护。
首次使用某张表先用 `INFORMATION_SCHEMA.COLUMNS` 核实列名；只能访问哪些库先用 `SELECT name FROM sys.databases WHERE HAS_DBACCESS(name) = 1` 确认；SQL Server 版本不同，`STRING_AGG` 等函数可能不可用。

### 查库纪律

- 🔴 **只读、单语句**；**禁止 `SELECT *`**，只列身份与权限列。凭据列一律不读、不写进文档，
  已知的有：`pwd` / `pwd2` / `salt` / `token` / `RandA`（`User`）、`biPwd`（`Client`）、
  `mwsToken` / `mwsApiToken` / `spRefreshToekn`（`Profile`）—— 新表先看列名再写 SELECT
- 🔴 **别对大表做无条件聚合**（如对全量广告表求 `MAX` / `COUNT`）：先用带索引的条件（`profileId` / `userId`）
  或 `TOP` 收窄。没有查询超时的 MCP 会被一条慢查询堵死，之后所有调用都排队
- 先查小表（用户、profile 映射），再拿 id 去大表点查；跨库 `UNION` 遇排序规则冲突加 `COLLATE DATABASE_DEFAULT`

### 换账号测试

- 换账号走 §2.2 交接；登录后**先核对身份**（页面右上角用户名 + 接口 / store 里的 userId）与计划的账号一致，再取证
  - **登录用的是「账号」字段，不是邮箱**；同一个人 / 同一邮箱可能有多个账号，各对应不同 userId —— 报给用户时写清要登录的**账号名**（库里的账号字段）而不是邮箱，登录后只认 userId 核对；不一致立刻停，请用户换计划的账号重新登录（实测首次登录落到了非计划的另一个 userId）
