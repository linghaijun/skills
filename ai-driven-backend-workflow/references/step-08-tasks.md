# 第八步：任务拆解（生成 tasks.md）

> 在编码前把需求拆成可勾选、有依赖顺序的实现任务清单，作为第九步逐条编码的唯一进度跟踪表。采用 OpenSpec tasks 模板。

**输入**：Checklist + DDL + API 契约 + 测试矩阵

**动作**：将 Checklist 每条（结合 DDL/API 落点）拆解为具体实现任务，按依赖顺序编排。

## tasks.md 结构
```markdown
## 1. <任务组名>
- [ ] 1.1 <任务描述，对应 Checklist AC-NN> [P0] [~2h] DoD: <完成判据>
- [ ] 1.2 <任务描述> [P1] [~1h] DoD: <完成判据>

## 2. <任务组名>
- [ ] 2.1 <任务描述> [P0] [~0.5h] DoD: <完成判据>

## 3. 回归任务（承接 Step7 回归验证清单）
- [ ] 3.1 <回归项 R-NN 的适配/验证任务> [P0] [~0.5h] DoD: <期望不变的行为已确认>

## 汇总
- 任务总数：X 条（P0: X | P1: X | P2: X）
- 预估总工时：~Xh
- 覆盖：AC X 条 | 回归项 R X 条
```

> **回归任务组的勾选时机**：第 3 组（回归单测、质量门禁、只读 SQL、写进测试交接文档）在测试步 / 交付收尾才做完，所以 `validate_step.py` 在**编码步只查第 1、2 组**，第 3 组在**交付门禁（全局一致性步）**才要求全部勾选。组标题必须保留「回归任务」字样，脚本靠它识别分组；不要把编码任务放进这一组躲检查。

### DoD（完成判据，强制）

只有 `[P0][~2h][AC-NN]` 说不清"什么算做完"，结果是"写完了但没接上"。每条任务必须带一句**可客观判定**的 DoD：

- ✅ 好：`DoD: POST /asset/share 返回结构与 Step6 契约一致（含 shareId/shareName）`
- ❌ 差：`DoD: 功能正常` / `开发完成` / `代码写完`

DoD 未达成**不得勾 `- [x]`**；Step11 A 表以 DoD 作为"是否真的实现"的判定依据之一。

### 优先级与估时
- **P0**：核心路径，阻塞下游（主表 Mapper/核心 Service/非功能落点/复用任务）
- **P1**：重要不阻塞（辅助查询/校验）
- **P2**：增强型（优化/魔法值抽取/边界补全）
- **估时**：CRUD ~0.5h，含业务逻辑 ~1-2h，跨模块 ~2-4h；超过4h需再拆分

**约束**：
- 每条任务必须标 `[P0|P1|P2]` + `[~Nh]`，缺任一视为未完成
- 任务粒度和 Checklist 条目对齐，便于逐条编码和回溯
- 末尾必须有汇总行（总数/P分布/总工时）
- 只做拆解，不写代码
- 进度跟踪：`- [ ]` 未完成 / `- [x]` 已完成

**产出物**：`.../Step 8-tasks.md`

**→门控**：🟡 **通知式** —— 落盘 → 汇报任务数 / P 分布 / 预估工时 → 直接进入 Step9。

> 🟡 **通知式门控**：产出物落盘 → 跑 `validate_step.py`（FAIL 必须修到通过）→ **一句话汇报**（路径 + 校验结果 + 本步做的关键决策）→ **不等待，直接进入下一步**。
> 用户随时可提异议；收到异议必须**回退重做本步及其下游**，不得争辩已经过了。
> 之所以不阻塞：本步产出物是文档/任务清单，**改起来几分钟且未产生不可逆后果**；把人的注意力省给真正拦不可逆事项的那几道门。

> 结构搬自 OpenSpec tasks 模板。详见 openspec-integration.md。
