# 第十二步：全局一致性审查与交付收尾

> ⚡ **子 agent 加速**（先过 `subagent-acceleration.md` §1 三问，判断不了就不派）：全局一致性：证据验收**必须**独立子 agent 盲审；跨文档一致性可按文档对并行拆分。

> 本步是交付前的**最终质量门禁**。Step11 已验证"代码符合需求"，本步验证"所有产出物彼此自洽"，确保文档链与代码链一致性，通过后统一交付。

**输入**：Steps 1~11 全部产出物（所有文档 + 全部业务代码 + 全部单测代码）

**动作**：对所有前置步骤的产出物进行跨步一致性审查，发现不一致时修复，最后统一提交。

## 六维审查（A ~ E 一致性 + F 证据验收）

### A. 文档链一致性（Spec ↔ Checklist ↔ 技术设计 ↔ DDL ↔ API ↔ 测试矩阵）
逐对检查文档间是否存在矛盾：
- **Spec vs Checklist**：Checklist 每条场景是否都能在 Spec 中找到对应的 Capability？Spec 中声明的 Capability 是否都有 Checklist 覆盖？
- **Checklist vs 技术设计**：Checklist 中的业务规则在技术设计中有无对应的伪代码/逻辑说明？
- **技术设计 vs DDL**：DDL 表字段是否覆盖了技术设计中涉及的全部持久化字段？类型是否匹配？
- **DDL vs API 文档**：API 请求/响应字段与 DDL 字段的命名是否一致（如 user_id vs userId，按项目中蛇形/驼峰规范校验）？
- **API 文档 vs 测试矩阵**：测试矩阵中的每个 API 调用是否在 API 文档中有对应端点定义？参数一致？
- **Checklist 两版一致（CRITICAL）**：`Step 3-Checklist-Jira.txt` 与 `Step 3-Checklist.md` 的条目数、`AC-NN`、顺序、前缀、状态标记、GWT 文本逐字一致；纯净版中不得出现任何标题/表格/说明性内容
- **AC 编号闭环（CRITICAL）**：以 Checklist 全量 `AC-NN` 为基准集，核对每个编号在 Step7 测试矩阵、Step8 tasks.md、Step10 自检报告、Step11 AI Review A 表中**四处均有出现**；任一处缺席判 ❌
- **AC 状态门禁**：Checklist 中所有条目应为 `[done]`；存在 `[open]`/`[blocked]` 时，逐条列出 `AC-NN` + 原因 + 用户是否同意放行，未放行不得进入交付收尾
- 🔴 **AC 时效性反查（L18）**：逐条回读 Checklist —— **这条 AC 描述的，还是代码现在真正做的事吗？**本次若有「有意改变既有行为」的改动（含为修缺陷而改），受影响的 AC 会**悄悄过期**：它不报错、测试也不红，只是从此描述了一个不存在的行为。过期 AC 有两害——照它验收会把**正确实现判成 fail**，照它回归会**长期保护一个已废弃的行为**。发现过期立即改写并注明「原文描述的是 X 时期的行为，因 Y 改为 Z」。🔴 **改写 AC 时必须同步改掉所有内嵌了该条原文的 `tests/AC-NN/case.md`**（`grep AC-NN tests/`）—— 漏改会留下两份互相矛盾的「原文」。**存在未改写的过期 AC、或 case.md 与 Checklist 不一致，不得判 PASS**
- **Jira 同步一致性（若已同步）**：文首 `AC-NN ↔ Jira Issue Key` 映射表与 Jira checklist 实际内容一致；本轮新增/改号的条目已同步更新 Jira
- **非功能映射表落地检查**：Step4 非功能映射表中所有落点（DDL/代码/API）是否在实际产出物中全部找到？

### B. 代码文档一致性（文档 ↔ 业务代码）
- API 文档端点路径/Method/参数/响应结构与 Controller 代码逐一比对
- DDL 表名/字段名与 Entity/Mapper XML 中的 SQL 片段比对
- 技术设计中声明的复用点是否在代码中实际调用了既有方法（非重复实现）
- 技术设计中声明的非功能落点（@Transactional/@Cacheable/@PreAuthorize/乐观锁）在代码中是否存在

### C. 测试代码一致性（测试矩阵 ↔ 单测代码）
- 测试矩阵中每个 Checklist 条目的 4 个分支（正向/边界/异常/业务约束）在单测代码中是否都有对应的 `@Test` 方法
- 单测中的 Mock 设置是否与被 Mock 接口的实际签名一致（参数类型/返回值类型）
- 单测使用的基础数据是否与 DDL 中的表结构/字段类型一致
- 🔴 **回归终检**：《Step 7-回归验证清单》全量 `R-NN` 结论是否均为通过；Step11 A4 标出的 🔴 Unverified Regression 是否已清零。**存在未验证回归项不得判 PASS**
- 🔴 **破坏性变更终检**：Step6「既有端点变更」表中 🔴 项的调用方是否全部适配；兼容期方案是否在 Spec 记录了旧字段清理时间点与责任人
- **零臆测终检**：Step11 维度 D 标出的 🔴 Unverified Assumption 是否全部已补取证或已获用户确认；文档链（Spec / 技术设计 / API 契约）中是否还残留"待确认 / 应该是 / 按惯例"字样未收敛（见 L8：决策必须回写文档）。**存在未收敛项不得判 PASS**
- **证据归档门禁**：每条 `AC-NN` 的 `tests/AC-NN/` 下 `case.md` + （`script/` **或** `REPLAY.md`）+ `evidence/` + `RESULT.md` 是否齐全，`tests/README.md` 索引是否与目录实际一致；**缺证据的 AC 判未测**
  - 🔴 **`case.md` 必须内嵌 Checklist 该条 GWT 原文**，且与 `Step 3-Checklist.md` **逐字一致**（内嵌是副本，会随 Checklist 改动漂移）；不一致判不一致项，必须修
  - 🔴 **作为判定依据的截图必须有标注版**（`-标注`，文件名内容用中文，框 + 编号 + **框边文字说明**，原图保留）；缺标注版判**证据不完整**，与缺证据同等对待。降级形式（zoom 裁剪图 / 录屏标时间点）须在 `RESULT.md` 写明降级理由
  - 🔴 **落库类 AC（同步/迁移/批量写入/定时任务/权限可见性）必须有覆盖面声明**：`RESULT.md` 写明「浏览器验证账号：X（1 个） | SQL 覆盖：N 个账号 / M 条 | 差异账号：…」。只有单账号实机验证、没有分组全量核对的，判**覆盖面不足**，与缺证据同等对待
- **10.4 收尾门禁**（若执行过浏览器实机验证）：验证报告 **E 表**中所有遗留脏数据是否已标记"已清理"——**存在未清理脏数据不得判 PASS**；**F 表**是否已 `git status` 确认无残留调试代码，提交前再复核一次

### D. 自动化一致性检测
- 若项目存在一致性检测脚本（Python/shell 脚本），运行并捕获输出
- 若不存在，AI 对上述 A~C 维度的关键项执行自动化逻辑检查（如正则匹配 API 路径、字段名交叉对比）
- **任何自动化脚本产出的报告必须复制到 docs 目录**，命令格式：`Step 12-{报告名}.{扩展名}`

### E. 修复与追溯
- 发现 `❌ 不一致` 项时记录到报告并修复（修改文档或代码，视不一致方向而定）
- 修复后标记该轮修复的文档/文件清单
- 修复若涉及跨层改动（如改 DDL/API 契约/Controller 签名），按 Step11 变更影响重新评估流程处理

### F. 证据验收（验收测试专员，CRITICAL）

A ~ E 查的是「产出物彼此是否自洽」，查不出「**证据是否真的证明了 AC**」—— 代码、证据、结论都出自同一个 AI，会共享同一个误解。
本维度由**独立 subagent** 以验收测试专员身份执行，**先盲审（不读 `RESULT.md`）再对账**，逐 AC **判定证据能不能通过验收**：`验收通过` / `验收不通过`（不通过须注明原因：缺证 / 证据不实）。

- 规则、检查点、派发模板：`references/evidence-acceptance.md`（必读）
- 产出：`Step 12-证据验收报告.md`
- 🔴 只有 `验收通过` 的 AC 才能置 `[done]`；`验收不通过` 的 AC 按该文件「修复循环」补证 / 重测，或交用户放行
- 🔴 主会话不得代做、不得改写 subagent 的判定；对判定有异议时写进报告「对账发现」并交用户裁决

## 产出物格式

`Step 12-全局一致性审查报告.md`，含以下内容：

```
审查概要: 总检查项X | ✅ 一致: X | ⚠️ 轻微不一致: X | ❌ 不一致: X | 已修复: X | AC: 总X [done]X [open]X [blocked]X | AC缺席X

A.文档链一致性:
  | 检查项 | 左文档 | 右文档 | 状态(✅/⚠️/❌) | 不一致说明 | 修复动作 |
  |--------|--------|--------|---------------|-----------|---------|
  | Spec Capability→Checklist 覆盖 | Spec.md:15 | Checklist.md:8 | ✅ | - | - |
A2.AC闭环与状态:
  | AC-NN | 测试矩阵 | tasks | 自检 | AI Review | 状态 | 放行说明 |
  | DDL字段→API字段一致性 | Step 5-ddl.sql:42 | Step 6-API接口定义文档.md:88 | ❌ | 字段 creative_id 在DDL中为 bigint，API文档为 string | 统一为 Long |

B.代码文档一致性:
  | 端点 | API文档定义 | Controller实现 | 状态 |
  |------|-----------|---------------|------|
  | POST /api/shares | 参数名 shareType | ShareController.java:32 参数名 type | ⚠️ 命名不一致，已统一为 shareType |

C.测试一致性:
  | Checklist条目 | 正向 | 边界 | 异常 | 说明 |
  |--------------|------|------|------|------|
  | SHARE - 分享入口 | ✅ | ✅ | ✅ | - |
  | SHARE - 审核状态 | ✅ | ⚠️ | ✅ | 边界测试中空状态未覆盖，已补 |

D.自动化检测:
  | 脚本 | 运行结果 | 报告文件 |
  |------|---------|---------|
  | field-consistency-check.py | 3 warnings, 0 errors | Step 12-field-consistency-report.txt |

E.修复追溯:
  | 文件 | 修复前 | 修复后 | 涉及步骤回退 |
  |------|--------|--------|-------------|
  | ShareController.java:32 | type | shareType | 无（纯代码内重构） |
  | Step 5-ddl.sql:42 | creative_id varchar(64) | creative_id bigint | 是 → 回退 Step5 重审 DDL |
```

> **前序步骤复检**：交付门禁会按当前产出物重跑前面每一步（不写状态）。`.workflow-state.json` 的绿灯只代表登记那一刻通过，之后改过 Checklist / 矩阵 / 问答记录，旧绿灯不会自己变红；复检报 FAIL 就修好并补跑该步 `--record`。另查「用例状态 vs RESULT」「回归清单汇总 vs 各行」「交接文档时效」，回写规则见 `browser-playbook-parallel.md` §12.7。

> **交付门禁 tasks 完成度**：`validate_step.py` 本步要求 tasks.md **全部任务**（含回归任务组）已勾选——回归单测、质量门禁、只读 SQL 结论、前端回归项写进《测试交接文档》都在本步之前完成。

## 交付收尾与代码提交

**前置条件**（全部满足）：
1. A~E 检查全部 ✅ 或 ⚠️ 且已修复
2. 变更影响已处理完毕
3. 用户明确确认"可以提交"
4. 10.3 自检报告全部 ✅
5. Checklist 全量 `AC-NN` 闭环无缺席，且非 `[done]` 条目已获用户明确放行
6. 《证据验收报告》中 `[done]` 的 AC 全部 `验收通过`；`验收不通过` 的 AC 已补证复验通过或获用户放行

**提交规范**：
1. **只 add 相关文件**（业务代码/单测/docs），**禁止 `git add .` / `-A`**
2. **提交信息**：`feat({需求id}): {需求title}` + 涉及模块 + Checklist 覆盖数 + 一致性审查结论
3. **DDL 单独提醒**：代码提交 ≠ DDL 已执行，需显式提醒"需手动执行 ddl.sql（及回滚脚本）"
4. **推送**：推 feature 分支，禁 push main/master/release；禁 `--force`；有冲突先 `pull --rebase`

**提交后**：汇报 commit hash，提醒后续（前端联调/部署/PR）。

## 审查终止条件
- **所有检查项 ✅** → 进入交付收尾
- **存在 ❌ 项** → 修复后重新执行本步（重新审查 + 再提交）
- **证据验收存在 `验收不通过`** → 补证 / 重测后，只对改动的 AC 再派 subagent 复验（最多 2 轮）
- **循环限制**：最多 2 轮修复，第 2 轮仍有 ❌ 则输出完整缺陷清单请求人工介入

**→门控**：🔴 **阻塞（唯一允许 git 提交的环节）** —— 落盘报告 → 汇报审查结论 → **暂停等用户明确说「可以提交」** → 才提交 → 汇报提交结果 → **进入 Step13（AC↔Subtask 匹配与提测）**

> 🔴 **阻塞门控**：必须**暂停等待用户明确确认**，未获通过禁止进入下一步。
> 之所以阻塞：**提交不可逆且对外**：代码进了仓、推了分支，撤回成本远高于多等一次确认。同批还要产出《测试交接文档》交给 QA。
> 经验沉淀改到 **Step13 提测终态之后**（见 `step-13-ac-subtask-handover.md` + `lesson-harvest.md`）。
