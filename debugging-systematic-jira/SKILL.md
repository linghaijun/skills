# 系统化排障（中文）

随机改代码浪费时间，还会制造新 bug。只治症状 = 失败。

**核心原则：先查清根因，再动手改。**

违反流程字面要求，就是违反排障精神。

## 铁律

```
没有完成「阶段 1：根因调查」之前，禁止提出或实施修复。
```

阶段 1 没做完 → 不能给修复方案。

## 何时用

任何技术问题都适用：单测失败、线上 bug、异常行为、性能、构建、联调。

**尤其要强制走流程时：**

- 时间紧、很想「先改一行试试」
- 看起来「一眼就能修」
- 已经试过多次修复
- 上次修了但没好
- 自己还没真正理解问题

**别因为这些借口跳过：**

- 「问题很简单」——简单 bug 也有根因
- 「赶时间」——乱试通常更慢
- 「领导要立刻修好」——系统化比瞎改快

## 四阶段（必须按序，不可跳步）

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细读错误信息**
   - 不要跳过 WARN / ERROR
   - 完整读堆栈：行号、文件路径、错误码

2. **稳定复现**
   - 能否可靠触发？精确步骤是什么？是否每次都出现？
   - 复现不了 → 继续收集证据，禁止猜修

3. **看近期改动**
   - git diff / 最近 commit / 依赖与配置 / 环境差异

4. **多组件系统：先埋点取证**

   系统跨多层（前端 → API → Feign → DB / Redis）时，**先在边界打诊断日志**，跑一遍看**在哪一层断**：

   ```
   对每个组件边界：
     - 记录进入的数据
     - 记录出去的数据
     - 核对环境 / 配置是否传到这一层
     - 核对该层状态
   先跑一轮定位失败层，再只深入那一层
   ```

5. **数据流回溯**

   错误出现在调用栈深处时：坏值从哪来？谁传进来的？一直往上追到源头。
   **在源头修，不要在症状点打补丁。** 详见 [`references/root-cause-tracing.md`](references/root-cause-tracing.md)。

### 阶段 2：模式对照

动手修之前先找「对的样子」：

1. **找仓内同类可运行例子**
2. **对照参考实现要读完整**（禁止只扫一眼就「改编」）
3. **列出工作版与坏版的每一处差异**（别假设「那个无关」）
4. **弄清依赖**：配置、环境、前置假设

### 阶段 3：假设与最小验证

1. **只立一个假设**：写清楚「我认为根因是 X，因为 Y」
2. **最小改动验证**：一次只改一个变量
3. **验证后再继续**：好了 → 阶段 4；不好 → **换新假设**，禁止叠加上一个「再补一刀」
4. **不懂就说不懂**，去查、去问，禁止假装知道

### 阶段 4：实施修复

修根因，不修表象。

1. **先有失败用例**（自动化单测优先；没有框架就用最小复现脚本）
2. **只做一处针对根因的修改**（禁止「顺便重构」）
3. **验证**：用例过了？相关测试没红？问题真的消失？
4. **修了仍不好**：停下数次数；&lt; 3 次回阶段 1；**≥ 3 次禁止再盲修**，先质疑架构（见下）
5. **连续失败 ≥ 3 次：质疑架构**
   - 每次修完又在别处冒新问题 / 必须大重构才能修 / 修 A 坏 B
   - 停下来和用户讨论：模式是否根本不对，是继续贴膏药还是改架构

## 阶段 5：交付闭环（本仓库强制）

排障到「代码改完」不算结束。按下面顺序收尾：

### 5.1 重启门控（禁止 Agent 擅自重启）

改完后先判断是否需要重启服务才能生效：

| 改了什么 | 要不要重启 | Agent 怎么做 |
|---|---|---|
| 后端 Java（`creative-management` / `platform-provider`） | **要**（IDEA 里跑着的 JVM 不热更 class） | **停下来告诉用户**：「请重启后端 xxx」，等用户说已重启再验 |
| 前端 Vite / creativehub 热更能覆盖的 `.vue` / `.js` | 通常不要 | 直接验；若 HMR 异常再请用户刷新或重启前端 |
| 配置 / Apollo / 环境变量 | 通常要 | 明确告诉用户重启哪一侧 |
| 纯文档 / 纯单测 / 未跑着的代码 | 不要 | 直接进入验证 |

🔴 **Agent 不得自己杀进程、不得自己重启 IDEA / Spring Boot / Chrome 日常实例。**  
只说清：重启哪个、为什么、重启完回一句即可继续。

### 5.2 验证（重启完成后再做）

按改动性质选验证层（与工作区 AGENTS 跑测分层一致）：

1. **有单测覆盖** → L1 只跑相关 `*UnitTest`（PowerShell + `mvn.cmd`，输出重定向到日志再读）
2. **无单测** → 明说「本次无测试覆盖」，不要用无关全量绿冒充验证
3. **需要页面行为 / 交互 / 出图 / toast / 配额** → **必须**走浏览器实机验证

### 5.3 浏览器验证 → 用 `cdp-drive-real-chrome`

需要打开页面、点按钮、看结果、截证据时：

1. **先读** `cdp-drive-real-chrome` 的 `references/SCRIPTS.md` + 项目 `PAGE-NOTES.md`
2. **先判定 Chrome 实例**（看 `--user-data-dir`，勿接日常浏览器）
3. **开测先 `chk401.mjs`**，登录失效立刻停、交给用户登录
4. 优先复用 L1 脚本（如 `creativehub-dim-switch.mjs` / `creativehub-drive.mjs`），禁止先现写探针
5. 🔴 点 Generate / 导出 / 写数据 → **本轮单独取得用户授权**
6. 证据落盘到 `.workbuddy/tmp/<需求>/` 或需求目录 `tests/AC-NN/evidence/`（gitignore 路径）

### 5.4 证据回写 Jira

验证通过（或明确失败结论）后，把结论与证据提交到**当前 Jira ticket 备注**。

**备注正文必须用下面三节（标题原文照抄，不要改名）：**

```markdown
**产生原因：**
<一句话 + 必要细节：坏在哪一层、为什么会发生；禁止只写「有 bug」>

**修复方式：**
<改了哪些文件 / 关键逻辑；对应 commit 或分支若已有则写上>

**修复验证：**
<环境 + 步骤 + 断言数字；有截图则嵌进备注正文，禁止写本机路径>
```

操作约定（细则见 [`references/jira-comment-template.md`](references/jira-comment-template.md)）：

1. Ticket 号优先用用户给出的；没有则从分支 / commit 推断，推断不出就问
2. **有截图时默认嵌进备注**：phase1 → [`scripts/jira-run-upload-command.mjs`](scripts/jira-run-upload-command.mjs) 拿 `fileId` → `addOrEditJiraIssueComment`（`contentFormat: html`，三节 + `<figure data-type="media-single">`）；标题用 `<strong>`，禁止 `<b>`
3. 修复验证写**断言数字**；图放在对应说明段落下，不要只写「见附件」
4. 已发过纯文字备注：用 `commentId` **编辑**同一条，塞入 media 节点（已 phase2 的同一 `fileId` 可直接嵌，不必重传）
5. 🔴 **禁止**本机路径（`.workbuddy/tmp/...`）；禁止凭据 / token / 整页 XHR；失败也写三节
6. 含 token 的临时文件用完即删

### 5.5 沉淀 L0 / L1（与验证同轮，禁止拖到「下次」）

Jira 备注写完后**立刻**做 harvest。细则见 [`references/harvest.md`](references/harvest.md)。

**判据**：下次换需求还能直接用吗？

| 答案 | 层 | 落点示例 |
|---|---|---|
| 能跨项目 | **L0 技能级** | CDP `scripts/` + `SCRIPTS.md`；本 skill `references/lessons.md` |
| 仅本项目页面 | **L1 项目级** | CDP `projects/<项目>/` 脚本 + `README.md` / `PAGE-NOTES.md` |
| 仅当次 | **L2** | 留 tmp；**删掉**误放进 skill 的 `_probe-*` |

最低动作（有浏览器验证时）：

1. 可复用操作 → 升入 `creativehub-drive.mjs` 一类 L1 驱动，或独立 `*.mjs` 并登记 README  
2. 页面事实 / 口径 / 坑 → `PAGE-NOTES.md`（带最后验证日期）  
3. 跨项目坑 / 通用手法 → CDP `SCRIPTS.md` 或本 skill `lessons.md`  
4. 改了 skill → `node --check` / 自检 → `distribute-agent-skills`  
5. 回复里用两三行写清「沉淀了什么 → 落在哪」

🔴 **验完不沉淀 = 本 skill 流程未完成**（与「没写 Jira 备注」同级）。

## 红旗 —— 立刻停，回到阶段 1

发现自己在想这些时，**停**：

- 「先临时修一下，以后再查」
- 「改一下 X 看看行不行」
- 「一次改好几处再跑测」
- 「跳过测试，我手动看看」
- 「大概是 X，先修了」
- 「不完全懂，但这样也许能好」
- 「参考太长，我自己改编一下」
- 还没回溯数据流就列「主要该改这些」
- 已经试过 2 次还说「再试一刀」
- 每次修完问题换地方冒出来

**连续失败 ≥ 3 次：先质疑架构，禁止第 4 次盲修。**

## 用户敲打信号（听到就回阶段 1）

- 「不是没发生吗？」——你在未核实的情况下假设了
- 「这样能让我们看到……吗？」——该加取证，而不是猜
- 「别猜了」——在不懂的情况下提方案
- 「再好好想想」——该质疑根本，不是继续贴症状
- 「卡住了？」（烦躁）——当前路径无效

## 常见自我合理化

| 借口 | 现实 |
|---|---|
| 问题简单，不用走流程 | 简单问题走流程也很快，且有根因 |
| 紧急没时间 | 系统化通常比反复试错更快 |
| 先试一刀再调查 | 第一刀定调；从一开始就做对 |
| 修好了再补测试 | 没测试的修复留不住 |
| 一次改多处省时间 | 分不清哪一刀有效，还易引入新 bug |
| 参考太长我改编 | 半懂必出 bug |
| 我看出问题了先修 | 看到症状 ≠ 理解根因 |
| 已经失败两次再试一次 | ≥3 次失败 = 架构问题，先讨论 |

## 速查表

| 阶段 | 关键动作 | 通过标准 |
|---|---|---|
| 1. 根因 | 读错、复现、查改动、取证 | 说清 WHAT + WHY |
| 2. 对照 | 找可运行例子、列差异 | 知道该对齐什么 |
| 3. 假设 | 单假设、最小试验 | 证实或换假设 |
| 4. 实施 | 失败用例 → 单点修复 → 验证 | bug 消失且测试绿 |
| 5. 交付 | 告知重启 → 验证 → CDP（如需）→ Jira 三节备注 → **L0/L1 沉淀** | 票上可复核 + 资产可复用 |

## 「查不到根因」时

若系统调查后确认是环境 / 时序 / 外部依赖：

1. 流程已走完，记录查过什么
2. 做合适处理（重试、超时、明确错误文案）
3. 加可检索日志，方便下次定位

**但：** 95% 自称「没有根因」的，其实是调查没做完。
