# 根因回溯（数据流向上追）

## 原则

bug 常在调用栈深处爆发。在爆发点打补丁 = 治症状。  
**沿着「谁把坏值传进来」往上追，直到找到最初触发点，在源头修。**

## 何时用

- 堆栈很长，错误不在入口
- 不清楚非法数据从哪来
- 需要弄清是哪个调用方 / 哪次用户操作触发的

## 步骤

1. **观察症状**：记下完整错误与现场状态  
2. **找直接原因**：哪一行代码直接抛错 / 写出坏结果？  
3. **问「谁调用了它、传了什么」**：看参数、上下文、闭包里的状态  
4. **再上一层**：重复，直到「坏值在这里被创造出来」或「正确假设在这里被破坏」  
5. **在源头修**：必要时在中间层加防御校验（defense-in-depth），但主修复必须在源头

## 本仓库常见回溯链

| 症状层 | 往上追 |
|---|---|
| 前端 toast / 空结果 | 响应解析 → 请求体 → 发起时的 form / 快照状态（勿用事后 UI 状态重读） |
| Controller 500 | Handler → Manager → Mapper / Feign |
| Feign 失败 | provider Endpoint → 平台 SQL / 上游 HTTP |
| 「有数据但页面像没有」 | 先看 XHR 体，再看权限过滤 / 前端门禁，别只看 DOM |

## 反例

- 只在 catch 里改文案，不查为什么进 catch  
- 用当前 `formData` 解释「生成中途切页签」的旧请求回包（应用点击 Generate 时的快照）
