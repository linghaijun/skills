# 第十步：逐条编码（后端业务代码 + 前端业务代码，Coding Only）

> ⚡ **子 agent 加速**（先过 `subagent-acceleration.md` §1 三问，判断不了就不派）：编码：tasks 中**文件集合互不相交**的任务组（前端组 / 后端组 / 不同仓）可并行派写者子 agent；同仓 `mvn` 别并发，子 agent 一律禁 git。

**输入**：Step1~9 全部产出物（尤其 tasks.md）

**动作**：【核心防错】拿 tasks.md 一条一条喂给 AI 逐个击破，**禁止一次性写完所有代码**。

**约束**：
- 编码提示词："针对 tasks.md 任务 N.x（对应 Checklist AC-NN），结合 Step5 DDL、Step6 接口定义、Step7 前端设计、Step8 测试指标，编写业务代码。"
- **只写业务代码，禁止写测试代码**（测试统一在 Step11.1 编写）
- 每完成一个任务将 tasks.md 中 `- [ ]` 改为 `- [x]`
- **按依赖顺序**：被依赖的先做（后端接口先于前端调用，组件 A 先于依赖方）；无法确定时向用户确认
- **前端编码时若后端未就绪**：按 Step6 API 契约 mock 数据，禁止臆造字段
- 🔴 **按 Step4 选定的落点改，禁止就地打补丁**：Step4「改动落点选择」定了在共享层改的就改共享层，不得图省事在当前调用点复制一份逻辑绕过去。确需偏离时**先说明理由并回写 Step4**，不要静默改变落点
- 🔴 **每完成一条任务顺手核对影响面清单**：Step4 清单中与本任务同主题、判定"需改"的同类点是否都已覆盖；编码中 Grep 时新撞见的同类点必须补进清单，**不得只改手头这一处就勾 `- [x]`**
- 🔴 **有意改变既有行为时，当场标记受影响的 AC（L21）**：本次若决定「改掉原来的做法」（含为修缺陷而改），立刻找出描述旧行为的 AC 并记进待改写清单 —— AC 不会因为实现变了就自动过期报错，拖到Step13才发现就是返工
- 🔴 **日志按「将来怎么查」写（见 L19）**：日志的读者是半年后的人和 AI。每条业务日志带**可定位业务键**；**兜底 / 降级分支禁止把不同根因塌缩成同一句固定文案**（必须带出最内层 cause）；异常作为参数传 logger，禁 `+ e.getMessage()`；永不打印凭据。否则故障时无法区分「永久失败需人工」与「瞬时抖动会自愈」

- 🔴 **后端任务组完成时做一次契约自测（30 秒，别等到 11.4）**：新增/改动的端点各打一次（`javascript_tool` 在已登录页面内 `fetch`，或 curl），确认**实际返回结构与 Step6 契约逐字段一致**（字段名、类型、枚举、分页结构）。不一致立刻改，**不要带着契约偏差进前端编码** —— 否则前端按契约写、后端按代码返回，要到 Step11.4 甚至联调才暴露，返工成本翻倍
  - 🔴 **只打只读端点（GET）**。`POST/PUT/DELETE` 这类**会写库的端点不许在编码步顺手打** —— 本步没有实机验证的授权流程，且本机联调后端连的是生产 US；这类端点要么留到 11.4（按那里的写操作授权红线逐条问），要么由用户当次明确授权后再打

**前后端编码顺序**：建议**后端先行**（接口/数据先就绪），再做前端；也可由用户指定。

**复用点强制落地（承接 Step4/9）**：
- 后端：tasks.md 标注"复用 XXXService.method()"的任务必须直接调用既有方法，禁止新建。签名不匹配时优先扩展既有方法
- 前端：必须复用既有组件与 pacvue-common-utils 工具，禁止重复实现（见 L15）

**非功能需求落地（承接 Step4 映射表）**：逐条对照映射表中"落点=代码/前端代码"的行：
- 事务：跨表写/跨 Service 标注 `@Transactional`
- 乐观锁：UPDATE WHERE 含 `version = #{version}`，Service 捕获 `OptimisticLockException`
- 缓存：`@Cacheable`/Redis，TTL 与映射表一致
- 并发控制：分布式锁(Redisson)/synchronized
- 权限：`@PreAuthorize` 按 API 文档标注 + 数据权限 visibleUserIds/profile（见 L14）
- 入参校验：Controller 层做**枚举值白名单**（非法值返回 `ResultVO.fail`）与**互斥必填空值校验**，不把校验下沉污染 Service；错误文案英文（见 L11、L13）
- 前端：loading/空/错误态、虚拟滚动、防抖、列表 key、Promise reject 处理
- **未落地即未完成**，不得勾选 `- [x]`

**前端编码专项检查**：用户可见错误必须英文友好文案，禁止暴露 `parseFailReason`/API code/异常堆栈（见 L16）。

**前端样式取自设计稿缓存**：需求有 Figma 链接时，编码前确认 `figma/` 已缓存（没有就按 `figma-ui-cache.md` 先跑 `scripts/figma_cache.py`）；色值、尺寸、圆角、字号、间距按 `figma/README.md`「关键样式」表与对应节点的 `design.md` 写，不凭截图目测。编码中发现设计稿与 AC 冲突，进「差异」表问用户，不自行取舍。

**禁止 git 提交（强制）**：只写入工作区，禁 `git add/commit`。提交统一在 Step13 审查通过+人工审批后进行。

**产出物**：
- 后端：Controller / Service / Mapper / DTO（按 `micro-api/src/...` 等既有结构）
- 前端：页面 / 组件 / 路由 / store / API 调用层 / 类型定义 / 样式（按前端仓库既有结构）

**→门控**：🟡 **通知式** —— 汇报代码文件清单（分前后端）+ tasks.md 勾选进度（`validate_step.py` 本步要求编码任务组全部勾选；回归任务组不在本步检查，留到交付门禁）→ 直接进入 Step11。

> 🟡 **通知式门控**：产出物落盘 → 跑 `validate_step.py`（FAIL 必须修到通过）→ **一句话汇报**（路径 + 校验结果 + 本步做的关键决策）→ **不等待，直接进入下一步**。
> 用户随时可提异议；收到异议必须**回退重做本步及其下游**，不得争辩已经过了。
> 之所以不阻塞：本步产出物是文档/任务清单，**改起来几分钟且未产生不可逆后果**；把人的注意力省给真正拦不可逆事项的那几道门。

> 后端规范见 `.agents/code-standards.md`、`.agents/architecture.md`；前端优先复用 Pacvue 组件与 pacvue-common-utils。
