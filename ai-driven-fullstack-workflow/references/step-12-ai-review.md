# 第十二步：AI Review —— 需求回溯与代码合规审查

> 本步验证"代码是否符合需求"（Checklist 回溯）。**仅审查，不提交**——提交统一在 Step13 全局一致性审查通过后进行。

**输入**：Step 3-Checklist.md + Step 6-API接口定义文档.md + Step 7-前端设计文档 + 两份测试矩阵 + 全部业务代码（后端+前端）+ 全部测试代码（后端单测；前端不写）+ Step 11-业务逻辑自检报告

**动作**：以独立审查者视角做**合规审查（A~F）**，再换成**挑刺者视角做缺陷猎捕（G）**，输出格式化报告。审查结果作为 Step13 的输入。

## 审查维度（合规 A~F + 缺陷猎捕 G）

**A. 需求回溯（Checklist Backtracking）**：按 `AC-NN` 顺序逐条比对 Checklist GWT（含 `[前端]/[后端]/[前后端]` 标签）与代码实现，标记 ✅已实现/⚠️部分实现/❌未实现，缺项附具体说明（如"[前端] 未实现 loading 态"）

**A2. AC 覆盖率反查（CRITICAL）**：以 `Step 3-Checklist.md` 的全量 `AC-NN` 为**基准集**，反向核对三处引用——
- Step 8 两份测试矩阵：每个 `AC-NN` 是否都有对应分支？
- Step 9 tasks.md：每个 `AC-NN` 是否都有对应任务？
- 本报告 A 表：每个 `AC-NN` 是否都有实现位置？

任一编号在上述任一处缺席 → **直接判 ❌ 漏实现**，计入「必须修复项」，不得以"应该实现了"带过。报告中输出缺席清单：`| AC-NN | 缺席位置 | 处理 |`。

**A3. 漏改反查（Impact Sweep，CRITICAL）**：以 Step4「影响面清单」为基准集，核对每个判定"需改"的同类点是否真的改了；并**重新 Grep 一轮**六类同类点（读取口径 / 其他入口 / 其他平台 / 读写两侧 / 枚举副本 / 其他调用方），看有没有清单上没有、编码期间新冒出来的遗漏。发现未改点标 🔴 **Missed Sibling**，计入「必须修复项」。报告输出：`| 同类点 | 类别 | 清单是否覆盖 | 是否已改 | 处理 |`

**A4. 回归验证审计（CRITICAL）**：以《Step 8-回归验证清单》全量 `R-NN` 为基准集，逐条核对**是否已验证且结论为通过**。未验证 / 结论空白的标 🔴 **Unverified Regression**，与未实现的 AC 同等对待，计入「必须修复项」。另核对：Step6「既有端点变更」表中所有 🔴 破坏性变更，其"其他调用方"是否都已适配（或兼容期方案已落地且记录了清理时间点）。报告输出：`| R-NN | 受影响功能 | 验证方式 | 结论 | 处理 |`

**B. 前后端契约一致性（Contract Consistency）**：对比前端 API 调用代码（URL/Method/请求参数/响应字段）与 Step6 契约；对比后端 Controller 与 Step6 契约；不一致标记 🔴Contract Misalignment，明确哪一端偏离

**C. API 契约合规（Contract Compliance）**：逐端点比对 URL/HTTP Method/参数（类型/必填/校验注解）/响应结构（字段名/类型）与 API 文档，不一致标记 🔴Contract Breach

**D. 测试覆盖审计（Test Coverage Audit）**：后端 —— 逐分支比对（正向/边界/异常/**业务约束**）与后端单测代码，标记 ✅已覆盖/⚠️边界缺失/❌分支缺失；前端 —— **不写自动化测试（用户约定）**，改为核查 Step11.3 自检报告对《前端测试验证指标矩阵》条目的覆盖，标记 ✅已自检/⚠️待人工验证/❌缺失

**E. 代码质量扫描（Code Quality Scan）**：后端 —— throws Exception、空 catch、魔法值、SQL 拼接、未鉴权接口、@Transactional 缺失、对前端可见文案是否英文（L13）；前端 —— 未处理 Promise reject、硬编码 URL、缺少 key、不必要 re-render、错误文案是否暴露原始技术信息（L16）

**E2. 架构边界合规（跑，不是看）**：执行 `ArchitectureTest` 并**拿退出码**，不得凭阅读判断。三条棘轮规则（Controller 不直连 Mapper / 构造器注入 / utils 不依赖 Spring）任一失败 = **本次新增了架构违规**，计入「必须修复项」。🔴 **禁止把新违规加进 `archunit-store` 基线**让它变绿。另核对 Step4「分层落点」表声明的层级与实际代码是否一致。

**F. Lessons 合规检查 + 零臆测审计**：
- 🔴 **实机验证结论可信度核查（L20）**：若执行过 11.4，逐条核对**否定型 AC（「无权限看不到」「跨客户不可见」）是否用受限普通账号验的** —— 用超管跑出的“通过”是**假绿灯**，一律改判 `NOT_RUN` 并说明缺什么账号；同时确认验证过程无写操作（或写操作有单独授权记录）
- 逐条对照 `lessons-learned.md` 中与本次改动相关的 lesson（如 L2 软删、L7 真源一致性〔枚举存储值 / 单一真源 / XML 表名〕、L14 数据权限、L15 前端复用），确认无违反
- **零臆测审计**：抽查本次实现中的关键事实性判断（枚举存储值、表名/字段名、上游依赖就绪、既有接口行为、复用组件是否真实存在），逐项核对**是否有可复核的取证**（`file:line` 或文档出处）或**曾经用户确认**。凡是靠"应该是/按惯例"推出来的，标 🔴 **Unverified Assumption**，并当场补取证或退回提问 —— 这类问题计入「必须修复项」，不得带入 Step13

**G. 缺陷猎捕（Bug Hunt）** —— 🔴 **本维度与其他维度性质不同，先读清楚再做**

> **角色**：你现在不是来确认这份代码没问题的，你是**被请来找出它的问题的**。
> 交付一份「零发现」的报告，等同于你没做这次审查。
>
> **为什么非要换这个视角**：Spec、设计、代码、单测、Step11.3 自检，**全是同一个 AI 写的**。
> 它们共享同一套误解 —— 需求看错了，测试也会按错的那样写，然后全绿。
> 你是整条流程里**第一个带着「这是错的」的假设来看它**的角色，这个位置没人能替。
>
> 前面 A~F 几个维度问的都是**「代码符不符合文档」**；
> 本维度问的是**「这段代码在什么输入、什么时序、什么数据状态下会错」**——
> 一段代码可以完全符合文档、过全部单测，依然有空指针、并发覆盖写、分页漏数据。

**动作**：按 `references/bug-hunting-checklist.md` 逐域猎捕。要点：

- **逐文件、逐 hunk 读完整上下文**，不能只看新增行；改了方法就把**调用方**也 grep 出来读
- **主动构造会让它出错的输入**：null / 空集合 / 0 / 负数 / 超长 / 重复 / 并发 / 分页边界 / 权限不足 / 上游超时 / 字段缺失
- 与本次改动无关的检查域可跳过，但**报告里要写明跳过了哪些、为什么**

**每条发现必须写全四行，缺一不算发现**：

```
[P1] AssetServiceImpl.java:88  分页漏数据
触发：total=21、pageSize=10 时请求 page=3
实际：返回空列表（offset 算成了 30）
应该：返回第 21 条
```

🔴 **这是过滤器，不是格式要求**：写不出具体触发条件的"问题"，绝大多数是看串了或想当然，
报上去只消耗修复方的时间，还会稀释真问题。**宁可少报，不可虚报。**

**报之前先证伪自己**：对每条候选发现，回头再读一遍相关代码，主动找「它其实没问题」的理由
（上游已经校验过了？这个分支根本走不到？框架已经兜住了？）。推翻不了的才报，并标：

- `CONFIRMED` —— 读过完整上下文，确认会发生
- `PLAUSIBLE` —— 有疑点但没读全（如依赖运行时配置），写明还差什么才能确认

**严重度 P0/P1/P2/P3** 定义见 `bug-hunting-checklist.md`。**P0/P1 计入「必须修复项」**，
P2/P3 列出并由用户决定本期修不修。

**零发现的处理**：确实一个都没找到时，**不许只写「未发现问题」**——
必须列出**你实际过了哪些检查域**、每个域为什么不适用或为什么安全。
一句话的零发现报告，与没做审查无法区分。

**约束**：审查必须逐条/逐端点/逐分支，A 表与 Checklist 的 `AC-NN` 必须一一对应（条数相等），每条发现附带精确文件行号，禁止凭空编造。

## 产出物格式

`Step 12-AI Review报告.md`：

```
审查概要: 总条目X | ✅X ⚠️X ❌X | 🔴契约不一致X | 🔴契约违规X | ❌缺分支X（后端） | ⚠️前端待人工验证X | 🐛质量缺陷X | 评估: PASS/CONDITIONAL PASS/FAIL

A.需求回溯表: [AC-NN, 条目, 归属, 状态, 实现位置, 缺失说明]
A2.AC覆盖率反查: [AC-NN, 缺席位置(测试矩阵/tasks/实现), 处理]
B.前后端契约一致性: [端点, 前端调用, 后端实现, 状态]
C.API契约违规: [端点, 预期(API文档), 实际(代码), 严重程度(Minor/🔴Critical)]
D.测试覆盖审计: [条目, 端侧, 正向, 边界, 异常]
E.代码质量缺陷: [文件, 行号, 端侧, 缺陷类型, 建议]
F.Lessons 合规: [Lesson, 检查结果(✅遵守/❌违反+说明)]
G.审查结论: 评估 + 必须修复项 + 建议修复项 + 审批说明
```

示例（A 需求回溯表）：
```
| AC-07 | SHARE - 分享入口 | 前后端 | ✅ | ShareController.java:25 / ShareDialog.vue:10 | - |
| AC-08 | SHARE - 审核状态 | 后端 | ⚠️ | AssetServiceImpl.java:88 | 仅 Approve/Deny，缺 Processing 轮询 |
| AC-09 | ... | 前端 | ❌ | - | 整个条目未实现 |
```

## 审查终止条件
- **PASS** → 进入 Step13
- **CONDITIONAL PASS** → 修复 Critical/必须修复项后重审
- **FAIL** → 修复全部后重审
- **循环限制**：最多 2 轮，第 2 轮仍 FAIL 则输出完整缺陷清单请求人工介入

## 变更影响重新评估

**触发条件**（任一即触发）：
1. **跨层改动**：改 Controller 签名/DDL 表结构/API 响应字段/Feign 契约/前端公共组件 props
2. **范围扩散**：修复改动文件数 > Step4 清单的 30%，或新增未声明模块改动
3. **非功能回归**：删除了已落点的 @Transactional/缓存 TTL/乐观锁 WHERE/前端性能方案
4. **架构突破**：引入新外部依赖（新 Feign/MQ topic/三方 API/新前端全局依赖）

**执行**：①停止修复 ②生成《变更影响重新评估报告》(触发原因+偏离的原始文档+回退步骤) ③按影响范围回退到 Step4/5/6/7 重审（影响需求理解则回退 Step2/3）④同一问题最多回退 1 次

**不触发回退的修复**：纯方法内部逻辑、补充校验/事务/乐观锁、测试断言修正（属收敛而非扩散）

**禁止 git 提交（强制）**：本步仅审查，所有修复代码只写入工作区，**禁止 `git add/commit`**。提交统一在 Step13 通过+人工审批后进行。

**→门控**：🔴 **阻塞** —— 落盘报告 → 汇报结论（PASS / CONDITIONAL PASS / FAIL）+ 必须修复项 → **暂停等确认** → 进入 Step13

> 🔴 **阻塞门控**：必须**暂停等待用户明确确认**，未获通过禁止进入下一步。
> 之所以阻塞：本步给出 PASS/FAIL **判定**，下一步就是提交；判定错了，缺陷直接进仓。
