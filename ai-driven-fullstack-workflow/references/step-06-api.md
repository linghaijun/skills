# 第六步：API 契约设计（前后端共享）

**输入**：Checklist + DDL + RESTful 规范 + Step4 非功能需求落地映射表

**动作**：设计前后端交互的**唯一契约**，确定每个 HTTP 请求的细节。**此文档是前后端的桥梁，后续前端所有步骤（Step7/8/10/11）必须严格以此为依据。**

**约束**：
- 格式：Markdown 或 Swagger/OpenAPI
- 每个字段标明**类型/是否必填/含义**；定义成功响应 + 业务异常错误码
- **前端友好**：响应结构考虑前端渲染便利性（分页结构、枚举值的字符串/数字约定、时间格式）；`xxxId` 类字段需同步返回展示名 `xxxName`/`xxxDisplay`（见 L3）
- **非功能需求落点（承接 Step4 映射表）**：
  - 限流/熔断：高并发接口标注限流策略
  - 幂等性：POST/PUT 写接口**先 grep 现状**看项目已有什么幂等机制（重试去重键 / 唯一索引 / 状态机 / 上游幂等），**沿用**它；确实没有、又要引入 `Idempotency-Key` 这类新约定时，**必须先问用户**（新增 header 是对调用方的对外约定，且全仓无先例 —— 见 L4「一切随大流」）。禁止只在文档里凭空声明一个没人实现的 header
  - 缓存策略：标注 `Cache-Control` 头及失效策略
  - 分页：继承 `BasePageReq`，声明默认/最大 pageSize
  - 权限：每个端点标注所需角色/权限(`@PreAuthorize`)
- **文案规范**：错误码/提示示例一律英文（见 L13）
- **待确认项**：文档内"待确认项"获得用户决策后必须即时回写文档（见 L8）

## 🔴 既有端点变更（破坏性变更管控，强制）

> 新增端点不会弄坏任何人，**改既有端点才是重灾区**：删字段、改字段名、改类型、改枚举取值、改默认/最大 pageSize、改错误码语义 —— 前端还在用旧的，**编译期无感知，上线才炸**。

改动任何既有端点时必须出下表（本次无既有端点改动则显式写明"无"）：

```
| 端点 | 字段/行为 | 变更前 | 变更后 | 破坏性? | 其他调用方(Grep 求证) | 适配方案 |
|---|---|---|---|---|---|---|
| POST /asset/page | adType | string | string[] | 🔴是 | Ads页:120 / 导出:88 | 同期改，AC-15 |
| POST /asset/page | tagName | - | 新增 | 否 | - | 前端选用 |
```

**判定「破坏性」的标准**（命中任一即 🔴）：删字段、改字段名、改类型、收窄取值范围、必填性变严、枚举删值或改值、分页结构变化、错误码语义变化、默认行为变化。

**硬约束**：

- 「其他调用方」一列**必须 Grep 求证**（前端调用层 + 其他后端服务 + Feign client），与 Step4 影响面清单互为印证；写"无"必须是查过的结论
- 🔴 破坏性变更**必须显式向用户确认**，并给出选项：①同期改所有调用方 ②加新字段保留旧字段（兼容期）③版本化端点。**禁止 AI 自行决定**
- 选定方案后必须补出对应 `AC-NN`（同期改），或在 Spec 记录兼容期与清理时间点
- 兼容期方案必须写明**旧字段何时删、由谁删**，避免留下永久技术债
