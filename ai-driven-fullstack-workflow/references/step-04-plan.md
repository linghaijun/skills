# 第四步：技术方案评估（后端 + 前端）

> ⚡ **子 agent 加速**（先过 `subagent-acceleration.md` §1 三问，判断不了就不派）：技术方案：影响面反查、复用清单搜索可按仓 / 关注点并行派只读子 agent；方案取舍由主 agent 定。

**输入**：Checklist + 后端技术栈（如 Spring Boot + MyBatis）+ 前端技术栈（既有栈，如 Vue 3 + TS）

**动作**：分别评估后端与前端的可行性，梳理实现步骤，**强制识别可复用能力**，**产出两份独立文档**。

## 共同约束（两份文档都必须包含）

- **影响面清单（强制，防漏改）**：不只列"要改哪些"，更要列"**还有哪些是同一件事**"并逐项判定：

```
| # | 同类点(文件:行/端点/组件) | 属于哪类(读取口径/其他入口/其他平台/写入侧/枚举副本/其他调用方) | 判定 | 理由或对应 AC-NN |
|---|---|---|---|---|
| 1 | AssetController#export:88 | 同一数据的其他读取口径 | 需改 | 与 list 共用过滤，AC-12 |
| 2 | WalmartAssetHandler:40 | 其他 productLine | 不需改 | 该平台无此字段（用户已确认） |
```

  - 候选来源：Step1「影响面反查」的清单 + 本步 Grep 复核（六类：读取口径 / 其他入口 / 其他平台 / 读写两侧 / 枚举副本 / 其他调用方）
  - **判定为"需改"的必须有对应 `AC-NN`**，没有就回 Step3 补条目；判定"不需改"必须写理由
  - **存在未判定项 → 本步未完成，禁止进入 Step5**
  - 清单同时是 Step12 维度 A3 / Step13 的漏改反查基准

- **改动落点选择（强制，禁止就地打补丁）**：影响面清单里判定"需改"的点 **≥2 处**时，必须先评估能否在**公共层改一处**解决（后端：公共 Service / 枚举单一真源 / BaseMapper / 拦截器；前端：共享组件 / composable / `@pacvue/utils` / 请求拦截器），再决定落点：

```
| 改动主题 | 同类点数 | 候选落点 | 选定落点 | 为什么是这一层 | 该层其他调用方影响 |
|---|---|---|---|---|---|
| 过滤条件注入权限 | 4 | ①各 Handler 各加一次 ②统一在查询组装处 | 统一组装处 | 4 处口径必须一致(L14)，分散必漂移 | 另有 2 个调用方，已确认同样需要 |
```

  - **≥2 处 → 上提共享层**；**=1 处 → 就地改**，不得为"将来可能复用"提前抽象
  - 🔴 **上提改动 = 影响面重新扫一遍**：改了共享层就等于改了它的**全部**调用方，必须重新 Grep 该层被谁调用，逐个判定是否受影响，结果补回影响面清单
  - 已有枚举/常量/公共方法的，直接改真源，**禁止新增并行副本**（见 L7、L15）

- 🔴 **分层落点（架构边界，机械门禁会验）**：除了"改哪一层共享/就地"，还要声明**落在哪一分层**，并对照项目既有分层写明有无跨层：

```
| 改动主题 | 分层落点 | 是否跨层 | 说明 |
|---|---|---|---|
| 素材列表加筛选 | Controller 收参 → Handler 编排 → Service 查询 → Mapper | 否 | 按既有分层 |
| 导出复用查询 | 复用 AssetQueryService | 否 | 不在 Controller 里拼 SQL |
```

  - 本项目的分层边界由 **ArchUnit 机械门禁**守（`creative-management-api` 的 `ArchitectureTest`，3 条规则全部 `freeze()` 棘轮、基线已提交进仓）：
    - `controllerMustNotDependOnMapper` —— **Controller 不得直连 Mapper**，必须经 Manager/Handler/Service；该规则**存量 0 违规**，新增一处立刻红
    - `noFieldInjection` —— 新类一律**构造器注入**，禁止把 `@Autowired`/`@Resource` 打在字段上
    - `utilsMustNotDependOnSpring` —— `utils` 包保持纯静态工具，不依赖 Spring 容器
  - 🔴 **棘轮的含义：这三条失败 = 你新增了违规**（存量已冻结不会报）。**禁止把新违规写进 freeze 基线**来让它变绿 —— 那是把门禁反向用成了许可证
  - 设计阶段就想清楚落在哪层，比编码后被门禁拦下再返工便宜

- 🔴 **回归风险候选（强制，供 Step8 产出回归清单）**：影响面清单里**判定"不需改"但走同一段共享代码**的点，以及**上提到共享层后被动受影响的其他调用方**，全部列为回归候选 —— **"不需改" ≠ "不会受影响"**：

```
| 受影响的既有功能 | 因为改了什么 | 期望不变的行为 | 回归验证方式 |
|---|---|---|---|
| Walmart 素材列表 | 共用 AssetQueryBuilder 注入了权限 | 返回条数与改动前一致 | 切 Walmart 账号跑列表比对 |
```

  - 本表是 Step8《回归验证清单》的输入，**不得为空**（确实零回归风险时写明"无共享代码改动"并说明依据）
- **技术盲区提示**：识别并发、大数据量、三方 API 超时、大列表性能、跨域、token 传递等风险
- **依赖与复用识别（强制动作）**：写新代码前必须 Search/Grep 现有代码库；"强制"的是**识别动作**和不重复造轮子；复用本身是"优先"——不适配可不复用，但须在复用清单写明理由
- **非功能需求落地映射（强制）**：Step1 收集的非功能需求必须逐条映射到具体技术落点：

```
| 非功能需求 | 落地技术方案 | 落点位置 | 验证方式 |
|---|---|---|---|
| 查询<1s | group_id 联合索引 | ddl.sql | 测试矩阵+11.3自检 |
| 500 QPS | Redis 缓存 5min | XxxServiceImpl | Step12 维度 E 检查 |
| 跨表原子性 | @Transactional | ShareServiceImpl | 11.3+Step12 维度 E |
| 前端大列表不卡 | 虚拟滚动/分页加载 | XxxList 组件 | Step8 前端矩阵+Step12 维度 E |
```

- **未映射的非功能需求 → 未完成本步，禁止进入 Step5**。落点必须可被后续步骤追溯验证

## 后端方案约束

1. **改动点清单**：现有后端模块/公共方法/已有表
2. **复用点清单（强制）**：可复用的 Service/方法（文件位置）、可复用的 DTO/常量/枚举、外部依赖（Feign/MQ/缓存/三方 API）；已判定可复用的直接调既有方法
3. **非功能需求落地映射表**（见上）
4. **核心业务伪代码**
5. **潜在风险提示**

## 前端方案约束

1. **技术栈确认**：明确框架（Vue/React）、状态管理（Pinia/Redux）、UI 库、HTTP 库、路由方案；**若项目已有既定栈，必须沿用**；无法确认时必须询问用户（禁止默认推断）
2. **页面/路由影响**：列出新增或改动的页面、路由路径、路由参数
3. **组件复用清单（强制）**：Grep 现有组件库与同类页面，列出可复用组件/工具（文件位置 + 调用方式）；通用逻辑先查 pacvue-common-utils（详见 L15）
4. **非功能需求落地映射表**：前端相关非功能需求（性能/兼容性/国际化等）逐条映射
5. **前端风险提示**：大列表性能、跨域、鉴权 token 传递、组件耦合等
