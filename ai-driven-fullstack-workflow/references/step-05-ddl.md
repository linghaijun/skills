# 第五步：数据库设计与 DDL

**输入**：Checklist + 实现计划 + 已有相关表结构 + Step4 非功能需求落地映射表

**动作**：设计数据模型，生成建表/改表 SQL。

## 🔴 前置：确认现状（强制，禁止凭记忆写改表语句）

> 改表 SQL 基于臆测的列名/类型是经典翻车（同类见 L7 的 53 处表名错误）。**动笔前先拿到现状。**

1. **涉及既有表时**，先取实际结构：`SHOW CREATE TABLE xxx`，或 Read 既有 DDL 脚本 / Entity 的 `@TableName` + 字段声明 / Mapper XML 的 `resultMap`
2. 现状核对结果写在 Step4 技术方案或门控汇报里（不贴进 SQL 脚本）
3. 取不到现状（无权限 / 表在别的库）→ 按**零臆测**转为提问，**禁止先写着看**
4. 新增列前先确认：**同名列是否已存在**、同类字段在本项目的既有类型约定（如金额用 decimal 还是 bigint 存分）
5. 改既有列（改类型/改长度/加非空/加唯一索引）属**破坏性变更**：必须评估存量数据是否满足新约束，不满足则配套 `data-backfill.sql`，并在文档显式标注风险

**规范**：MySQL 8.0，snake_case。
- 每表必含：`id`(主键)、`create_time`、`update_time`、`is_deleted`(逻辑删除)、`version`(乐观锁)
- 根据 Checklist 查询条件自动建索引
- **非功能需求落点**：映射表中"落点=ddl.sql"的行必须在 DDL 实际落地，SQL 注释标注来源（如`-- 支撑"查询<1s"`）；高并发场景优先覆盖联合索引
- **EXISTS 子查询涉及软删表时，必须加 `AND tx.is_delete = 0`**（见 L2）

**迁移方式（强制）**：手动执行。🔴 **直接给能执行的纯 SQL**（用户偏好）：`ALTER TABLE …` / `CREATE TABLE …` 原样写出，头部一两行注释说明用途与「部署前执行」即可；**不要**用 `SET @x` + `PREPARE` / 存储过程包装幂等，也不要把现状结构大段贴进脚本（现状核对在对话 / 技术方案里说明）。新建表可用 `CREATE TABLE IF NOT EXISTS`。**必须配套 `ddl-rollback.sql`**（每条 DDL 的逆操作）。涉及数据回填另提供 `data-backfill.sql`。

**产出物**：`.../Step 5-ddl.sql` + `Step 5-ddl-rollback.sql` + `Step 5-data-backfill.sql`(如有)

**→门控**：🔴 **阻塞** —— 落盘 → 汇报路径 + 变更摘要（建哪些表/加哪些列/改哪些既有列）→ **暂停等确认** → 进入 Step6。

> 🔴 **阻塞门控**：必须**暂停等待用户明确确认**，未获通过禁止进入下一步。
> 之所以阻塞：DDL 要**人工在库上执行**，执行后不可逆；改既有列还可能撞上存量数据。这道门同时是 Step4 技术方案的兜底——技术方案的问题大多会在 DDL 上显形。

> 数据库操作遵循 `.agents/database.md`（MyBatis 规范、事务管理）。
