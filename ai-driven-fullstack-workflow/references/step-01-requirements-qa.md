# 第一步：需求澄清与问题收集

**输入**：PRD/UI/业务背景

## 0. 变更类型分流（本步第一个动作）

> 13 步对"改 3 行的 bugfix"不成比例 —— 硬套的结果是干脆不走流程，所有规则归零。**先分流，再按路径执行。**

AI 判定类型 → **向用户确认** → 结论写入 Step2 Spec 文首「变更类型」：

| 类型 | 判据 | 执行路径 |
|---|---|---|
| **A. 新功能** | 新增 Capability / 新页面 / 新表 | **全流程 13 步** |
| **B. 增强改造** | 改既有功能，无新表、无新页面 | 跳过 Step5（确无表改动）/ Step7（确无新页面或组件树变化），其余照走 |
| **C. Bugfix / 微调** | 单点缺陷或文案/样式微调，AC ≤ 3 条 | Step1(**含影响面反查**) → 3 → 10 → 11.2/11.3 → 12 → 13；**回归验证清单必做** |

**硬约束**：

- 跳过的步骤必须在 Spec 文首**逐条写明"跳过 X，理由"**，Step13 按**选定路径**核对，不按 13 步硬套
- **分流只能降流程密度，不能降质量门**：零臆测、影响面反查、回归验证、AC 追溯、禁止中途提交，**三条路径一律适用**
- 判不准时按**高一档**走（B 拿不准就按 A）；执行中发现范围超出判定（如 bugfix 牵出表结构变更）→ **立即升档并补做跳过的步骤**
- 复杂 bug 先用 `systematic-debugging` skill 定位根因，再按 C 路径走

**动作**：系统性识别输入中不明确/有歧义/细节缺失之处，整理为结构化问题逐一向用户提问。**不直接进入设计或编码**。

**覆盖维度**：①功能边界(触发条件/前置后置/适用范围) ②异常场景(报错/拒绝/降级及文案) ③数据来源(用户输入/系统计算/三方接口/格式) ④前后端交互(页面跳转/弹窗/加载态/空态/多入口) ⑤权限角色(含前端入口可见性与数据权限) ⑥非功能需求(性能/并发/异步) **⑦影响范围(同类场景是否一并改，见下「影响面反查」)**

**约束**：每轮≤5个问题，可衍生追问直至澄清。

## 🔴 每个问题都带「需要跟产品经理确认」选项

PRD 里的冲突、空白、默认值这类问题，答案本该来自产品，开发能拍板的不多。
不给这个出口，用户只能在推荐项里先挑一个顶着 —— 代答的结论会以「用户已确认」的身份一路流进 Spec，
到 Review 甚至上线才暴露。

- 每个问题（AskUserQuestion 或纯文字提问一律适用）的**最后一个选项**固定为：
  - label：`需要跟产品经理确认`
  - description：`暂不定，记入待 PM 确认清单，产品答复后回写`
- AskUserQuestion 每题最多 4 个选项 → **实质选项最多 3 个**，第 4 个留给它
- 纯工程问题（分支、目录、变更类型分流）也照带，不做豁免 —— 要不要问产品由用户判断
- 用户选了它：该问题状态记 `待PM确认`，**不得**按推荐项代填，后续追问也不得以某个候选项为前提

## 问答记录落盘：`Step 1-需求澄清问答记录.md`

**每轮问答结束就追加写入**（不要等全部问完再补）。**一个问题一节**，按「范围 / 交互 / 数据 / 流程工程」等用 `##` 分组，
解析与写回由 `scripts/qa_record.py` 负责（看板、`validate_step.py` 都用它，别手搓另一套格式）：

```markdown
## 二、Hook / Scene 与 Prompt 联动

### Q6 · Hook 生成后默认选哪一项
- **状态**：待PM确认
- **问题描述**：
  Hook 选项里固定有一个「Custom」（用户自己写 Prompt），其余是 AI 生成的 Hook。两份材料默认值不同：
  - PRD 3.2 字段表：默认「第二项」，即第一个 AI Hook，并自动回填 Prompt
  - 原型：仍停在 Custom，Prompt 留空

  这决定用户第一眼看到的是「AI 已替你选好、Prompt 已填好」还是「一片空白、自己挑」。
- **候选项**：
  - A. 按 PRD：默认第一个 AI Hook 并回填
  - B. 按原型：默认 Custom，不回填
  - C. 需要跟产品经理确认
- **已选**：C
- **当前结论**：
  （待产品答复）
- **来源**：PRD 3.2；原型（冲突）
```

- 编号 `Q1..`（AI 自查补出的问题可用 `N1..`），**编号一经写入不改**；标题行格式固定 `### Q6 · 标题`
- 「状态」只有三个值：`已定` / `待PM确认` / `PM已确认`（产品答复后改，「当前结论」写明产品原话或依据）
- 「已选」写候选项字母，或「自定义」；用户选的是推荐项时「来源」写「用户（推荐暂定）」，复盘时能一眼认出**代答**
- 多行内容缩进两格续写；候选项每项 `  - A. …`，**最后一项固定是「需要跟产品经理确认」**
- AI 自查发现「还没问到、但该问产品」的点，也作为一节写入（状态 `待PM确认`），不要只停在对话里
- 文件末尾 `## 待产品确认清单` 列出 `待PM确认` 的问题；**同时把清单原样贴到对话里**。看板「需求问答」页签可一键复制 / 导出 `.md` / `.csv`（也可 `qa_record.py pm --format csv --out …`）

### 🔴 问题必须写清楚：不看对话也能读懂

清单是要**转给产品**、几天后**自己复盘**的，一句话标题（「Hook 默认值？」）别人看不懂、过几天你也看不懂。
「问题描述」必须讲清四件事：

1. **背景**：这个字段 / 功能是什么，用户在哪看到它
2. **现状与证据**：PRD 怎么写、原型 / 截图怎么画、代码现在怎么做（`证据：file:line`）
3. **冲突或空白**：哪里互相矛盾、哪里没写
4. **为什么必须定**：选不同答案，用户看到的 / 开发要做的有什么不同

候选项也要写**后果**，不只写选项名。`qa_record.py check`（Step1 的 `validate_step.py` 会调用）对缺描述判 FAIL、过短判 WARN。
**向用户提问时（AskUserQuestion 的 question 文本）同样适用**：问题本身要自带背景与冲突点，别让用户回翻对话。

### 看板编辑与改动确认（用户可在看板上改答案）

- Step1 开始后起看板服务，告诉用户地址：`python scripts/verify_dashboard.py --dir <需求目录> --serve`（或 `--all --develop docs/develop --serve`）。
  「需求问答」页签逐题展示问题描述 / 候选项（✓ 标出当前所选）/ 结论 / 来源，**服务模式下可编辑保存**；双击 HTML 打开只读
- 用户在看板保存 → 写回本 md，并在需求目录 `.qa-changes.json` 登记一条「待确认」改动。**看板上只改选项（与状态），不改「当前结论」**；选「自定义」时输入的文字即结论
- **产品确认链接**：「待产品确认」区点「生成产品确认链接」→ 局域网地址（端口 8786，带随机令牌，14 天有效，可作废）。产品打开后只看得到这几道题，选项里的「需要跟产品经理确认」显示为「自定义」+ 输入框；提交即写回为 `PM已确认`，并登记为 `by=pm:<名字>` 的待确认改动。局域网端口只开放产品页，看板 / 编辑 / 归档仍仅本机可用
- 🔴 **AI 每一步开始前跑 `python scripts/qa_record.py changes --dir <需求目录>`**（退出码 3 = 有待确认改动）。有改动时：
  1. 逐条把「改前 / 改后」列给用户，确认这是他要的
  2. 确认后**按新选择重写「当前结论」**（用户只改了选项时，结论还是旧的；改成新选项的完整结论），再**同步下游**：Spec、Checklist、已产出的设计文档里引用该结论的地方一并改（影响面同「变更影响重评估」）
  3. `qa_record.py ack --dir … --id <改动id> --note "已同步 Spec §x / AC-NN"`；用户不认可则 `reject`（md 恢复为改动前）
- `validate_step.py` 任何一步发现「待确认」改动都判 **FAIL** —— 不靠记忆

## 🔴 「没有疑问」不是合格产出

> **本步的产出是问题清单，不是结论。** 一条问题都提不出来，几乎总是意味着
> 你把 PRD 省略掉的部分自己脑补了 —— PRD 是人写给人看的，必然有省略；
> 那些脑补会原样流进 Step2 Spec，一路不被质疑，通常要到 Review 才暴露。

- 🔴 **确实清楚的地方，要说明它为什么清楚**：指到「零臆测原则」的 ①就地取证 / ②文档取证 的**具体出处**，而不是只说"这块没问题"
- 🔴 **提不出问题时，倒过来自查**：上面「覆盖维度」①~⑦ 逐个走一遍 —— 异常场景的文案定了吗？空态/加载态定了吗？多入口都覆盖了吗？权限角色呢？这七类里通常至少有一类 PRD 没写
- 本步与零臆测原则**管的不是同一件事**：零臆测管「每条结论有没有来源」，本条管「你有没有在找该问的东西」——来源齐全但压根没往某个维度想，零臆测查不出来

## 🔴 零臆测原则（CRITICAL，贯穿本步）

> **凡是不确定的，要么在代码/文档里找到证据，要么问用户。禁止凭经验、惯例、命名直觉填空。**

**三选一，没有第四条路**：任何一条进入问答记录、进而流向 Step2 Spec 的事实性判断，必须归入以下之一：

| 处置 | 做法 | 记录方式 |
|---|---|---|
| **① 就地取证** | Glob / Grep / Read 实际代码、DDL、既有接口、配置，拿到**可复核的证据** | 标注 `证据：<file>:<line>`，并附关键代码/字段原文 |
| **② 文档取证** | PRD / Swagger / Confluence / 本地技术文档有明确出处 | 标注 `来源：<文档名> <章节/字段>` |
| **③ 列入提问** | 取不到证据 → **必须**写进本轮问题清单问用户 | 标注 `待用户确认` |

**禁止清单**：

- ❌ 用"通常 / 一般来说 / 应该是 / 按惯例 / 大概率 / 我理解是"等措辞替代取证
- ❌ 从字段名、接口名、枚举名**推断**其语义或存储值（典型翻车：`ad_type` 究竟存 `aiName` 还是 `dbName`，见 L7）
- ❌ 拿**其他平台 / 其他模块**的实现反推本次需求的行为（见项目 CLAUDE.md「严格文档驱动」）
- ❌ 假设上游依赖已完成（必须 Glob/Grep 实际文件确认，见 L6）
- ❌ 把"代码现状"直接当成"需求"（代码现状只排第 5 优先级，见下节）

**自检**：本步收尾前逐条扫问答记录，**每条事实性结论都要能指到 ①/②/③ 之一**；指不到的退回列入提问，**不得带着未标注来源的结论进入 Step2**。

**取证成本过高时**：明确告知用户"该项需要 X 才能确认（如需跑起服务 / 需要 DB 数据 / 需要 Swagger 权限）"，转为提问，**不要用猜测兜底**。

## 🔴 影响面反查（CRITICAL，防漏改）

> **需求描述的往往只是"被发现的那一处"。** PRD 通常来自某个具体场景的反馈，同类场景大概率没被写进去 —— 不主动反查就会漏改，上线后变成"同一个 bug 修三次"。

**动作**：对需求中的每个改动点，反问「**还有哪些地方是同一件事？**」，用 Grep 求证后列入问答记录，并在 Step4 固化为影响面清单。

**按这六类逐个扫（高频漏点）**：

| # | 同类场景 | 怎么查 | 典型翻车 |
|---|---|---|---|
| 1 | **同一数据的其他读取口径** | grep 同一张表/同一 Service 的其他查询方法 | list 改了，detail / export / filter-options / 下拉搜索没改（L14 要求四处口径一致） |
| 2 | **同一功能的其他入口** | grep 同名组件/路由/按钮文案 | 列表页改了，详情页/弹窗/右键菜单没改（Checklist 的 `COMMON` 前缀正为此设计） |
| 3 | **其他 productLine / 平台** | grep `ProductLines` 枚举、`@Platform` 实现类 | Amazon 改了，Walmart / ADSP 没改 |
| 4 | **读写两侧** | grep `set<Field>(` 找全部写入点 | 读取侧按新约定解析，写入侧还在写旧值（L7 全链路返工） |
| 5 | **同一枚举/映射的多份副本** | grep 枚举值字符串字面量 | Service 私有矩阵与枚举漂移（L7） |
| 6 | **被改组件/方法的其他调用方** | grep 组件名 / 方法名的全部引用 | 改了公共组件入参，其他页面静默出错 |

**产出**：问答记录中给出「影响面候选清单」，每项标注 `需改 / 不需改（理由）/ 待用户确认`。

- **不确定该不该一起改的，必须问用户**（本期做 or 另开需求），禁止 AI 自行决定扩大或缩小范围
- 用户确认"本期不做"的，标 `[blocked]` 并在 Step2 Spec 写明，避免后续审查误判漏实现
- 范围一旦确认扩大，Checklist 必须补出对应 `AC-NN`，否则后续步骤追溯不到

**产出物**：`Step 1-需求澄清问答记录.md`（含待 PM 确认清单）

**→进入 Step2**：所有问题获回答，AI 用 1~2 句总结确认，用户明确确认；且零臆测自检通过（无未标注来源的事实结论）。

存在 `待PM确认` 时：贴出清单后**暂停**。用户可以 ①带回产品答复 → 回写为 `PM已确认` 再继续；②明确说「先按暂定继续」→ 进入 Step2，Spec 里对应结论标 `[待PM确认]`。无论哪种，**Step3 🔴 门控前必须清零**（`validate_step.py --step 3` 对残留的 `待PM确认` 判 FAIL）—— Checklist 的 AC 要进 Jira，不能建立在没确认的前提上。


## 信息来源优先级（冲突裁决）

多来源信息冲突时按以下优先级取值，并把冲突点**显式记入问答记录**：

1. 用户最新明确指令
2. UI 截图 / 设计稿（视觉与交互事实）。给的是 Figma 链接时，先按 `figma-ui-cache.md` 缓存到需求目录 `figma/` 再读，不凭截图目测
3. PRD / Confluence（业务范围事实）
4. 本地技术文档（既有设计约束）
5. 当前代码现状（仅作参考，**不自动等于需求**）

被低优先级来源覆盖掉的内容必须向用户复述确认，禁止静默取舍。

> **OpenSpec 对应**：≈ `/opsx:explore`（先探索、不定结构的理念）。详见 openspec-integration.md。
