# 缺陷猎捕清单（Step12 维度 G 专用）

> 这份清单回答的问题**不是**「代码符不符合文档」——那是维度 A~F 的事。
> 这份问的是：**这段代码在什么输入、什么时序、什么数据状态下会错？**
>
> 一段代码可以 100% 符合 Checklist、通过全部单测、过完所有合规检查，
> 依然有空指针、并发覆盖写、分页漏数据。合规审查抓不到这些，只有按机制猎捕才行。

## 怎么用

1. **逐文件、逐 hunk 读完整上下文**，不能只看新增行。改了一个方法，就把该方法与它的**调用方**都读一遍（`grep` 调用点）。
2. **对每个变更点，主动构造至少一组会让它出错的输入**：null、空集合、0、负数、超长、重复、并发、分页边界、权限不足、上游超时、字段缺失。
3. 按下面的检查域逐条过。**与本次改动无关的域跳过，但要在报告里写明跳过了哪些、为什么**。
4. 每条发现必须能写出**复现场景**（见下）；写不出来的删掉，不要留着凑数。

## 每条发现的必填格式

```
[P1] AssetServiceImpl.java:88  分页漏数据
触发：total=21、pageSize=10 时请求 page=3
实际：返回空列表（offset 算成了 30）
应该：返回第 21 条
证据：offset = (page) * size，未减 1
```

🔴 **没有「触发 + 实际 + 应该」三行的，不算发现。** 这三行是过滤器：
写不出具体触发条件的"问题"，绝大多数是看串了或想当然，报上去只会消耗修复方的时间。

## 严重度

| 级别 | 含义 | 例子 |
|---|---|---|
| **P0** | 数据错误/丢失、越权、线上崩溃、不可逆 | 删改 SQL 缺 `WHERE`、权限判断可绕过、事务未回滚、软删数据被物理删 |
| **P1** | 主流程功能不正确 | 边界算错、空指针、分页漏数据、并发覆盖写、金额精度丢失 |
| **P2** | 次要功能/异常分支问题、明显性能隐患 | 循环内查库、错误文案错、日志吞异常、N+1 查询 |
| **P3** | 可维护性 | 魔法值、复制粘贴逻辑、死代码、缺关键日志 |

## A. 输入与边界

- 入参为 `null` / 空字符串 / 空集合 / `0` / 负数 / 超长时，各走哪条分支？有没有分支是"没想到"的？
- 数字：会不会溢出（`int` 装了计数）？除数可能为 0？浮点直接比较相等？**金额用了 double**？
- 字符串：`substring` / `charAt` 的下标有没有越界可能？`split` 后数组长度假设成固定值？
- 分页：`pageSize=0`、`pageIndex=0` 或负数、`offset` 算错（差 1）、`total` 与实际条数不一致
- 时间：时区（本项目多处 PST）、区间是开还是闭、跨天/跨月/跨年、夏令时
- 枚举：收到**不认识的值**时怎么办（抛异常 / 走 default / 静默忽略）？哪种是对的？

## B. 空值与解引用

- 方法返回 `null` 的可能路径，调用方有没有判？`Optional` 有没有被 `.get()` 直接拆开？
- Map 的 `get` 结果直接用？`getOrDefault` 的默认值是不是也有意义上的歧义？
- 链式调用 `a.getB().getC()` 中间节点可能为 null？
- 自动拆箱：`Integer` 参与算术或 `==` 比较时可能 NPE / 比较的是引用

## C. 分支与逻辑

- `if/else` 是否覆盖全部取值？有没有"两个条件都不满足"的漏网状态？
- 条件顺序：短路求值是否依赖了前一个条件的副作用？调换顺序会不会 NPE？
- 取反写错（`!a && !b` vs `!(a && b)`）、`>` 写成 `>=`
- 早返回 / `continue` / `break` 后，后面本该执行的清理或计数是否被跳过？
- 状态机：非法流转拦住了吗（已审核的还能再提交？已删除的还能被引用？）

## D. 集合与循环

- 遍历中修改集合（`ConcurrentModificationException`）
- 循环内查库 / 调接口（**N+1**）；批量接口被逐条调用
- `subList` / `toList` 后仍引用原集合
- 去重用了 `equals` 但没重写 `hashCode`；用对象做 Map key 但它可变
- 大集合一次性加载进内存（无分页、无流式）

## E. 错误处理

- `catch` 了但什么都不做（吞异常），或只 `log` 不向上传递，导致**失败被当成成功**
- `catch (Exception)` 范围过宽，把本该抛出的业务异常也吃掉
- 降级分支把**不同根因塌缩成同一句固定文案** → 故障时分不清"永久失败需人工"与"瞬时抖动会自愈"（见 L19）
- 异常信息里带了敏感数据 / 原始堆栈直接返回给前端（见 L16）
- `finally` 里再抛异常，覆盖掉原始异常

## F. 并发与时序

- 两个请求同时改同一条记录：后写的覆盖先写的（**丢更新**）？有没有乐观锁 `version`？
- 先查后写（check-then-act）之间有没有竞态窗口？
- 共享可变状态：成员变量装请求级数据、`static` 集合被多线程写、`SimpleDateFormat` 复用
- 异步任务：主线程已返回但事务尚未提交，异步里查不到刚写的数据
- 重复提交 / 重复消费：接口幂等吗？MQ 消息重投会不会产生两条
- 🔴 **测试代码改静态 / 全局状态**（static mock 开关、单例缓存、系统属性）：JUnit 类级并发时别的测试类同时在跑，互改开关 → 随机红 / 随机绿。相关测试类加 `@ResourceLock("<资源名>")`，或改成实例注入；别靠串行运气（CP-58118 首次跑单测因两个测试类互改静态 mock 开关而红。测试代码的问题按下文「不算发现」与业务缺陷分开记，但要修）

## G. 事务与数据一致性（后端）

- 跨表写有没有 `@Transactional`？范围是不是太大（把远程调用包进事务）？
- `@Transactional` 加在 **private / 同类内部调用** 的方法上 → **不生效**
- 事务里调外部接口：接口超时会把事务一起拖长、锁持有过久
- 异常类型：默认只对 `RuntimeException` 回滚，受检异常不回滚
- 先提交事务再发消息 vs 先发消息再提交 —— 哪一侧失败会导致数据与消息不一致？

## H. SQL 与 ORM（后端）

- 🔴 **软删条件**：`WHERE` / `JOIN` / `EXISTS` 子查询里**每个**带 `is_delete` 的表都加了条件吗（见 L2）
- 🔴 **数据权限**：列表/详情/导出/筛选项**四处口径一致**吗？`visibleUserIds` 与授权 `profileIds` 都注入了吗（见 L14）
- 更新/删除语句**缺 `WHERE`** 或 `WHERE` 条件可能为空 → 全表操作
- 字符串拼接 SQL（注入风险）；`${}` 与 `#{}` 用反
- 动态 SQL 的 `<if>` 分支：某个条件都不满足时，`WHERE` 会不会变成 `WHERE AND`、或条件全丢
- 枚举→DB 存储值：写入侧和读取侧用的是同一个属性吗（见 L7）
- 表名/字段名与实际 DDL 一致吗（见 L7）
- 索引：新加的查询条件命中索引吗？大表全扫？

## I. API 契约与序列化（后端）

- 响应字段名/类型与 Step6 契约一致？枚举取值范围一致？
- `Long` 传给前端是否精度丢失（JS 安全整数上限）
- 时间字段格式与时区约定
- 入参校验：枚举白名单、互斥必填（见 L11）；非法值返回的是 `fail` 而不是 500
- 返回给前端的文案是英文吗（见 L13）

## J. 前端响应式与生命周期

- `ref` / `reactive` 用错：对象整体替换导致失去响应性；解构 `reactive` 丢响应性
- `computed` 里有副作用；`watch` 没设 `immediate` 导致首次不执行
- 组件卸载后：定时器 / 事件监听 / `AbortController` 有没有清理（内存泄漏）
- 请求竞态：快速切换筛选条件，**先发的后回**覆盖了后发的结果
- `props` 被子组件直接修改

## K. 前端渲染与交互

- 列表渲染 `key` 用了 index → 增删后状态错位
- 空数据 / loading / 错误 / 权限不足四态是否都有（见 Step8 前端矩阵）
- 慢接口：loading 撑不住高度导致页面跳动；用户能在加载中重复点击
- 表单：未提交草稿丢失、校验绕过（只有前端校验没有后端校验）
- Promise reject 未处理；错误文案暴露原始 code / 堆栈（见 L16）
- 🔴 **默认选中 / 预选依赖异步数据**（打开抽屉 / 弹窗时按接口结果预选筛选项、默认值）：① 打开第一帧有没有值 —— 没有就是「先未选中、过一会儿才选中」的中间态，用户会看见（缓存 + 提前预取，打开时同步写入）；② 首次请求是否只等它需要的那份数据（别把无关的慢接口一起 `Promise.all`，实测被拖 6 秒）；③ 新数据回来后会不会覆盖用户刚做的修改；④ 缓存过期（同会话切 client、标签删了重建）会不会按旧 ID 选错 —— 只在用户没动过时以新数据纠正（CP-58118 Q100，QA P2 + 用户反馈「打开后没选中」）
- 多标签页 / 切换账号后，缓存的筛选条件或 localStorage 串数据（存储 key 带 `userid_` 前缀了吗）
- 🔴 **CSS 过渡与计时器配合**（进度条「停在 100% 再换图」、动画结束再隐藏 / 卸载）：停留 / 延迟计时要**包含过渡时长**，且过渡时长与计时常量**同源**（同一个常量，或从样式读），否则条还没画满就被换掉（CP-58118 Q89：只停 0.5s 时条只画到 96% 就换图，返工 + 全部 100% 证据重拍）

## L. 安全与权限

- 权限判断可否绕过（只在前端隐藏入口，后端不校验）
- 越权：改一个 id 就能访问别人的数据（水平越权）
- 日志/响应里打印了凭据、token、密码
- 文件上传：类型与大小校验、路径穿越

## M. 回归面（最容易被跳过，也最容易出事）

- 这次改动影响了哪些**没被改的调用方**？（`grep` 方法名/端点/组件名）
- **老数据**还能跑吗？（新增非空字段、改了枚举含义、改了默认值）
- 老配置 / 老缓存 / 老消息格式还兼容吗？
- 共享层改动：`≥2` 处调用的公共方法被改了，其余调用方的行为变了吗？

## 不算发现的（避免凑数）

- ❌ 写不出「触发 + 实际 + 应该」三行的猜测
- ❌ "建议加个注释""可以考虑重构"这类无缺陷的风格意见（除非命中 P3 的具体项）
- ❌ 与本次改动无关的历史代码问题 —— 记进「遗留观察」，不进必须修复项
- ❌ 已被冻结基线接受的架构存量违规（见维度 E2）
- ❌ 单测里的问题当成业务代码缺陷（分开记）
