# 第三步：需求对齐与结构化 Checklist（前后端共享）

**输入**：Step 2-Spec.md

**动作**：将 Spec 功能描述翻译为高严谨性 BDD 测试用例（用户操作流程，前后端共享同一份）。

## 核心约束（CRITICAL）

> 本节即 L1 的落地；Step12 需求回溯会抽查是否混入技术细节或乱序。

1. **只写前端用户操作流程**：Checklist 描述用户在页面上「看到什么 / 点什么 / 得到什么」。
   - ✅ 允许：点击按钮、选择商品、粘贴 URL、勾选结果、Save to Library、提示文案、按钮置灰等
   - ❌ 禁止：接口路径、请求/响应字段、错误码、表名、DDL、配额扣减实现、异步任务、缓存、权限注解等技术细节
   - 后端数据/逻辑场景**不在 Checklist 展开**，由 Step8《后端单元测试验证指标矩阵》承接（每条 Checklist 拆后端分支）
2. **按测试执行顺序编排**：条目顺序 = 测试同学实际执行顺序 = 用户真实操作路径。  
   推荐大顺序：  
   `进页/切入口 → 准备来源 → 配置 Setting → 触发生成/提交 → 查看与处理结果`  
   同一步内：**先主路径（happy path），后异常/边界**。
3. **多入口功能用前缀区分**：
   - 共用流程前缀固定写 `COMMON`
   - 各入口/模式用独立前缀（如 `PRODUCT_TO_IMAGE` / `IMAGE_TO_IMAGE` / `URL_TO_IMAGE`）
   - 格式：`* [open] AC-NN {PREFIX} - 场景描述`
4. **条目顺序编号（CRITICAL）**：每条 Checklist 必须带全局连续的 `AC-NN` 编号。
   - 格式：`* [open] AC-01 {PREFIX} - 场景描述`
   - 🔴 **零填充两位，宽度全局统一**：`AC-01` `AC-02` … `AC-99`；**超过 99 条时整份改为三位**（`AC-001`…），不得一份文档里 `AC-9` 与 `AC-10` 混用。**禁止写 `AC-1`/`AC-001`（当条数 ≤99 时）**——混用会导致 `tests/AC-NN/` 目录名对不上、字符串排序错乱（`AC-10` 排在 `AC-2` 前面），且下游按编号反查时静默失配
   - 本规范由 `scripts/validate_step.py` 强制校验（「AC 编号宽度统一」「tests 目录名与 AC 编号一致」两项）
   - **全局连续**：编号跨模块/前缀/章节统一递增，不按前缀各自从 01 重来
   - **按最终排序编号**：先按约束 2 排好测试执行顺序，再从上到下顺序编号
   - **编号即追溯锚点**：Step8 测试矩阵、Step9 tasks.md、Step11.3 业务逻辑自检、Step12 AI Review 引用 Checklist 时一律写 `AC-NN`，禁止只写场景描述
   - **中途插条目**：优先追加到所属阶段末尾并接续最大编号；若必须重排导致大面积改号，则整份重编号并在文首注明「本次已重编号」，同时同步更新下游文档中的引用
   - 已写入 Jira 的条目编号视为对外契约，除非同步更新 Jira，否则不得改号（Jira 同步见 `prd-to-jira-ac` skill）
5. **归属标签（可选）**：可用 `[前端]` / `[后端]` / `[前后端]` 标注实现/验证归属，便于 Step9 拆任务与 Step10 编码分配；标签**不代表**可以写技术细节。
6. **Spec 回写（CRITICAL）**：若新增/修改/删除了 Spec 未覆盖的需求点，必须同步回写 Step 2-Spec.md，确保 Spec 始终是唯一需求真理来源。

## 格式

`* [open] AC-NN {模块或前缀} - 场景描述` + 严格 **Given-When-Then**（支持多 Given 前置）。

- 每条必须带 `AC-NN` 全局连续编号（见核心约束 4）
- 模块名/前缀对应 Spec Capability；多入口场景必须带前缀
- **从用户交互视角**描述（禁「请求列表 / BasePageReq / is_deleted / 同一列表 API」等后端术语）
- 粒度须为可独立交付/测试的最小业务单元
- 章节可用 `## 1. … ## 2. …` 标出测试阶段，便于按序执行

**示例（共用）**：
```
* [open] AC-01 COMMON - 进入页面并查看剩余额度
>> Given: 用户有权限进入 Image Generation
>> When: 用户打开页面并查看 Setting 右侧 Quota
>> Then: Setting 区右上角显示「Remaining Quota: 数字」；悬停在旁边的 ⓘ 图标上显示额度说明
>> 图示: 图 1 ②（UI/图1-设置区全貌.png）
```

**示例（前后端联动，只描述用户可见结果）**：
```
* [open] AC-07 SHARE - 资产详情页分享入口
>> Given: 用户位于 Creative Hub -> Asset 页面，查看单个素材详情
>> When: 用户点击素材旁边的 "Share Asset" 按钮
>> Then: [前后端] 页面跳转至 Share 页面并自动弹出分享创建弹窗，且该素材已被预选；弹窗内可见该素材最近一次审核状态（Approved/Denied/Processing）
```

## 🔴 写给人看：不回翻、不猜位置、有图对照

Checklist 是给测试、产品、几天后的自己看的。读者**不会**记得上下文，也不会去翻别的条目。

**写法硬规则**（`validate_step.py --step 3` 自动检查）：

| 规则 | 反例 | 正例 | 检查 |
|---|---|---|---|
| 不用简写，第一次出现就写全称 | 「PD 为空」 | 「Product Description 为空」 | 人工 |
| 不引用别的条目 | 「其余字段同 AC-56」「同上」 | 把字段逐个写出来 | FAIL |
| 不用指代 | 「三者均不可操作」「以上操作」 | 「Prompt 编辑器不能输入；AI Optimize Prompt 按钮点击无反应；Generate 按钮点击无反应」 | WARN |
| 写清页面位置和元素名 | 「显示按钮」 | 「Prompt 编辑器右上角显示『AI Optimize Prompt』按钮」 | 人工 |
| Then 写具体可见结果（文案原文、数值、状态） | 「提示错误」 | 「提示『Optimize failed. Please try again.』，Prompt 保持原文」 | Then < 20 字 WARN |

**图示行**：每条在 Then 之后加一行
`>> 图示: 图 5 ①②（UI/图5-Hook与Scene回填Prompt.png）`
没有合适的图写 `>> 图示: 无（页面位置：…）`。图片路径必须存在（否则 FAIL）；有 `UI/` 图而条目缺图示行会 WARN。
「图示」行只在主文档里，`checklist_jira.py` 生成 Jira 纯净版时自动去掉。

### 文首「一页读懂」（必含，缺失 WARN）

放在编号约定之后、场景完备性自检之前，三样东西：

1. **联动总览图**（`UI/图0-联动总览.png`）：主流程从左到右（谁触发谁），加「会触发 / 不会触发 / 内容变化规则 / 锁定规则 / 失败兜底 / 多入口」几块，**每块写「对应 AC」**
2. **页面全貌标注图**（`UI/图1-…全貌.png`）：页面每个功能区一个红框编号，说明写「新增 / 改动 / 属于哪张票 / 见图 N」
3. **字段速查表**：字段 | 位置（图 1 编号）| 默认值 | 什么时候变 | 失败或为空时

另外每个章节标题下嵌入本章用到的图（Markdown 图片），读者顺着往下看就能看到图。

### 标注截图怎么做（有原型 / 测试环境页面时必做）

- **分区截**：按功能区出 6 ~ 10 张（来源区、分析中、选项区、回填结果、优化中、结果区……），**不要**每条 AC 一张图
- **每个编号说明下写「对应 AC：AC-xx、AC-yy」**：先写完 Checklist 的图示行，再按「图 N 的编号 → AC」统计出对照表，传给标注脚本自动加上。图上不写 AC 的标注，读者对不上，等于没标
- **工具**：`scripts/annotate.js`（注入页面后调用 `window.__ann(items, {labelX, labelW, title, note, acs})`：红框 + 圆圈编号 + 右侧说明框 + 虚线连线，返回裁剪范围），用 Playwright 驱动原型到对应状态后 `fullPage` 截图并按返回的 `top/bottom` 裁剪，存到需求目录 `UI/`
- **原型做不出的状态**（如原生 title 提示、四行回填的最终文字）可以在页面上画示意，但标注里必须写「示意」，文字以 Checklist 为准
- 看板「用例明细」顶部会显示 `UI/` 下全部图片；展开某条 AC 会显示它图示行引用的图

## 🔴 场景完备性自检（落盘前强制，防漏需求）

> **Checklist 漏掉的场景，Step8 矩阵永远补不出来** —— 矩阵是按已有 `AC-NN` 拆分支的。这里是漏需求的**单点故障**，必须在本步堵住。

落盘前逐类回答 **有 / 无需（附理由）/ 待用户确认**，把"有"的补成 AC，把"待确认"的问用户：

| # | 易漏场景类型 | 自问 |
|---|---|---|
| 1 | **重复提交与并发** | 连点两次会怎样？两个人同时改同一条记录？ |
| 2 | **权限边界** | 只读角色看到什么？无权限用户直接访问 URL？数据权限外的记录？ |
| 3 | **空与首次** | 一条数据都没有时页面长什么样？首次进入无历史配置？ |
| 4 | **状态机非法流转** | 已审核的还能再提交吗？已删除的还能被引用吗？ |
| 5 | **超长与特殊字符** | 超长文本、emoji、HTML 标签、前后空格 |
| 6 | **分页与排序边界** | 最后一页删光了？排序字段为 null？总数为 0？ |
| 7 | **取消与中断** | 中途关闭弹窗？请求进行中切页？刷新后状态还在吗？ |
| 8 | **多入口 / 多标签页 / 多账号** | 另一个入口进来行为一致吗？两个标签页同时操作？切换账号后缓存？ |

- 补出的条目按核心约束 4 接续编号，并按约束 2 插入正确的测试顺序位置
- 用户确认"本期不做"的标 `[blocked]` + 原因，并回写 Spec（避免 Step12/13 误判漏实现）
- 自检结论写进 Checklist 文首「场景完备性自检」小节，**列出 8 类的逐条结论**，不得只写"已自检"

## 代码 Gap-Check（可选，首次进项目须先征得同意）

Checklist 初稿完成后，**首次在该项目/模块使用本流程时**必须先问用户：

> 我可以读取相关代码与本地技术文档，检查 Spec/PRD 是否遗漏了已有行为、模块边界、联动逻辑或边界条件吗？

- **用户同意**：读相关代码 + 本地技术文档，重点排查——已有校验/告警流程、依赖模块与联动设置、隐藏前置条件、边界与降级行为、feature flag / 权限 / 状态分支。
- **用户拒绝**：仅基于 Spec + PRD 产出，在文首「假设与未知」小节显式标注假设项与未知实现细节。

**硬约束（CRITICAL）**：
- gap-check 结果只能以「建议新增 AC」「Spec/PRD 补充建议」「待确认问题」三种形式提出，**禁止静默扩大范围**
- **代码现状 ≠ 产品真理**：既有实现的怪异行为不得直接转成需求；须经用户确认后才追加 AC 并回写 Spec
- 采纳的补充项按核心约束 4 接续编号，条目后标注 `(来源: 代码 gap-check)`

## 条目状态生命周期

Checklist 是可验收的**活文档**，条目状态随流程推进回写：

| 状态 | 含义 | 由哪一步置位 |
|------|------|--------------|
| `[open]` | 已澄清，待实现/待验证 | Step3 落盘时默认 |
| `[done]` | 实现完成且业务逻辑自检通过 | Step11.3 业务逻辑自检 该条 ✅ 后回写 |
| `[blocked]` | 被阻塞 / 本期不做 | 任意步骤，**必须附一行原因**并同步回写 Spec |
| `[waived]` | 证据验收未通过、**用户明确放行**（不是「已验证」） | 交付前（证据验收之后）；证据验收报告必须有点名该 AC 的「风险接受记录」（放行范围 + 用户原话 + 风险），否则 `validate_step.py` 交付门禁 FAIL；交接文档「已知限制」要列出放行项请测试关注 |

- 自检未通过、仅部分实现的条目**保持 `[open]`**，禁止提前置 `[done]`
- Step13 交付门禁：存在非 `[done]` 条目时，必须在审查报告中逐条列出 `AC-NN` + 原因 + 用户是否同意放行

`.../Step 3-Checklist.md`

## 产出物 2：Jira 可拷贝纯净版（强制同时产出）

`.../Step 3-Checklist-Jira.txt` —— **整份文件全选复制即可直接粘进 Jira checklist 字段**。

**只允许出现条目本体**，每条 4 行，条目之间空一行：

```
* [open] AC-01 COMMON - 进入页面并查看剩余额度
>> Given: 用户有权限进入 Image Generation
>> When: 用户打开页面并查看 Setting 右侧 Quota
>> Then: 展示剩余额度；悬停可见额度说明

* [open] AC-02 COMMON - 额度不足时触发生成
>> Given: 用户剩余额度为 0
>> When: 用户点击 Generate
>> Then: 按钮置灰；悬停提示额度不足并给出获取额度入口
```

**严禁出现（CRITICAL）**：
- 任何标题（`#` / `##`）、章节名、分隔线
- 前缀约定 / 排序原则 / 假设与未知 / `AC-NN ↔ Jira` 映射表等说明性内容
- Markdown 代码围栏（``` ）、表格、引用块、脚注
- 条目编号以外的任何注释（含 `(来源: 代码 gap-check)` 这类标注——它只留在主文档）
- 文件头尾的空行以外的任何多余字符

**生成规则**：用 `python scripts/checklist_jira.py --dir <需求目录>` 生成（自动去掉「图示」行与「(来源: …)」括注；条目带 `[Story号]` 时按 Story 拆分），不要手工复制。
- 内容从 `Step 3-Checklist.md` 机械抽取，**顺序、编号、前缀、状态标记（`[open]`/`[done]`/`[blocked]`/`[waived]`）与主文档逐字一致**，不得改写措辞
- 主文档任何条目变更（新增/改号/改描述/状态回写）后，**必须重新生成本文件**，两者不允许漂移
- 需要按 Jira issue 分开粘贴时，每个 issue 单独出一个文件：`Step 3-Checklist-Jira-{ISSUE-KEY}.txt`，内部仍只含条目本体
- 扩展名用 `.txt` 而非 `.md`，避免编辑器/预览器插入额外渲染字符

## Review 门控

**两份产出物**落盘（完整版 + Jira 可拷贝纯净版）→ 汇报两个路径与条目数（含编号区间 `AC-01 ~ AC-NN`，可按前缀统计）→ **暂停** → 用户确认 → 进入 Step4

## 🔴 门控：Spec + Checklist 合并确认（阻塞）

**→门控**：两份产出物落盘（完整版 + Jira 纯净版）→ 汇报路径、条目数与编号区间 `AC-01 ~ AC-NN`、场景完备性自检八类结论 → **暂停等用户明确确认** → 进入 Step4。

> 🔴 **这是编码前第一道、也是最重要的一道阻塞门控**，它同时确认 Step2 的 Spec：
> Checklist 是 Spec 的逐条翻译，**两者一起看才判断得出「范围对不对」**，分两次看各只能看到一半。
> 之所以阻塞：①范围错了**后面全白做**，是全流程返工代价最高的一处；②`AC-NN` 一经写入 Jira 即为**对外契约**，改号要同步 Jira。
> 确认时重点看三件事：**有没有多做**（Spec 没有的需求混进来了）、**有没有漏做**（八类易漏场景的结论）、**AC 粒度能不能直接当测试用例**。

## Jira 同步（可选）

Review 门控通过后，可将 Checklist 同步进 Jira 的**真实 checklist 字段**，交由 `prd-to-jira-ac` skill 执行（它负责字段探测、格式镜像、写入后回读校验）。

- 同步前在 `Step 3-Checklist.md` 文首维护映射表：`| AC-NN | Jira Issue Key | 同步时间 |`
- `AC-NN` 一经写入 Jira 即为**对外契约**，改号必须同步更新 Jira（见核心约束 4）
- 人工粘贴走 `Step 3-Checklist-Jira.txt`（全选复制即可）；自动写入走 `prd-to-jira-ac`
- **禁止**把 AC 直接写进 Jira description

> **OpenSpec 对应**：GWT ≈ OpenSpec spec.md 的 Scenario WHEN/THEN。本工作流用 Given-When-Then（多 Given 前置）。详见 openspec-integration.md。
