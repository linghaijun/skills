# 浏览器实机验证 Playbook（Step 11.4）

> 与具体项目无关的操作经验。项目侧的机器/路径细节写在各项目自己的浏览器文档里。
> 来源：CP-57337 实机验证（2026-09-28）一轮踩坑的提炼。

---

## 0. 红线：默认只读

允许：浏览、筛选、翻页、切账号、截图、抓包。
**禁止：删除、修改、上传、分发、改名、提交任何表单**，以及一切会写数据的点击。
唯一例外是用户对**该具体动作**单独授权，且授权**不跨条目、不跨会话继承**。
拿不准某个按钮会不会写数据时：**先问，别点**。

🔴 **「账号可用」不等于「写操作被授权」—— 每一次写/删都必须单独问。**

用户给了一个能登的测试账号，只代表**这个账号可以用来测**，**不代表**可以拿它去
删除、修改、上传、分发、提交。常见的错误推理，全部不成立：

| 错误推理 | 为什么不成立 |
|---|---|
| 「用户给了账号，就是让我去测」 | 给账号解决的是**能不能登进去**，不是**能不能写** |
| 「这是测试账号 / 测试环境，写坏了无所谓」 | 测试库里常有真实客户数据；写操作还会污染**其他人正在用的**验证基线 |
| 「这条 AC 本来就要写操作才能验」 | 那更要问 —— AC 需要写，不等于此刻可以写 |
| 「上一条写操作用户同意了」 | 授权**不跨条目**。上一条同意的是上一条 |
| 「用户说『帮我验证』就是默认授权了」 | 「验证」是目标，不是对具体写动作的授权 |

**正确做法**：读操作先做完（定位入口、确认数据现状、想清楚会写什么），
然后**带着具体信息问**，让用户一眼能判断风险：

> 要验 AC-NN 需要执行写操作：
> **动作**：点「X」按钮 ｜ **账号**：`<登录名>` ｜ **对象**：`<具体哪条数据>`
> **会产生什么**：`<新增/修改哪张表的什么记录>`
> **可逆吗**：`<能否撤销、怎么撤销>` ｜ **影响面**：`<是否影响其他人的数据或基线>`
> 确认执行吗？

用户明确说「可以」才动手。**只要对方没有明确说可以，就当作没授权。**
拿不准算不算写操作时，按写操作处理。

凭据永远由用户输入，AI 不代输、不读取凭据存储。

## 1. Step 0：两件事不做，后面所有证据作废

### (0) 🔴 动手前必读：脚本分层 + 坑清单 + 页面笔记（别现写、别重摸）

页面整体很少大变，**大多数操作路径可复用**。变了就更新资产，不要每次从零写探针。
开浏览器前按下面顺序读完再动手（跳过 = 白跑一轮的高发原因）：

| 顺序 | 读什么 | 放哪 | 解决什么 |
|---|---|---|---|
| **①** | **`cdp-drive-real-chrome` → `references/SCRIPTS.md`** | skill（跨项目） | 全局层脚本目录 + 选型决策树 + **坑清单**；**禁止先现写** |
| **②** | 同 skill → `projects/<项目>/README.md` + **`PAGE-NOTES.md`** | skill 内按项目分目录（不进项目 git） | 页面层脚本（如 Ads 布景）+ 该项目页面的事实 / 口径 / 坑；页面改版只改这里 |
| **③** | 新项目还没有 PAGE-NOTES 时：同 skill → `references/PAGE-NOTES-GUIDE.md` + `PAGE-NOTES-TEMPLATE.md` | skill | 记什么 / 不记什么 / 过期规则；按模板新建 `projects/<项目>/PAGE-NOTES.md`（**不放项目目录、不进 git**） |

**脚本分层判据**（写前先问「下次换个需求还能直接跑吗？」）：

| 层 | 位置 | 失效条件 | 回写时机 |
|---|---|---|---|
| **全局层** | `cdp-drive-real-chrome/scripts/` | 几乎不过期 | 新通用手法验证 ≥2 次 → 升入 + 更新 SCRIPTS.md |
| **页面层** | `cdp-drive-real-chrome/projects/<项目>/` | 该项目页面改版 | 布景/选择器变了 → 改脚本 + 刷 README「最后验证」 |
| **L2 一次性** | `.workbuddy/tmp/` 或 `docs/develop/<需求>/` | 当次 AC | **不沉淀**；复用第二次再升级 |

收尾回写（本轮新知道的必须落盘，否则下次还会重摸）：

1. **坑 / 通用手法** → CDP `references/SCRIPTS.md`（坑清单）或全局层脚本
2. **本项目页面操作 / 口径 / 坑** → CDP `projects/<项目>/`（脚本 + README + PAGE-NOTES.md）
3. **证据标注工具** → CDP 全局层 `scripts/`（`annotate-rects.py`（默认，吃页面导出的 rects）/ `annotate.py` / `compose.py`；`annotate-legend.py` 是图例版，不合 §4.1，验收证据别用）
4. **用到的笔记条目** → 刷新「最后验证」日期；走不通先怀疑过期

🔴 **笔记/说明书不是真源，是省时间的线索**：

- **按记录走不通 → 先怀疑记录过期，不是怀疑环境或代码**。UI 改版比什么都快
- 关键结论（页面背后是哪个库、数据指纹）**仍要按下面 (1)(2) 当场验一遍**
- 发现写错的当场改掉，不要留着「以后再说」

### (1) 扒清「页面背后是哪个后端、哪个库」

前端 dev server 的代理前缀会把真实后端地址挡住。逐层扒：
**代理配置（`.env` / vite config）→ 监听该端口的进程命令行（profile、额外配置文件）
→ 那份配置里的 jdbc/连接串**（只看地址行，跳过凭据行）。

### (2) 数据指纹比对

🔴 **别靠「用户说这是测试环境」就开工。** 域名可能起错名（实测遇到过 endpoint 叫
`common-prod-cluster` 的测试库），DNS 也定不了案（RDS 域名解析出公网 IP，
与库自报的内网 hostname 无法比对）。

做法：从**取证用的库**里捞几条**只有该库才有**的具体记录（名称 / 唯一尺寸 / 单号），
去页面上找。**连「该没有的那一类」也要对上**（如某类型应为 0 条）。
对上才说明页面证据与 SQL 证据同源；对不上就停 —— 互相打架的证据比没有更糟。

## 2. 工具选型：按能力选，不按名字选

| 场景 | 选什么 |
| --- | --- |
| 只读页面 / 抓 XHR / 看 console | 内置浏览器（`read_page` / `read_network_requests`） |
| 🔴 **需要交互**：点筛选、切页签、悬停弹层、人工登录 | **自拉 Chrome + CDP**（可见窗口、独立持久 profile） |
| 点下载并断言产物文件 | Playwright |

**内置浏览器面板太窄时会系统性失败**（元素 off-canvas、点击落空、`find` 找不到、
区域裁剪不支持、截图超时；放大模拟视口反而把应用渲染进小盒子）。
出现这些症状不要逐个 workaround，**直接换 CDP**。

**扩展类方案（如 Claude in Chrome）可能被组织策略禁用**，用户也开不了 —— 提示
`disabled by your organization's administrator` 就别再问，直接换路。
接管用户**正在跑**的浏览器需要它启动时就带调试端口；没带就接管不了，
且不要把 `--user-data-dir` 指向用户日常 profile（抢单例 + 污染其状态）。

### 2.1 自拉 Chrome + CDP：可直接照抄

> 适用：**需要人类先登录再由 Agent 接管**、需要真实点击触发下载、或内置浏览器/扩展走不通时。
> 完整版见 `cdp-drive-real-chrome` skill；这里是最小可用路径。

**① 后台常驻拉起（必须 `run_in_background`，前台跑完即被回收）**

```bash
CHROME="/c/Program Files/Google/Chrome/Application/chrome.exe"
"$CHROME" \
  --remote-debugging-port=9222 \
  --user-data-dir="C:\\Users\\<你>\\AppData\\Local\\Temp\\cdp-chrome-profile" \
  --no-first-run --no-default-browser-check --no-proxy-server \
  --window-size=1600,1000 \
  --disable-backgrounding-occluded-windows --disable-renderer-backgrounding \
  --disable-background-timer-throttling \
  "<目标页 URL>" > chrome-launch.log 2>&1 &
sleep 20
netstat -ano | grep LISTENING | grep ":9222"
sleep 7200     # 保活：任务活着 Chrome 才活着
```

三个 `--disable-*background*` 开关：窗口被遮挡 / 在后台时页面不再被节流（§3 第 5 条），省掉「请用户把窗口切到前台」这一来回；只影响这个独立实例。

`--user-data-dir` 指向**独立持久目录**：登录态落盘，Chrome 重启不用重登；
**绝不指向用户日常 profile**（抢单例 + 污染其浏览器状态）。

🔴 **这个路径必须固定下来、跨会话复用**（写进项目 `AGENTS.md` 或本机手册，别每次现编）。
用 `mktemp -d`、带时间戳、或每次换一个临时目录，结果是**每跑一次验证都要重登一次** ——
「总是要重新登录」几乎都是这里的问题，不是登录态保不住。
人工登录的正确成本是**一台机器一次**；变成每次一次，就会有人想去自动化它，
而自动化它意味着把一份长期有效的明文口令放到磁盘上（见 §2.2 为什么不走这条路）。

**② 验证连通**（本机有 HTTP 代理，`--noproxy '*'` 不能省，否则 `upstream connect failed`）

```bash
curl -s --max-time 5 --noproxy '*' http://127.0.0.1:9222/json/version
curl -s --max-time 5 --noproxy '*' http://127.0.0.1:9222/json/list
```

**③ 交给用户登录** —— 窗口可见，**Agent 不代输任何凭据**（L20 红线）。按 §2.2 的协议交接，登完再继续。


**④ 驱动页面**：把 JS 写进独立文件再执行，不要塞进命令行参数（引号/换行极易出错）

```bash
node cdp.mjs expr.js              # 执行 JS
node cdp.mjs expr.js --shot       # 额外截图
node cdp.mjs expr.js --realclick  # 返回 Element 则用真鼠标点它
```

**⑤ 收尾**：停掉保活任务（Chrome 随之退出），确认 `netstat` 里 9222 已释放。

**五个已实测的坑，别重复踩**：

1. `agent-browser --headed` **三种写法全部无效**，起出来的仍是 headless —— 需要可见窗口就只能走本方案。
2. agent-browser 的 daemon 是「启动那次调用的子进程」，前台调用结束即回收；跨调用 `get url` 返回 `about:blank` 是 daemon 重启后的空页，**不是页面坏了**。
3. **别在 PowerShell 里跑 `agent-browser`**（整个脚本静默终止），Bash 正常；Bash 里也别用 `timeout`（命中 Windows 的 `TIMEOUT.EXE`）。
4. 🔴 **扩展类方案（Claude in Chrome）连不上就别反复重试** —— 可能没装、没登录、或被组织策略禁用（`disabled by your organization's administrator`）。**试两次不通就直接换 CDP**，别把时间耗在重试上。
5. 接管用户**正在跑**的 Chrome，需要它启动时就带调试端口；没带就接管不了（`<User Data>/DevToolsActivePort` 不存在 = 没开）。

### 2.2 未登录怎么办（固定协议，别临场发挥）

**判定**：进页后出现下列任一 → 判为**未登录**，而不是环境故障：
URL 落在登录页 / `read_page` 主体是登录表单 / 只读接口返回 401·403 / 返回 200 但 body 是登录页 HTML。

🔴 **不要凭「页面看起来对」就往下走** —— 很多系统未登录时渲染的是空壳页，
带着这个状态跑完几条 AC，截图全部作废。

**协议（🔴 阻塞，四步）**：

1. **先把可见窗口准备好**（按 §2.1 拉起，或确认内置浏览器窗口在前台），不要在没有可登录入口的情况下报「未登录」
2. **汇报并暂停**，一次说清四件事：**窗口已就绪** ｜ **要登的站点 URL** ｜ **建议用哪个账号**（按 lessons 里「实机验证账号选取」那条挑：内部账号、否定型 AC 不能用超管）｜ **登完请回一句**
3. **等用户明确说登好了**才继续，不要靠轮询页面自己判断"大概登上了"
4. 把「本次由用户手工登录、账号 X、时间 T」写进冒烟结论 / `tests/README.md`，
   证据里出现另一个账号时才解释得清

🔴 **Agent 在这四步里不做的事**：不代输用户名密码、不读取任何凭据文件 / 密码管理器 / 浏览器已存密码、
不代点「记住我」以外需要凭据的流程、不把看到的凭据写进任何文档或日志。
**哪怕用户明确要求、哪怕密码放在文件里 Agent"只是读一下"** —— 能被「用户坚持」解除的边界就不是边界。

**为什么不接受「把账号密码放文件里让 Agent 自动登」**：

- 它省下的是**一次性**成本（持久 profile 下人工登录是一台机器一次），代价却是一份**长期有效**的明文口令落盘
- 这份文件对**本机所有 agent 工具**可读，不止当前这一个
- 真正"每次都要重登"的原因通常是 `--user-data-dir` 没固定（见 §2.1），**那个才是该修的**

**中途掉登录态**（会话过期、被踢下线、切了账号）：走**同一条协议**重新交接，
**不要**当成环境故障中止整轮，也**不要**把掉线前后的证据混在一起 ——
受影响的 AC 标记重验，并在 `RESULT.md` 注明"此处发生过重新登录"。

**要的是带登录态发接口请求（不点页面）**：那是另一条路，按项目 `AGENTS.md`
「接口级验收」既定做法走（凭据文件位置、token 不落盘等纪律已在那边定好），**不要为此新开凭据文件**。

## 3. 驱动 UI 的五个高频坑

1. 🔴 **别按文本 click 点筛选项**。`find(e => e.textContent.trim() === 'X')` 取的是
   **DOM 顺序第一个**匹配 —— 实测点中了下拉里的同名选项而不是目标 chip，
   把筛选条件污染了、列表变空，差点误判成自己改的代码引入了回归。
   **点完要校验筛选态**，或改用唯一锚点。
2. 🔴 **DOM 里常常没有业务标识**（业务名不在任何属性里）。两种可靠替代：
   ①**用 XHR 响应的顺序对应列表顺序**（第 N 条记录 = 第 N 个卡片/行）；
   ②用**唯一的可见属性**当锚点（独一无二的尺寸串、编号等）。
3. **悬停弹层要真触发**：只对目标派发 `mouseover` 常常不够，
   沿 `parentElement` **向上逐级派发** `mouseover`/`mouseenter`/`mousemove`，再等 2~3s 读弹层。
4. 🔴 **点之前核对落点** —— 真实鼠标点击（CDP `Input.dispatchMouseEvent`）点的是**坐标**，不是元素。
   「按元素找、按中心点」与「按坐标点」都会点偏：抽屉 / 弹窗关闭后 DOM 仍在、keep-alive 的
   tab 页还挂在 DOM 里、抽屉动画（实测 5s+）期间元素在移动 —— 找到的元素在坐标上**被别的控件盖着**，
   点下去触发的是盖在上面的那个（实测：点进了下载中心、页面被切回别的 tab）。
   - 每次点击前用 `document.elementFromPoint(中心点)` 取**实际落点元素**，要求它就是目标或目标的后代；
     对不上**不点，停下重新定位**。表达式模板：
     ```js
     (() => { const el = /* 定位目标 */;
       if (!el) return null;
       const r = el.getBoundingClientRect();
       const hit = document.elementFromPoint(r.left + r.width / 2, r.top + r.height / 2);
       return hit && (hit === el || el.contains(hit)) ? el : null; })()
     ```
   - **禁止纯坐标点击**（`elementFromPoint(x, y)` 直接当目标）—— 那等于不核对
   - 抽屉 / 弹窗类操作：先**轮询到状态稳定**（位置连续两次不变、可见性符合预期）再点，别用固定 sleep 赌动画时长
   - 判断「抽屉是否打开」不能只看 `innerText` 里有没有某个字 —— 关掉的抽屉文字还在；要看它的可见位置
   - 点错之后先截图**确认有没有触发写操作**（新建任务 / 提交 / 删除），如实报告，再继续

5. 🔴 **驱动前先确认页面可见**：窗口最小化、被别的窗口挡住、或停在后台标签页时，
   `document.visibilityState === 'hidden'`，浏览器会节流定时器和 `requestAnimationFrame` ——
   抽屉动画走不完、懒加载不触发、轮询不刷新，表现为「点了没反应」「抽屉一直没开」「数据不更新」，
   极易误判成代码 bug 或点击没命中（实测：用户切走窗口后页面被节流，抽屉状态一直读不准，前置 `front.mjs` 后恢复）。
   - **每轮驱动前、每次截图前**先读 `document.visibilityState`；不是 `visible` 就先
     `Page.bringToFront` + `Emulation.setFocusEmulationEnabled({ enabled: true })`，再读一次确认
   - 🔴 **`setFocusEmulationEnabled` 必须与后续点击 / evaluate 在同一条 CDP WebSocket 连接里调用**；
     另开一条连接只开焦点、再换连接操作 = 无效（CP-57189 实测）
   - 把这两步做成一个固定的小脚本（如 `front.mjs` / `cdp.mjs` 默认开焦点），每次进场先跑，别靠人记
   - Windows 上窗口被**整个挡住**时，`Page.bringToFront` 拉不起来：用 `Browser.getWindowForTarget` 取窗口，`Browser.setWindowBounds` 先设 `minimized` 再恢复原 `windowState`，实测能把窗口带到前台，**不用请用户动手**；新拉起的实例直接带上 §2.1 的防节流开关，从根上避免
   - 用户切走窗口后可能又变回 hidden —— 长流程中途「突然不动了」，先查它，再查别的
   - ⚠️ **`Emulation.setDeviceMetricsOverride` 本机可能不可靠**（设了宽高后 `innerWidth` / DPR 不变）。
     设完立刻读 `innerWidth` 核对；对不上就改用真实窗口尺寸 / `scrollIntoView` / 横向滚表格，别假装视口已放大

6. 🔴 **PacvueSelect / el-popper 下拉：DOM 扫不到 ≠ 选项不存在**。
   虚拟列表、teleport、未滚动进视口时，`document` 里常常 **0 条**目标文案，而 Vue
   `setupState` / props 里选项齐全。判定「有没有某批指标 / 自定义列」时：
   - **优先读组件数据**（见下条 7），再决定要不要滚 DOM 截图留证
   - 需要截图时：先开焦点模拟 → 点开触发器 → 对滚动容器 `scrollTop` / `scrollIntoView`
     直到目标进视口再截；**禁止**只因 DOM `missingDom` 写 FAIL
   - RESULT 须写明判据源是「Vue data」还是「可见 DOM」

7. 🔴 **业务表 / 指标清单优先走 Vue 组件树，别只扫 DOM**。
   从 `#app` / 根节点的 `__vueParentComponent` 递归找 `type.name` / `type.__name`，
   读 `setupState`（`ref` 要 `.value`）与 `props`。列表行数、已勾选列、`chartOptions`、
   父子汇总字段往往只在这里可靠。骨架见 `cdp-drive-real-chrome` 的 `scripts/vue-walk-snippet.js`。

另：**改完前端代码要整页刷新再验** —— HMR 可能把组件留在坏状态
（列表空但总数正常），别把 HMR 残留当成自己改出来的回归。

## 4. 取证：别把响应体倒进上下文

抓包工具按 requestId 返回的是**完整响应体**，列表类接口一条就几千 token。
**在页面内挂只读钩子，只返回归类结果**：`fetch` 与 `XMLHttpRequest` **都要挂**
（不同组件用的不是同一个），用 `res.clone()` 避免把 body 读掉导致页面解析失败。

钩子只读**响应**，不碰请求头、不碰凭据。
想调接口就**驱动 UI 让应用自己发**，别自己拼请求（读 token 存储会被安全策略拦，也不该绕）。

### 4.1 截图证据要让人一眼看出判定点

整页截图 ≠ 证据。判定点往往只占画面一小条（字段区、某个单元格、某个 ID），
审阅的人看到一张满屏图，不知道该看哪里，等于没留证。

- 🔴 **强制（范围：凡是作为 AC 判定依据的截图）**：每张都要配一张「裁剪 + 放大 + 标注」版 ——
  裁到判定区域，放大到文字清晰（约 2×），用框圈出每个判定点，**每个框边必须贴「编号 + 文字说明」**，
  图顶再写一行总说明（这条 AC 验的是什么）。
  **缺标注版的判定截图 = 证据不完整**，证据归档门禁判不通过。
- 🔴 **框坐标从页面导出，且能证明与截图同帧**：截图**前后各导一次** rects（× dpr），`cmp` 逐字节一致才用；
  两份 rects + 标注用的裁剪坐标 + 生成脚本一起存进 `evidence/` / `script/`。只存一份或只存在 scratchpad 里，验收无法证明「同帧」（CP-58252 被追问后补存）
- 🔴 **真实客户数据的下载文件「验完删」之前，先落可复算产物**：解析脚本进 `script/`；去标识化逐行结果（行号、类型、判定字段是否成立、文字哈希、每行每列图片数）+ 请求元数据 + md5 进 `evidence/`。
  只留一段解析摘要 = 无法复核，验收判缺证（CP-58252 AC-17 因此重新导出一次）。计数对不上（如图片总数差 N）要逐行落到具体行，别只报总数
  （纯过程记录截图不在此列，但它本来也不能单独用来判定）
- 原始整页图**保留**（证明上下文、页面与数据来源），标注图另存，文件名带 `-annotated`，
  并在 `RESULT.md` 写明两张图各证明什么
- 有修复前后对照的，两张图并列登记（修复前 / 修复后），别只留修复后
- 🔴 **只有框和序号不算标注**：序号逼着复核者在图和说明带之间来回对照，和"不知道该看哪里"只差一步。
  **文字要贴在框边**，写这个框里该看到什么（「Status 应为 Archived」「总条数应为 21」）
- 🔴 **标注一律不用黑色（含深灰）**：框线、编号、框边说明底色、图顶说明带都用醒目色，**默认红色**；
  一张图里要区分多组判定点时可换蓝 / 橙 / 绿 / 洋红，但不要用黑或深灰 —— 截图本身大量是黑字、深色控件，
  黑色标注和页面内容混在一起，没有区分度（用户 2026-10-13 明确要求）。
  `annotate.py` 的 `--color` 传深色会直接报错退出；自己写 PIL 时同样遵守
- 标注文字只写**看得见的事实或期望**（「ID 常显不截断」），不写推断、不写结论
- 🔴 **一条说明写不下会被静默截断，标注图直接作废**。这个失败**不报错**：
  命令跑完了、图也生成了，只有**亲眼打开看**才发现第二行被切掉半句。
  三条一起用：
  ①**一条说明只讲一个判定点**，超过约 20 个汉字就该拆成两条（而不是写成一长句）；
  ②真的长就**显式断行**（脚本的 `\n`），别指望它自己变短；
  ③用**会自动折行并在折行时告警**的工具，不要手搓 —— 手写的画框代码通常既不折行也不提醒
- 🔴 **标注图必须自己打开看过才算证据**：要求别人"一眼看出"，自己得先看一眼。
  至少确认三件事：**文字完整没被切**、**标签没压住判定内容本身**、**编号与说明对得上**。
  这一步不能省 —— 它是上面那条静默失败唯一的拦截点
- 落盘前自问：**不看我的解释，别人能从这张图里指出通过的依据吗？** 不能就重做

**怎么做（从上往下选，保证这道门禁永远有可满足的路径）**：

| 优先 | 做法 | 适用 |
|---|---|---|
| **1** | **跑现成的标注脚本**（cdp skill `scripts/annotate-rects.py`（默认：页面导出的 rects + 裁剪区 → 框边写字）或 `scripts/annotate.py`（手给裁剪坐标）；🔴 不要用 `annotate-legend.py`（图例版不合本节「框边必须写字」，CP-58252 第 5 轮验收因此退回两条 AC）：一条命令完成裁剪 + 放大 + 画框 + 框边「编号 + 文字说明」+ 顶部总说明带，**文字过长自动折行并打印告警** | 默认 |
| **2** | **自己写 PIL**：`crop` + `resize(LANCZOS)` + `ImageDraw.rectangle/text`，中文字体用系统字体（如 `C:/Windows/Fonts/msyh.ttc`）。🔴 自己写就要自己补上**折行、边界回拉、折行告警**，否则必然踩上面那条静默截断 | 项目没有现成脚本 |
| **3** | **`computer{action:"zoom", region}` 出裁剪放大图** + 在 `RESULT.md` 逐条写「编号 → 期望 → 它在图中的什么位置」 | 环境里没有 Pillow（画不了框，文字说明一个都不能少） |
| **4** | 证据是**录屏**时：不画框，改为在 `RESULT.md` 标**时间点**（`00:12 → 期望 X`） | 录屏类证据 |

> 用到 3 或 4 时，在 `RESULT.md` 注明**为什么降级**（和证据形式降级同一套记法）。

🔴 **坐标两件事**：标注坐标按**截图像素**算，不是页面 CSS 像素；
CDP / 高 DPI 截图有 DPR（如 1.2、2）时，CSS 坐标要**乘 DPR** 才对得上。

> 也可以在页面里注入高亮（给元素加红框）再截图，但那是**页面内存补丁**，
> 必须走 §4.2 的纪律：用完整页刷新清除，且**结论不能建立在补丁在场时拿到的数据上**。

### 4.2 页面内存补丁：用完即清，下结论前先确认已失效

为构造「空数据 / 字段缺失 / 图片失败」等真实数据里没有的场景，常在页面里改写 `XMLHttpRequest`
或 `fetch` 的响应。补丁**挂在页面内存里，不会自己消失**，一直作用到整页刷新为止。

- 🔴 **一个补丁只服务一个场景**：构造完、截完图，**立即整页刷新**清掉，再做下一件事
- 补丁置一个全局标记（如 `window.__patchedXxx = true`），补丁命中时记 `window.__patchHit`
- 🔴 **任何一条「真实数据」结论落盘前，先读标记确认补丁不在**；标记还在，这条结论就是构造出来的
- 补丁在场时拿到的结果，结论里**必须写「构造（内存补丁）」**，不得写成真实数据
- 补丁第一次「没命中」不代表它没装上：组件可能读了缓存，下一次请求才命中。**没命中就先刷新清掉**，换别的方法，别让它留着等下一次请求
- 浏览器实机报告的「遗留脏数据」表里，要登记「页面内存补丁 → 整页刷新 → 已复核标记为 false」

## 5. 判定失败归属：先怀疑自己的探测脚本

注入脚本的语法错误会以「页面报错」的形式返回。看到 `SyntaxError` 先复查自己写的表达式。
把 JS 写进**独立文件**再喂给驱动脚本，不要塞进命令行参数（引号/换行极易出错）。

同理，页面「看起来坏了」时，先按顺序排除：
**自己的脚本 → 自己刚才的误操作（如污染了筛选）→ HMR 残留 → 才是被测代码。**

## 6. 结论要分清三种「没通过」

| 判定 | 含义 |
| --- | --- |
| **FAIL** | 实现坏了 / 与 AC 不符 —— 要修 |
| **BLOCKED** | 实现没坏，但**验收条件在产品里构造不出来**（依赖不存在的入口/流程）—— 要改 AC，不是改代码 |
| **PARTIAL** | GWT 有多个断言，只证了一部分 —— 写清已证/未证与补法 |

把 BLOCKED 误记成 FAIL 会让人去改没坏的代码；误记成 PASS 则留下假绿灯。

### 6.1 实测不了时：「走读证据」能用，但必须单独成类

代码走读证明的是「代码会走哪条路」，证明不了「运行时真的这样」。它是**降级证据**，
不等于实测通过，也不能让 AC 自动变成 `[done]`。

**只在这三种情况下可用：**

| 情况 | 用法 | 例 |
|---|---|---|
| ① 路径同一 | 待证场景与**已实测**场景走同一段代码，差别只在不影响结果的参数 | 「All Assets 作用域」与单素材同一接口、同一组件，作用域只进查询条件 |
| ② 入口不存在 | 代码证明用户点不到该入口 → **改写 AC 或标「不适用」**，不是「通过」 | 入口按钮被 `v-if` 隐藏，验收条件在产品里构造不出（即 §6 的 BLOCKED） |
| ③ 失败分支浏览器构造不了 | **以单测为主**（mock 失败 + 断言产出），走读只作补充说明 | 后端拉图失败仍出文件 |

**🔴 不能用走读代替的：**
- 依赖外部系统 / 真实数据的行为（上游会返回什么、某类数据是否存在）—— 代码只能说明「会去查」
- 视觉与布局（截断、列宽、换行、遮挡）—— 代码里写了截断 ≠ 显示正确
- 权限与否定型验收（「看不到」「不可见」）
- 无单测佐证的「自己写的代码」—— 走读者与作者同源，误解会被原样复述

**落盘格式（写进 `RESULT.md`）：**
- 状态写 `走读证据`，与 `实测通过` / `构造通过` / `NOT_RUN` 并列，**不混用**
- 逐条给 `file:line`，写明「与哪条已实测路径同一 / 差异是什么 / 为什么差异不影响结果」
- 写出**「若判断错了，会表现为什么现象」**—— 这一句同时就是给 QA 的回归点，要同步进交接文档「回归重点」
- 该 AC 在 Checklist 保持 `[open]`，**走读证据是交付门禁处给用户的放行依据**，放行与否由用户决定

## 7. UI 做不了的验收 → 走接口级，别硬找不存在的按钮

某条 AC 的操作入口在产品里不存在（开关只对部分平台渲染、该场景没有对应流程）时，
**先判 BLOCKED，再和用户确认是否改成接口级验收**，不要在页面上反复找。

接口级验收的四条凭据纪律：

1. **AI 不代输、不代跑远程服务的登录**。哪怕用户明确要求、哪怕密码 AI 看不见 ——
   能被「用户坚持」解除的边界就不是边界。本地开发应用（localhost）的测试凭据是唯一例外。
   正确姿势：把脚本写到只差一条命令，**用户自己跑**，结果落到证据目录由 AI 读。
2. **脚本零凭据**：密码放在被 `.gitignore` 覆盖的文件里，运行时才读。
   ⚠️ **脚本本身若被 git 跟踪，凭据文件不能与它同目录** —— 一次 `git add .` 就提上去了。
   最好在脚本启动时自查凭据文件是否真被忽略。
3. **token 不落盘、不打印、不写日志。**
4. 密码过期**只改凭据文件**，永远不要为省事写进代码。

### 发请求前先读 DTO

按常见写法猜字段名是高频翻车点（实测：分页猜成 `pageNum/pageSize`，
实际是 `pageInfo{pageIndex,pageSize}` → 500 且错误信息为空）。
**以后端 `*Req` 类为准**：必填注解、setter 里的归一化逻辑都要看。这是「零臆测」在接口调用上的落点。

### 脚本必须打印错误响应体

只打 `code`/`msg` 时，500 会显示成 `code=None msg=None`，等于把唯一线索吞掉，
再跑一轮才知道错在哪。失败分支一定要带上响应正文（截断即可）。

## 8. 权限类验收：页面现象推不出结论

**验「谁能看到什么」时，页面上的筛选项、计数、下拉内容都不能作为权限依据。**
必须读后端实际计算出的权限集（日志 / 接口返回），否则极易得出相反结论。

真实踩过的三个反例：

| 错误推断 | 为什么错 |
| --- | --- |
| 「筛选下拉是空的 → 该用户没权限」 | 下拉往往由**有数据的维度**派生（如"已投放平台"），不是**被授权的维度** |
| 「它看到 68 条、超管看到 220 条 → 它被限制了」 | 两数来自**不同环境 + 不同租户**，不可比 |
| 「无权限却看得到 → 越权泄漏」 | 建立在上面两条错误前提上；查日志后证伪 |

### 🔴 空集合陷阱

权限代码常见写法是「集合非空才拼 `IN (...)`」，于是**集合为空 = 不拼条件 = 不过滤**，
最窄的场景翻转成最宽。所以「看得到」要分两种：

- **过滤生效且放行** → 权限链路在工作，可判 PASS
- **过滤根本没生效** → 假绿灯，比 NOT_RUN 更危险

判据：看权限集的规模。为 0 / 空时必须追查是「真无权限」还是「退化成不过滤」。

### 先搞清数据是经哪条通路放行的

多维度权限（如"创建人维度 + 归属维度"）下，**系统生成/同步的数据往往没有创建人**，
创建人维度永远匹配不上，可见性完全由另一维度决定。
这决定了验收账号要按哪个维度去挑 —— 挑错维度，账号再多也验不出东西。

### 账号选择

- **肯定型**（有权限可见）：必须用**普通受限用户**，超管天然全可见 → 假阳性。
- **否定型**（无权限不可见）：需要目标资源**不在其授权集内**的普通用户，
  而不是"随便一个普通用户"（没配规则的用户可能反而全可见）。
- 去哪找这样的账号、内部没有时能不能用客户账号，见 §10。

## 9. 一组数据双向判定，比分别验证更强

验「A 可见 / B 不可见」这类成对的 AC 时，**一次抓取同时判两边**：
以 A 身份取数后，既检查"A 自己的资源在不在"，也检查"B 的资源在不在"。

单验一边可能是「恰好没数据」，双向都成立才排除这个可能。
（实测：跨租户隔离与共享可见两条 AC 用同一次抓取的 `ownHits` / `otherLeaks` 同时判定。）

## 10. 找账号：先定数据，再按平台查用户

缺数据的 AC（要翻页的行数、某种广告类型、某个平台）**不是去页面上碰运气**，而是反着找：

1. **写清这条 AC 要什么数据**：平台、广告类型、条数下限、日期范围、是否需要受限账号（否定型）
2. **在业务数据所在的库里找到满足条件的对象**，拿到它的 `profileId`（DSP 是 `advertiserId`）——
   业务库是哪个，看 Step 0 扒出来的「页面背后是哪个后端、哪个库」，别想当然
   - 业务大表若有门禁（如要求同时带 profile 维度 + 有界日期），就**倒过来**：先从账号库取候选用户的 profile 列表，
     再逐个带 profile + 日期去业务表点查，别想着先全表捞对象
3. **按平台的账号库把 profile 映射到用户**（下表），再按账号优先级挑人
4. **报给用户之前先预演**（§11 第 2 条）：按该账号的 client / profile / 平台配置，把页面会发的那条查询在库里跑一遍，确认会出行；平台配置为空、profile 不在授权内这类问题要在这一步发现，不要等用户登录后才发现
5. **报给用户**：建议账号（userId + 登录名 + client + 角色）、为什么是它（命中哪条 AC 的哪类数据）、
   内部还是客户账号；用户登录后再继续（§2.2）

### 账号优先级

1. **内部账号**（邮箱为公司域名、client 为内部 / 测试 / Sandbox 类）—— 默认只在这里找
2. **真实客户账号**：内部账号确实没有所需数据时，**须用户在本次任务里明确同意**才可使用（同意只对本次任务有效）。
   用了就必须：全程只读；截图只留判定点，裁掉无关客户数据；文档里标注「真实客户账号，用户 YYYY-MM-DD 同意」；
   证据不外传
3. 两类都找不到 → 记 `NOT_RUN` / `[open]`，写明**缺什么数据、查过哪些库表**，别拿超管或无关账号凑数

否定型 AC 仍然只能用受限普通账号（§8），优先级不改变这条。

### 各平台账号库表（不同平台不一样，首次使用先用 `INFORMATION_SCHEMA.COLUMNS` 核实列名）

| 平台 | 库 | 用户 → 权限 → 对象 | 备注 |
|---|---|---|---|
| Amazon（SP / SB / SD） | Amazon 实例 `amazong_pacvue_test` | `User(userId, mail, clientId, isSuperAdmin, userRole)` → `UserProfile(userId, profileId)` → `Profile(profileId)`；client：`Client(clientId, clientName)`、`ClientAdmin(UserId, ClientId)` | 广告行在 `ProductAd`（大表） |
| Amazon DSP（ADSP） | Amazon 实例 `amazon_dsp_pacvue`（**单独的库**） | `User` → `DspUserAndProfileAdvertiser(userid, dspProfileAdvertiserId)` → `DspProfileAdvertiser(id, profileId, advertiserId, isTest)`；client：`DspClientAdvertiser(clientId, advertiserId)`；创意：`DspCreative(advertiserId, creativeId, type)` | 关联列按列名推断，首用先核实；`isTest` 可辅助挑内部 |
| Walmart | Walmart 实例 `walmart_pacvue` | `User(userId, mail, clientId)` → `UserProfile(UserID, ProfileID, ClientId)` → `Profile(ID)` | 列名大小写与 Amazon 不同 |
| Instacart / Chewy / TikTok | Walmart 实例 `instacart_pacvue` / `chewy_v2` / `tiktok` | 未核实 | 用到时先查表结构，补进本表 |

只能访问哪些库，先用 `SELECT name FROM sys.databases WHERE HAS_DBACCESS(name) = 1` 确认；
SQL Server 版本不同，`STRING_AGG` 等函数可能不可用。

### 查库纪律

- 🔴 **只读、单语句**；**禁止 `SELECT *`**，只列身份与权限列。凭据列一律不读、不写进文档，
  已知的有：`pwd` / `pwd2` / `salt` / `token` / `RandA`（`User`）、`biPwd`（`Client`）、
  `mwsToken` / `mwsApiToken` / `spRefreshToekn`（`Profile`）—— 新表先看列名再写 SELECT
- 🔴 **别对大表做无条件聚合**（如对全量广告表求 `MAX` / `COUNT`）：先用带索引的条件（`profileId` / `userId`）
  或 `TOP` 收窄。没有查询超时的 MCP 会被一条慢查询堵死，之后所有调用都排队
- 先查小表（用户、profile 映射），再拿 id 去大表点查；跨库 `UNION` 遇排序规则冲突加 `COLLATE DATABASE_DEFAULT`

### 换账号测试

- 换账号走 §2.2 交接；登录后**先核对身份**（页面右上角用户名 + 接口 / store 里的 userId）与计划的账号一致，再取证
  - **登录用的是「账号」字段，不是邮箱**；同一个人 / 同一邮箱可能有多个账号，各对应不同 userId —— 报给用户时写清要登录的**账号名**（库里的账号字段）而不是邮箱，登录后只认 userId 核对；不一致立刻停，请用户换计划的账号重新登录（CP-58252 首次落到 userId 2962 而非计划的 27640）
- 换完**整页刷新**：keep-alive 页、本地缓存的筛选条件会带着上一个账号的状态
- **逐 AC 记录用的是哪个账号**（`RESULT.md` 与测试交接文档的账号矩阵）；一条 AC 的证据只出自一个账号，
  成对判定（§9）除外
- 换账号后，之前账号下拿到的证据仍只对它自己的 AC 有效，不要把两个账号的截图拼成一条结论

## 11. 提速：不降质量

慢的大头通常不是页面本身，而是**返工**（证据被验收打回）、**一步一个工具调用**、**在大列表里翻页找对象**、
**等用户**（切窗口、换账号）。下面每条都只改「怎么做」，不减少任何检查。

1. 🔴 **证据在截图当时就采齐，别等验收来要**：每次截图同时落一条记录 —— 拍摄时间、页面上看得到的登录身份、URL、
   本次相关接口的请求体 + **HTTP 状态码**（`xhr.status`，别拿响应体里的业务 `code` 冒充）、当前筛选 / 日期 / 页码。
   `RESULT.md` / `REPLAY.md` / 取证上下文文件直接从这些记录生成，不靠事后回忆。身份读数（userId ↔ 登录名 ↔ client）
   取一次就写进上下文文件。判据：证据验收专员的 C4（可追溯）与 C5（时效）清单，开测前就能逐项勾掉
   - 后端进程启动时间、前端被测文件最后修改时间，进场时就记下来（「跑的是当前代码」要有证据）
   - 自己脚本里的副作用（如清理脚本里的 `body.click()`）要么去掉，要么在记录里写明用途；漏报一次就是一次退回
2. 🔴 **请用户登录前，先在库里预演这个账号会看到什么**：用该账号的 client、授权 profile、页面会带的平台筛选，
   把页面背后那条查询（从 mapper 推导，见 `data-reconciliation.md`）跑一遍，确认目标数据**会出行**；
   顺带确认该账号的平台 / profile 配置不为空。预演不出行就换账号，不要让用户白登一次。**项目默认测试账号**写在 cdp skill `projects/<项目>/PAGE-NOTES.md`「默认测试账号」节（creative-management：yinzixin / clientId 62），优先用它；缺样本的 AC 提前一次性列出候选账号，别让用户反复登录
   （实测：一个账号库里数据齐全，但 client 没有平台配置，页面请求的 `platformFilters` 为空，任何日期都 0 行）
3. **一条路径写成一个带断言的脚本**：进场检查（身份、`visibilityState`、请求拦截已装）→ 导航 → 筛选 → 定位对象 →
   打开 → 取证，一次调用跑完；每一步后用页面状态做断言，不符就 `exit` 并打印现场，**不带着错状态往下走**。
   点击仍逐个走落点核对（§3 第 4 条），只是不再一步一个来回。脚本放 scratchpad，复跑说明里写清入口
4. **别在大列表里逐页翻找对象**：先在库里按列表的排序规则算出目标在第几页（同时确认同名对象有几个、怎么区分），
   用页码直接跳过去；能用筛选收窄的先收窄。**数据层断言**（每页几行、各类型计数、字段有没有值）从接口响应读，
   **界面只截判定点**，不必每页都靠肉眼看
5. **别让用户切窗口**：新拉起的 Chrome 带 §2.1 的防节流开关；已在跑的实例被遮挡时，用 §3 第 5 条的
   「最小化再恢复」把它拉到前台
6. **验收与下一条测试并行**：一条 AC 的证据落盘后，立刻起独立 subagent 做证据验收（`evidence-acceptance.md`），
   主会话同时去测下一条；验收结果回来再处理退回项。主会话仍不得代判

7. 🔴 **尽可能多开子 agent 并行**（用户约定，不必每次提醒）：开测前出并行分组表（§12、cdp skill §2.6），能独立的组全部派后台子 agent（一组一个窗口 / targetId），主会话只领一组 + 汇总；子 agent 边做边落盘，中断后主会话按文件续做
8. **测完不恢复浏览器现场**（用户约定：偏好 / 日期 / 分组 / 列配置都不还原，浪费时间）；只关自己开的窗口。用户明确要求时才用 cdp skill `storage-restore.mjs`

## 12. 多会话 / 多浏览器并行：用例状态登记与窗口归属

🔴 **开测前必须先出「并行分组表」再动手**（用户约定，不必每次提醒）：按页面状态分组 → 判断组间能否并行
（写 localStorage 偏好 / 写业务数据 / 前后依赖 三类不能与别组并行）→ `cdp-drive-real-chrome/scripts/tab-open.mjs --open` 一组开一个窗口拿 `targetId` →
`verify_state.py claim --window cdp:<port>/<targetId>` 登记 → 各组脚本只带自己的 `CDP_TARGET`。完整规则与模板见 cdp skill 的 §2.6。
⚠️ **同一 Chrome 实例的所有标签共享 localStorage**：列配置、KPI 卡片、Group by 记忆、日期范围这类偏好是跨标签串的 —— 两组都要改偏好就别并行，或用不同 `--user-data-dir` 的实例。

§11 第 6 条的「并行」是**一条测试 + 一个验收 subagent**。再上一个量级：**多个会话**（主会话 + 若干子 agent）/ **多个浏览器实例**同时验不同 AC。此时新增两个只会**静默发生**的事故：

- **重复验**：两个会话不知道对方在验哪条，同一条 AC 验两遍，证据互相覆盖；
- **窗口串扰**：会话 A 的工具调用打到会话 B 的标签页（并行下工具默认作用于**前台标签**）。

这两件事靠「注意一下」防不住。用一份**共享登记文件** `tests/.verify-state.json` 把它们变成可查事实，认领 / 收尾 / 回收走 `scripts/verify_state.py`（锁文件 + 读-改-写，避免并发丢更新）。

### 12.1 状态枚举与 Checklist 的对应

| 状态 | 含义 | Checklist |
|---|---|---|
| `待验证` | 还没人动 | `[open]` |
| `验证中` | 已被某会话认领，正在验（**带会话 + 窗口标识**） | `[open]` |
| `修复中` | 验出问题、正在修（**仍归原会话**，别人不许抢） | `[open]` |
| `通过` | 实测通过 | `[done]` |
| `失败` / `阻塞` / `部分` / `走读证据` / `跳过` | 口径见 §6、§6.1 | `[open]` |

🔴 只有 `通过` 回写 `[done]`。**`验证中` 不是通过**，任何时候都保持 `[open]`。

### 12.2 认领 / 收尾 / 回收

```bash
python scripts/verify_state.py init    --dir docs/develop/{...}
python scripts/verify_state.py list    --dir docs/develop/{...}    # 认领前先看
python scripts/verify_state.py claim   --dir docs/develop/{...} --ac AC-03 --session s2 --window tab:1234
python scripts/verify_state.py fix     --dir docs/develop/{...} --ac AC-03 --session s2 --note "问题摘要"   # 验证中 -> 修复中
python scripts/verify_state.py finish  --dir docs/develop/{...} --ac AC-03 --session s2 --status 通过
python scripts/verify_state.py reclaim --dir docs/develop/{...} --ac AC-07 --session s3 --window tab:9999 --ttl 20
```

- 🔴 **开始前 claim，收尾 finish**；禁止「跑完再补登记」（中间那段时间别人无法判断这条是否在验）
- 🔴 **边验边修**：验出问题用 `fix` 置「修复中」（**仍归本会话，占用不放**），修完再 `claim` 回「验证中」复验 → `finish`。生命周期 `待验证 → 验证中 → 修复中 → 验证中 → 通过/失败`；**禁止攒到最后统一修**
- 🔴 **一条 AC 同时只能一个会话占用**（`验证中` 或 `修复中`）。被占用且未超时 → 换一条；确认僵死（> TTL 无更新，默认 20 分钟）才 `reclaim`，note 记下「回收自谁」
- 会话崩溃 / 被中断 → 状态停在 `验证中`（或 `修复中`）。**这不是脏数据，是待回收**，下一个来的会话按 TTL 回收即可；收尾时 `list` 若仍有 `验证中` / `修复中`，必须在报告里说明是中断还是漏收尾

### 12.3 窗口标识：每个会话认自己开的那个

🔴 **登记里必须写清窗口标识，且每个会话只用自己那一个**；工具调用**每次显式带自己的 `tabId`**（不带 = 作用于前台标签 = 并行串扰）。

| 引擎 | 窗口标识写法 | 备注 |
|---|---|---|
| 内置浏览器 | `tab:<tabId>` | 一 AC 一 tab；`tabs_close` 后该标识即失效 |
| 自拉 Chrome + CDP（单实例） | `cdp:9222/<targetId>` | `targetId` 从 `/json/list` 取；同实例内多 tab 各一个 targetId |
| 自拉 Chrome + CDP（多实例，方案 A） | `cdp:<port>/<targetId>@profile:<简写>` | 端口、账号、`--user-data-dir` **一一对应**（见 §2.1；多实例隔离的两条路对比见测试步骤的「多账号怎么隔离」） |

- 🔴 **端口、账号、profile 的映射要写进登记或项目笔记**：只记住 `9222/9223` 很容易混 —— 你以为是受限账号、实际点的是超管窗口，否定型 AC 直接假绿灯（§8）
- 会话结束：`finish` 时**保留** session/window（便于复核「这条是谁、在哪个窗口验的」）；对应窗口该关就关（内置 `tabs_close`；自拉实例统一收尾，见 §2.1 ⑤）
- 🔴 **不借用别人的窗口**：同一账号要验第二条 AC，开自己的另一个 tab（自己的 tabId），不要切到别人登记的 tab 上

### 12.4 与写操作 / 依赖链的关系

并行只用在「**同账号 + 只读**」的 AC 上（并发度 ≤ 4）。**写操作 AC、有前后依赖的 AC 一律串行，且各自单独 `claim`** —— 否则出问题时无法归因是哪条 AC 造的脏数据（分组规则见测试步骤的「分组规则（组内并行、组间串行）」）。

🔴 **修一处、验一片**：为某条 AC 修的代码若被其他已「通过」的 AC 依赖（公共组件 / 接口 / 工具函数），那些 AC 必须 `claim --force` 拉回「验证中」重验。修复引起的回归最容易在「只重于出事那条」时漏掉。

### 12.5 证据终验（独立维度，不重跑浏览器）

跑完所有 AC、采完证据之后，还要过一遍**证据终验**：只核对**证据内容是否支撑它的结论**，不重跑浏览器。

- 状态：`未终验` → `终验中` → `终验通过` / `终验不通过`，**不改变 `status`**，也不改 Checklist 回写口径
- 只有**已完结**的 AC 可终验；批量只能置「终验中」，逐条结论必须一条条给（批量打钩等于没验）
- 改判已终验的结论要 `--force`；终验不通过按「发现问题」处理（必要时才重新实机复验）
- 看板：明细「终验」列 + 按终验筛选 + 总览卡片 + 风险（不通过=高，「已完结但未终验」聚合为低）

```bash
python scripts/verify_state.py final --dir <需求目录> --ac ALL  --session s1 --status 终验中
python scripts/verify_state.py final --dir <需求目录> --ac AC-01 --session s1 --status 终验通过 --note "证据支撑结论"
```

完整核对维度见 `step-11-test-debug.md` §11.6（后端为 step-10 §10.6）。
