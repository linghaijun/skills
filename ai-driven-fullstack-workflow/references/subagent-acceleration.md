# 子 agent 加速（何时用、怎么用、何时不用）

> 两个 workflow 共用本文件（逐字相同，按**步骤名称**而不是步号引用，因为两边步号不同）。
> 目标是**省时间、省主上下文**，不是为了显得并行。每次准备派子 agent 前过一遍 §1 的三问；
> 判断不了就不派 —— 派错的代价（结果要返工、上下文要重讲）通常大于串行做完。

## 1. 先过三问（全部是「是」才派）

| # | 问 | 「否」的典型情况 |
|---|---|---|
| 1 | **独立吗？** 这块活不需要等别的结果、也不跟别的写者改同一批文件 | 下游要用上游结论；两个写者都要改同一个 Service / 同一个 .vue |
| 2 | **够大吗？** 预计 ≥10 次文件读取 / 搜索，或 ≥2 个互不相干的区域（多仓、多模块、多 AC 组） | 已知文件和行号的单点查询、一两处小改 —— 自己做更快 |
| 3 | **能验收吗？** 产出可以用「结论 + 证据 `file:line` / SQL / 截图」抽检 | 只能给出「感觉」「建议」、主 agent 无法复核的结论 |

三问全「是」→ 派；任何一个「否」→ 主 agent 自己做。
**收益判断**：多个子 agent **同一条消息里一起发**才是并行；一个一个发只是换了个地方串行。

## 2. 按步骤的推荐用法

| 步骤 | 适合派子 agent 的活 | 并发建议 | 注意 |
|---|---|---|---|
| 需求澄清 Q&A | 按仓 / 模块并行取证代码现状（后端仓、provider、前端仓各一个只读 Explore） | 2–4 个只读 | **向用户提问、记录答案只能主 agent 做**；子 agent 只供证据 |
| Checklist（可选代码 gap-check） | 按 Story / 入口分组逐条对代码找缺口 | 按组数，≤4 | 结论必须带 `file:line` |
| 技术方案 | 影响面反查（原则「影响面反查」）、复用清单搜索、同类实现对照，按仓或按关注点拆 | 2–4 个只读 | 方案取舍由主 agent 定，子 agent 只出事实 |
| 编码 | tasks 中**文件集合互不相交**的任务组（典型：后端组 / 前端组；不同仓） | 写者 ≤ 不相交文件集数 | 契约已在「API 契约」步冻结才可并行；**任何写者都禁 git**；同一仓的 `mvn` 构建不要并发（target 目录互踩） |
| 测试 / 编译自愈 | 大段日志、surefire 报告的定位分析（只读） | 1–2 | 修复由主 agent 或单一写者执行，避免两处同时改 |
| 浏览器实机验证 | 按 AC 组并行，每组一个窗口 | 见 `browser-playbook-parallel.md` §11/§12 | 🔴 并行规则（锁窗口、`verify_state.py` 认领、写操作单独授权）全文以 parallel 文件为准 |
| 数据核对（只读 SQL） | 按 AC 组并行写 / 跑对账 SQL | **重查询同时 ≤2** | 慢查询会拖垮共享 MCP 服务；全程只读，见 `data-reconciliation.md` |
| AI Review | 合规各维 / 缺陷猎捕 / lessons 合规 按维度拆给不同子 agent | 2–4 | 子 agent 发现的问题**主 agent 逐条复核**后才写进报告，误报直接剔除 |
| 全局一致性审查 | 证据验收**必须**由独立子 agent 盲审（见 `evidence-acceptance.md`）；跨文档一致性可按文档对拆 | 按 AC 量 | 证据验收子 agent 不能是做验证的那个 |
| 经验沉淀 | 一般不派 —— 量小，且要用户确认 | — | — |

## 3. 绝不派给子 agent 的事

- 🔴 **所有阻塞门控**：向用户汇报、等确认、替用户做选择（破坏性变更方案、范围裁决）
- 🔴 **所有写操作授权类**：DDL 执行、`git add/commit/push`、写 Jira、写数据库、造数 —— 子 agent 的 brief 里要明写「禁止」
- 需要完整对话上下文才能判断的事（需求细节的取舍），除非 brief 能把上下文讲全
- 两个写者会碰同一文件的活；同一个浏览器窗口 / 同一个已登录会话的操作

## 4. brief 怎么写（子 agent 看不到对话）

必含六项，缺一项就会返工：

1. **目标**：一句话说要什么结论
2. **范围**：仓 / 目录 / 文件 / AC 编号；**可写范围**（只读任务写「只读，禁止修改任何文件」）
3. **约束**：零臆测（结论标 `证据：file:line`）、禁 git、禁写数据、禁连生产、禁占用别人的浏览器窗口
4. **已知事实**：已确认的口径、契约路径、需求目录路径 —— 别让它重新猜
5. **输出格式**：结论清单 + 证据；给字数上限（通常 ≤1500 字），禁止粘大段原文
6. **完成标准**：什么算做完（例如「每条 AC 都有结论」「编译通过」）

纯机械的搜索 / 汇总可以选更便宜的模型；需要设计判断的保持主模型。

## 5. 结果怎么收

- 子 agent 的报告是**线索不是证据**：写进任何交付物前，主 agent 至少抽检关键结论（打开它给的 `file:line` 看一眼），这同样适用原则「零臆测」
- 写代码的子 agent 收工后，主 agent 看 diff、跑编译 / `validate_step.py`，不能只看它的「已完成」
- 两个子 agent 结论冲突 → 主 agent 取证裁决，不取平均
- 🔴 **收到汇报的同一轮由主 agent 回写所有记录处**（verify_state 状态、RESULT 结论、回归清单行与汇总、tasks 勾选、交接文档）—— 子 agent 通常不动这些，主 agent 不回写就没人回写，见 `browser-playbook-parallel.md` §12.7
- 在本步产出物或汇报里注明「哪些部分由子 agent 产出、已抽检哪些」
