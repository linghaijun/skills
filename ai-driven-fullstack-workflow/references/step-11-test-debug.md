## 11.2 编译运行测试与自愈
- **后端**：Maven 编译 + 跑单测；**前端**：构建（如 `npm run build`，不跑组件测试——不写）

### 🔴 根因优先（防"改测试让它过"）

> **"改断言迁就实现"是"单测全绿但线上有 bug"的头号来源。** 11.3 自检是兜底，兜在后面不如堵在前面。

- **每个失败先归类再动手**，并写明归类依据：
  | 分类 | 典型特征 | 正确处置 |
  |---|---|---|
  | 业务代码 bug | 实际值不符合 Step8 矩阵的预期 | **改业务代码** |
  | 测试写错 | 断言值与 Step8 矩阵不一致，或测试前置数据构造错 | 改测试，**并说明原断言错在哪** |
  | Mock 与真实签名不符 | 参数/返回类型对不上 | 对齐真实签名（见 `.agents/testing.md`） |
  | 环境问题 | 端口占用、依赖未起、脏 target | 修环境，**不要改代码迁就** |
- 🔴 **禁止为了让测试通过而放宽断言/删断言/加 `@Disabled`**；确需改断言，必须引用 Step8 矩阵说明"原预期为什么是错的"
- 🔴 **同一用例连续 2 次改的都是测试而非业务代码 → 强制停下问用户**（大概率是在绕过真问题）
- 报错原因不明朗、或修了又坏的，用 `systematic-debugging` skill 定位根因，**不要靠反复试**
- 🔴 **架构门禁 `ArchitectureTest` 什么时候跑**（本机实测 **11.6 秒**，3 条规则）：

  | 时机 | 跑不跑 | 为什么 |
  |---|---|---|
  | **L1 改动反馈**（默认） | **改动触及这三类时必跑**：新增/修改 **Controller**、**新建类**（构造器注入）、动 **`utils` 包** | 这三类正是三条规则的触发面，当场发现比收口后返工便宜 |
  | **L2 模块收口** | **必跑** | 11.6s 对高频 L1 偏重，收口时挂上，仍在"写完这个模块"的范围内 |
  | **L3 全量门禁 / 本步终验 / 提交前** | **必跑** | 最后一道 |

  ```powershell
  # 单独跑架构门禁（约 11.6s + maven 启动）
  & "C:\Users\HaijunLing\programs\apache-maven-3.9.14\bin\mvn.cmd" `
    -pl creative-management-api "-Dtest=ArchitectureTest" `
    "-Dsurefire.failIfNoSpecifiedTests=false" "-Dcheckstyle.skip=true" test
  ```

  🔴 **这三条规则是 `freeze()` 棘轮，存量违规已冻结进 `archunit-store/`（随仓库提交）——
  它们失败的含义就是「本次新增了架构违规」，不是历史遗留。必须修代码，
  禁止把新违规写进 freeze 基线让它变绿**（那是把门禁反向用成许可证）。
  存量基线：Controller 直连 Mapper **0 条**（这条最干净，一碰就红）、字段注入 408 条、utils 依赖 Spring 16 条。
- **自愈终止**：连续 3 轮未全 Pass 则停止，汇报错误清单、每轮归类结论和已尝试方案，请求人工介入

## 11.3 业务逻辑自检（防"测试全 Pass 的虚假安全感"）

> 测试是 AI 自己写的，可能漏写分支或断言写错。"全部 Pass"只证明"已写的测试通过了"，不等于"需求全部实现了"。

**动作**：AI 以挑刺者视角对业务代码做以下自检（不依赖测试结果）：

1. **Checklist 逐条对照**：按 `AC-NN` 顺序逐条核对，每条 GWT 的 When/Then 在代码中有实现支撑（含前端交互态）；自检报告须逐条列出 `AC-NN` 与结论
2. **分支完整性**：列出所有 if/switch 分支与测试矩阵对照，标记代码存在但单测未覆盖的分支
3. **空值/边界自查**：null、空集合、超长字符串、size=0、负数等防御（前后端同查）
4. **副作用验证**：DB 写操作方法的 @Transactional、回滚、update_time/version 更新
5. **前端态覆盖**：逐条对照《Step 8-前端测试验证指标矩阵》（人工验证清单），核查 loading/空/错误/权限不足态是否有实现；错误文案是否英文友好且不含原始技术信息（见 L16）
6. 🔴 **回归项核对**：逐条走《Step 8-回归验证清单》的 `R-NN`，按其"验证方式"执行（跑既有单测 / 留到 11.4 实机 / 交人工），**回填结论列**。未验证的 `R-NN` 与未实现的 AC **同等对待**，不得判本步通过

**输出格式**：
```
| Checklist 条目 | 端侧 | 实现位置 | When 分支 | Then 落实 | 自查结论 |
|---|---|---|---|---|---|
| AC-07 SHARE - 分享入口 | 前后端 | ShareController.java:25 / ShareDialog.vue:10 | ✅ | ✅ | OK → `[done]` |
| AC-08 SHARE - 审核状态 | 后端 | AssetServiceImpl.java:88 | ⚠️ 仅 Approve/Deny | ⚠️ 缺 Processing | 需补 → 保持 `[open]` |
```

**状态回写（CRITICAL）**：自查结论为 ✅ 的条目，必须把 `Step 3-Checklist.md` 中该 `AC-NN` 由 `[open]` 改为 `[done]`；⚠️/❌ 条目保持 `[open]`；本期不做的标 `[blocked]` 并附原因 + 回写 Spec。自检报告末尾汇总：`[done] X 条 / [open] X 条 / [blocked] X 条`。状态回写后**必须重新生成 `Step 3-Checklist-Jira.txt`**，保持两版一致。

发现 ⚠️/❌ 项时先修复业务代码（非测试），修复后重跑 11.2 确认无回归，直至全部 ✅。
**自检终止**：连续 2 轮仍有未解决项则停止，连同自检报告一起提交 Step12 AI Review。

**产出物**：①《Step 11-业务逻辑自检报告》(md) ②全部 ✅ 的业务代码

**→门控**：🔴 **阻塞** —— 汇报自检报告 + `[done]/[open]/[blocked]` 汇总 → **暂停等确认** → AI 询问是否执行 11.4

> 🔴 **阻塞门控**：必须**暂停等待用户明确确认**，未获通过禁止进入下一步。
> 之所以阻塞：本步把 `AC-NN` 从 `[open]` 回写成 `[done]`，**这个状态是 Step13 交付门禁的判据**；回写错了等于给未完成的需求盖了完成章。（用户同意则执行 11.4 后再进入 Step12；拒绝则直接进入 Step12）

#### 进场检查（强制前置，未过禁止进 AC-01）

> 名字刻意不叫「Step 0」：`browser-playbook-core.md` §1 已经有一个 Step 0（扒清页面背后是哪个库 + 数据指纹），两个都在浏览器验证开头、内容完全不同，同名必然串。

> 目的：避免 dev server 没起 / 网关 502 / 前置数据缺失，走到第 3 条 AC 才暴露，导致前面所有操作与截图作废。

**0. 先读项目的浏览器笔记**（若项目维护了页面级笔记，本工作区见 `AGENTS.md`「浏览器笔记与可复用脚本」）：
读对应模块那份，拿到入口路径、操作→XHR 对照、异常态构造方式、已知的坑、测试数据在哪，省掉重复摸索；
没有就新建一份空的，验证过程中边做边填。
🔴 **笔记不是真源**：按它走不通时**先怀疑笔记过期**，不是怀疑环境或代码；用到哪条顺手刷新它的验证日期。

按顺序做四件事，**四项全过才允许开始走 AC**：

1. **进页可达**：`navigate` 到验证环境首页（或目标模块页），页面正常渲染（`read_page` 能拿到预期主体结构）
2. 🔴 **登录态确认（显式探测，不要等接口 401 才反推）**：满足下列任一即判**未登录** ——
   URL 落在登录页 / `read_page` 主体是登录表单 / 只读接口返回 401·403 / 返回 200 但 body 是登录页 HTML。
   **不要凭「页面看起来对」就往下走**：很多系统未登录时渲染的是空壳页，带着这个状态跑完几条 AC，截图全部作废
3. **控制台干净**：`read_console_messages{onlyErrors:true}` 无阻断性 JS 报错
4. **接口通且有数据**：触发一个**只读**列表/详情端点，`read_network_requests` 确认 HTTP 200 且返回非空（验证鉴权与测试数据都已就位）

**判为未登录时**：这不是环境故障，**不要中止整轮**，按 `browser-playbook-tools-cdp.md` §2.2 的交接协议走——
备好可见窗口 → 一次说清「窗口已就绪 ｜ 要登哪个站点 ｜ 建议用哪个账号（按实机验证账号选取那条 lesson 挑） ｜ 登完回一句」→ **暂停等用户明确说登好了** → 继续。
🔴 **Agent 不代输用户名密码、不读取任何凭据文件 / 密码管理器 / 浏览器已存密码**；
「把账号密码放文件里让 Agent 自动登」一律不走 —— 持久 profile 下人工登录是**一台机器一次**，
总是要重登说明 `--user-data-dir` 没固定，该修的是那里（playbook §2.1）。

其余任一项不过 → **立即停止**，汇报失败项 + 疑似原因（服务未启 / 数据为空 / 环境 URL 错），请求人工处理，**不进入 AC 验证**。
冒烟结论写入 `tests/README.md` 顶部「进场检查」小节；**本次若由用户手工登录，记下账号与时间**，
证据里出现另一个账号时才解释得清。

#### 执行规则（只读优先）

- 🔴 **取证要当场采齐、登录前要先预演、路径要写成带断言的脚本** —— 见 `browser-playbook-parallel.md` §11「提速：不降质量」；那里每条都只改做法，不减检查

- 🔴 **浏览器操作默认只读（L20）**：只浏览 / 筛选 / 翻页 / 切账号 / 截图 / 抓包；**禁止删除、修改、上传、分发、改名、提交任何表单**。唯一例外是用户对**该具体动作**单独授权，且授权**不跨条目、不跨会话继承**；拿不准某个按钮会不会写数据时**先问再点**

- **覆盖**：本次 Checklist 中标 `[前端]`/`[前后端]` 的 `AC-NN` 条目，按编号顺序走一遍用户路径
- **写操作默认不执行**（新建/删除/提交/支付）；确需验证写路径时，先说明影响 → 获用户明确同意 → **仅在测试环境**执行 → 记录产生的脏数据

- 🔴 **一 AC 一闭环（CRITICAL，禁止批量补证）**：每条 AC **当场走完当场落盘**，再开始下一条：

  ```
  ⓪ 认领登记：verify_state.py claim --dir <需求目录> --ac AC-NN --session <自己> --window <自己开的窗口>
     → 该条置「验证中」并登记会话 + 窗口标识（多会话并行时的互斥锁，见下「多浏览器/多会话并行」）
     🔴 登记文件还不存在（第一次跑）先建：verify_state.py init --dir <需求目录> [--acs AC-01,AC-02]
        或 verify_state.py init --dir <需求目录> --from-result（按已有 tests/AC-NN/RESULT.md 回填历史状态）
        —— 没 init 就 claim / final 会直接报错停住；11.6 的 final 也需要登记文件非空（空的会拒跑，
        免得 --ac ALL 在 0 条上空转「通过」）
  ① 开该 AC 专属 tab（并行）→ 流水天然隔离，无需 marker；
     若复用同一 tab（串行），则记 marker：当前流水条数/时间戳，或 navigate 重进页面清流水
  ② 执行该 AC 的操作步骤（只用 ⓪ 登记的那个窗口）
  ③ 立刻取证：截图/录屏 + read_page 文本 + read_network_requests（只取 marker 之后的请求）
  ④ 立刻写盘：evidence/ 落文件 + 写 tests/AC-NN/RESULT.md（含本轮 marker 值；顶层第一条 `- 结论：<状态词>` 用 ⑤ 的同一个词）
  ⑤ 收尾登记：verify_state.py finish --ac AC-NN --session <自己> --status <通过/失败/阻塞/…>
     🔴 登记状态与 RESULT「- 结论：」必须一致 —— validate_step 测试步 / 交付门禁查「用例状态 vs RESULT」，不一致判 FAIL（回写规则见 parallel §12.7）
  ⑥ 刷新看板：⑤ 的 claim / fix / finish / final 登记成功后**自动**重跑 verify_dashboard.py（不用手动跑；
     加 --no-dashboard 才跳过，禁止为省时间跳过）。🔴 每验完一条 AC 看板必须马上体现 ——
     用户靠看板看进度，「全部验完再统一刷新」等于用户全程不知道进度。
     不走 verify_state 登记的（如主会话手工改 RESULT.md）改完要手动跑一次 verify_dashboard.py --dir <需求目录>
  ⑦ 才允许进入下一条 AC
  ```

  **禁止走完一批 AC 再回头整理**——`requestId` 会随流水翻页失效、截图时机也已错过，事后补的证据不可信。

- 🔴 **并行验证轮开始后冻结代码**：≥2 组同时在测时只修**阻塞缺陷**，非阻塞问题 `fix` 登记 + 留现场证据，攒到本轮所有组收尾后一起改、一起 `invalidate`、一起重验 —— 边测边改会让别组正在拍的证据随时过期、同一批 AC 反复重拍。全文 → `browser-playbook-parallel.md` §12.4

- 🔴 **边验边修，不攒批（CRITICAL）**：走 AC 时**发现问题立即停下来修，修完接着验这条，验完再进入下一条**。禁止「先把所有 AC 跑完，最后统一修」——攒到最后，现场（截图时机、请求流水、构造态）全丢，一条挂起还会拖垮整轮的结论归属。

  ```
  ① 发现问题 → verify_state.py fix --dir <需求目录> --ac AC-NN --session <自己> --note "<问题摘要>"
     → 状态「验证中」→「修复中」（仍归本会话；别人不许抢，见下「多浏览器/多会话并行」）
  ② 改业务代码（非绕过）：禁止改测试 / 放宽或删断言 / @Disabled 让它变绿（11.2 根因优先）
  ③ 重跑 11.2 编译自愈确认无回归；前端改完先整页刷新再进页面（HMR 可能留坏状态，见 playbook §3）
  ④ verify_state.py claim --dir <需求目录> --ac AC-NN --session <自己> --window <原窗口> → 回到「验证中」复验
     （该 AC 已被上一条链完结时，先 `claim --force` 才能重验 —— 见 §11.6 与 parallel §12.7）
  ⑤ 复验通过 → verify_state.py finish --dir <需求目录> --ac AC-NN --session <自己> --status 通过
     （只有「验证中」能 finish；状态已是 通过/失败/部分/阻塞/跳过 的，先 `claim --force` 再 finish）
     仍失败 → 同一问题最多 2 轮，第 3 轮停下汇报请求人工介入
  ```
  > 🔴 每个子命令都必须带 `--dir <需求目录>`（`verify_state.py` 把 `--dir` 设成 `required=True`，
  > 漏了直接 exit 2 = 「必须停」档，一次正常登记就变成一次人工介入）。

  - 🔴 **两条 CRITICAL 的优先级（并行下以「冻结代码」为准）**：**并行验证轮内**（≥2 组同时在测）只修**阻塞缺陷**，
    非阻塞问题 `fix` 登记 + 留现场证据，攒到本轮收尾一起改一起重验 —— 此时「边验边修」降级为「只修阻塞」；
    **单组串行验证时**按「边验边修」立即修。拿不准就先判断是不是并行轮（默认并行，见下「并行执行」）
  - 🔴 **每次改代码当场作废受影响 AC**：修复 / 口径变更 / 动公共代码（组件 / 接口 / 工具函数 / Mapper）之后，立刻 `verify_state.py invalidate --dir <需求目录> --acs <受影响 AC> --reason "<HH:MM 文件 改了什么>"`，拿不准就多作废；只记时间线不算登记；`R-NN` 同此 —— 旧证据证明不了新代码，时效类退回曾占验收不通过的一半。全文 → `browser-playbook-parallel.md` §12.4
  - 🔴 **修复若触发跨层改动 / 范围扩散 / 非功能回归 / 架构突破 → 立即停止本步**，回退对应步骤（Step4/5/6/7）重审后再回来（Step12「变更影响重评估」红线）

- **XHR 归属锚点**：**一 AC 一 tab 时可跳过本条**（流水按 tab 隔离，实测见上）。**复用同一 tab 走多条 AC 时**，全量流水无法区分归属，因此每条 AC 开始前**必须**重进页面清流水或记录 marker，取证只认 marker 之后的请求，并把 marker 值记进 `RESULT.md`
- **每条 AC 必须留证（落盘到 `tests/AC-NN/evidence/`）**：操作步骤 → 页面可见结果（`read_page` 文本或截图）→ 对应 XHR（Method + URL + 状态码 + 关键响应字段）；
  截图/录屏按 `AC-NN-序号-<中文描述>-原图/标注.<ext>`（文件名内容用中文，见 `doc-output-and-context.md`「证据文件命名」） 命名；该轮结论写入 `tests/AC-NN/RESULT.md`（通过/失败 + 复跑入口 + 环境 + marker）
- 🔴 **证据形式按优先级取：能录像就别截图，能截图就别只写字；截图必须标注（框住判定点 + 框边写字，未标注不算证据，`browser-playbook-evidence.md` §4.1）** —— 有 UI 可见结果的 AC 必须有录屏 / 动图或截图，抓包 / 日志只能补充；降级必须在 `RESULT.md` 写「证据降级：因 <原因> 无法录屏/截图，改用 <实际形式>」，没写理由 = 未留证。为什么：接口 200 而页面白屏、文案没翻译、按钮还是灰的，只有画面能暴露。全文（GIF 与录屏怎么选、关键帧连拍）→ `doc-output-and-context.md` §一「证据形式优先级」
  - 🔴 **UI 与接口都实测不了时**，可退到「走读证据」，但只限路径同一 / 入口不存在 / 失败分支三种情况，单独标状态、不得据此置 `[done]`，细则见 `browser-playbook-core.md` §6.1
- **抓包取证**：`read_network_requests` 按 `urlPattern` 过滤本次相关端点；需要响应体时用 `requestId` 二次读取；**结论必须有 XHR 或截图支撑，禁止凭页面观感臆断**
- **契约核对**：抓到的实际请求参数 / 响应字段（字段名、类型、枚举、分页结构）与 Step6 API 契约逐字段比对，不一致标 🔴Contract Misalignment 并写明哪一端偏离
- 🔴 **数值类 AC 必须做数据核对**：该 AC 的预期含具体数值 / 条数 / 聚合结果时，抓完 XHR **当场**按 **11.5** 核库对账，结论写进同一份 `RESULT.md`。只比对页面和 XHR **不算验证通过** —— 接口返回什么就显示什么，证明不了这个数是对的
- 🔴 **落库类 AC 必须做全量核对**：该 AC 的结果在库里留了痕（同步 / 迁移 / 批量写入 / 定时任务 / 权限可见性）时，除了用当前账号实机验证，**必须再按账号/租户分组核一次全量** —— 浏览器只看得见你登的那个账号，别的账号漏了、串了、重了，它一个都报不出来。**查出任何差异账号，即便当前账号正常，本条 AC 也不得判通过**
- **控制台**：`read_console_messages` 取 `onlyErrors`，任何 JS 报错一律记为缺陷
- **复跑说明落盘**：每条 AC 走完后，把该 AC 的环境 / 账号角色 / 前置数据 / 编号操作步骤 / 预期 XHR 写入 `tests/AC-NN/REPLAY.md`。Agent 实机验证轨**不写测试代码**（前端不写单测 / 组件测试），由 `REPLAY.md` 承担「可复跑」；但**产出过证据的脚本必须存进 `script/`**（fetch patch、标注 / 裁剪、解析、采样 —— scratchpad 不算存档，证据验收按 C7 判不通过），细则见 `evidence-acceptance.md` C7 与 `doc-output-and-context.md` §一「测试证据目录」


#### 🔴 并行执行（默认就并行）

- 🔴 **默认并行**：同账号 + 只读的 AC 一 AC 一 tab、并发 2–4（不超过 4）；**写操作 AC、有前后依赖的 AC 一律串行**（脏数据要能归因）；
  **每次工具调用显式带自己的 `tabId`**（不带 = 作用于前台标签 = 串扰）；每条 AC 走完立即关 tab。
  收益是消除等待（A 标签等接口时操作 B 标签），不是 CPU 并行；只有 11.4.1 的并行分组表写明「为什么只能串行」才串行。
  全文（实测能力边界、分组表、一 AC 一 tab 时免 marker）→ `browser-playbook-parallel.md` §12.0
- 🔴 **多账号用 CDP 隔离登录态，默认多实例（方案 A：独立端口 + 独立 `--user-data-dir`）**：同一浏览器所有 tab 共享 cookie；
  只换端口不换 profile 等于没隔离；登录必须人来做，所以「登一次能用多久」比省内存重要。全文（A / B 对比）→ `browser-playbook-tools-cdp.md` §2.4

#### 🔴 多浏览器 / 多会话并行：用例状态与窗口归属

多会话（主会话 + 子 agent）或多个浏览器实例同时跑时，会**静默**发生两件事：同一条 AC 被两个会话重复验、A 会话的操作打到 B 会话的窗口上。
解法是共享登记文件 `tests/.verify-state.json`（走 `scripts/verify_state.py`，锁文件防并发丢更新）。全文 → `browser-playbook-parallel.md` §12.1–§12.3。

- 🔴 **开始前 `claim`（登记会话 + 窗口标识），收尾 `finish`**；禁止「先跑完再补登记」
- 🔴 **一条 AC 同一时刻只能一个会话占用**（`验证中` 或 `修复中`）：被占且未超时就换一条，不许抢；僵死超 TTL（默认 20 分钟）才 `reclaim` 并记回收自谁
- 🔴 **每个会话只操作自己登记的窗口**，每次工具调用显式带自己的 `tabId`；窗口不共享、不借用
- 🔴 **只有 `通过` 回写 `[done]`**；`验证中` / `修复中` / `失败` / `部分` / `走读证据` / `跳过` 一律保持 `[open]`，`阻塞` 回写 `[blocked]`（`verify_state.py finish` 会打印该回写哪个）；11.3 已置 `[done]` 的 AC 实机结论不是「通过」时**退回 `[open]`**（状态枚举 `待验证 | 验证中 | 修复中 | 通过 | 失败 | 阻塞 | 部分 | 走读证据 | 跳过`）
  - 🔴 交付门禁对 `[open]` 与 `[blocked]` **同等拦截**；要放行只有 `[waived]` + 证据验收报告里的风险接受记录（`browser-playbook-parallel.md` §12.1）
- 🔴 **写操作 AC、有依赖的 AC 一律串行且各自单独 `claim`**

**子 agent 并行时**：派发子任务时就写死它的 `--session` 与独占的 `--window`，任务描述里明确「只碰这个窗口」；会话之间靠登记文件协调，不靠共享上下文。
🔴 **brief 必须逐条带上 `browser-playbook-parallel.md` §12.6「子 agent brief 必含项」**（断言清单进 NOTES、「无反应」真实点击、标注图逐张 Read 目检、证据晚于最后相关改动、401 自检、CDP 调用 ≤30s 超时、脚本进 `script/`）—— 那些规则本来就有，退回多是因为 brief 没要求、子 agent 不知道。

#### 🔴 写操作授权红线（每一次都要单独问）

> **「用户给了可用账号」不等于「写操作被授权」** —— 账号解决的是**能否登入**，不是**能否写**。

- **每一次**删除 / 修改 / 上传 / 分发 / 提交**都要单独问**，问的时候必须带上足够用户判断风险的信息：
  **动作 + 用哪个账号 + 具体对象 + 会写什么 + 是否可逆 + 影响面**
  - ❌ `需要执行删除操作，可以吗？`
  - ✅ `要用 qa_internal@x 删除素材「A-123」（该 client 下唯一一条 Approved），会真删库、不可逆，且 AC-18/AC-22 依赖它 —— 确认执行？`
- 授权**不跨条目、不跨会话继承**：上一条 AC 同意过，这一条要重新问
- 以下均**不构成**授权：「这是测试账号」「这条 AC 本来就是验删除的」「上一条你同意过」「步骤文档里写了」
- 🔴 **拿不准算不算写操作时，按写操作处理**（先问）。典型易误判：保存草稿、点「应用」、切换开关、拖拽排序、标记已读、触发重新生成

#### 异常态构造（标准手法）

页面天然只走得出正常态，loading / 5xx / 空数据基本造不出来。用内置浏览器的 `javascript_tool` 在**目标页面内临时 patch `window.fetch`**，**刷新即恢复、不落任何代码**（天然符合 L17：临时调试代码不得进仓）：

```js
// 造 500 错误态：验证前端错误文案是否英文友好、是否暴露原始技术信息（L16）
const _f = window.fetch;
window.fetch = (u, o) => String(u).includes('/creative/asset/page')
  ? Promise.resolve(new Response('{"code":500,"msg":"Internal Error"}',
      { status: 500, headers: { 'Content-Type': 'application/json' } }))
  : _f(u, o);

// 造空数据态：同样 patch，但返回 {"code":200,"data":{"list":[],"total":0}}，验证空状态插画/文案
// 造 loading 态：await new Promise(r => setTimeout(r, 3000)) 后再 _f(u, o)，验证骨架屏/loading 不闪烁不卡死
```

- 用完**必须刷新页面还原**，并在 `RESULT.md` 注明"该态由 fetch patch 构造"
- 权限不足态仍用**切换无权限账号**构造（patch 不能替代真实权限链路验证，见 L14）
- 响应式用 `resize_window`（mobile/tablet）验证

**自愈**：发现问题先改**业务代码**（非绕过），重跑 11.2 编译自愈确认无回归，再回本步复验；连续 2 轮未通过则停止，汇报清单请求人工介入。**边验边修的具体流程（状态流转 `验证中 → 修复中 → 验证中`、公共代码回归重验、影响面超界回退）见 11.4.2「执行规则」的「边验边修，不攒批」。**

### 11.4.3 验证报告

**产出物**：`.../Step 11-浏览器实机验证报告.md`

```
验证概要: 环境X | 冒烟 ✅ | 覆盖 AC X 条 | ✅X ⚠️X ❌X | 🔴契约偏差X | JS 报错X | 写操作X 次(已授权)

A.逐条验证: | AC-NN | 操作路径 | 页面结果 | XHR(Method+URL) | 状态码 | 响应关键字段 | 契约一致 | 结论 |

C.控制台错误: | 页面 | 错误信息 | 触发操作 |

```

- 截图/录屏存 **`tests/AC-NN/evidence/`**，命名 `AC-NN-序号-<中文描述>-原图/标注.<ext>`（文件名内容用中文，见 `doc-output-and-context.md`「证据文件命名」）；本报告是汇总，逐条明细仍在各 AC 的 `RESULT.md`
- **E 表必须写明"谁清、清没清"**，不能只给"清理建议"；未清理项由 Step13 交付前门禁复查，**存在未清理脏数据时不得判 PASS**
- 🔴 **F 表为强制收尾项（对应 L17）**：11.4 为构造异常态 / 排查问题常会临时改代码或加 `console.log`，本步结束必须**逐仓** `git status` + `git diff --stat` 确认无残留（前端常为多仓：宿主仓 + 嵌套独立仓，每个仓都要查），任一仓有残留必须先清理再出报告
- 🔴 **浏览器笔记回写（强制收尾项）**：把本轮新知道的回写进项目的页面级笔记（本工作区见 `AGENTS.md`「浏览器笔记与可复用脚本」）——入口路径、操作→XHR 对照、异常态构造方式、踩到的坑、用过的测试数据（**只记登录名，不记任何凭据**），并刷新该文件的验证日期。本轮跨需求复用过第二次的脚本，升级到 `scripts/` 并补齐用途/用法/依赖/最后跑通日期。**不回写等于下次重摸一遍**
- 收尾时生成 **`tests/README.md`** 索引：顶部「进场检查」小节 + `| AC-NN | 结论 | 用例 | 复跑入口(REPLAY/script) | 证据文件 |`
- 🔴 **收尾强制刷新看板（终版）**：`py scripts/verify_dashboard.py --dir <需求目录>` → 刷新 `<需求目录>/验证进度看板.html` 与外层 `docs/develop/index.html`；`tests/README.md` 顶部加一行实时看板链接（服务模式 `http://127.0.0.1:8787/index.html#/<URL 编码后的需求目录>`，见 SKILL.md 执行指令 1.5）。每条 AC 的 `claim` / `fix` / `finish` / `final` 登记时 `verify_state.py` 已自动刷新；收尾再跑一次是为了刷新证据清单、RESULT 摘要等快照。看板是辅助产物，缺失/过旧只提示不判 FAIL（见 `doc-output-and-context.md`「验证进度看板」）
- 🔴 **G 表与 `tests/.verify-state.json` 必须一致**：收尾时不得残留「验证中」（所有 AC 要么已 `finish`，要么在报告里注明为何中断）；有残留「验证中」视为本步未收尾
- 本报告是 Step12 AI Review 契约一致性维度的**证据来源**

**步骤偏差回写**：实际操作与步骤文档不一致时（多一步、换了入口、数据不满足），必须回写 `Step 11-浏览器验证步骤.md`，保持两份文档一致，便于测试同学按同一份步骤复跑。

**→门控**：🔴 **阻塞** —— 汇报报告路径与验证结论 + **E 表脏数据是否已清理** + **F 表逐仓无残留调试代码** + **G 表无残留「验证中」**（多会话并行时）+ **看板已刷新** → **暂停等确认** → 进入 Step12

> 🔴 **阻塞门控**：必须**暂停等待用户明确确认**，未获通过禁止进入下一步。
> 之所以阻塞：实机验证可能**产生了脏数据、动过真实账号**；本步要确认脏数据已清理、临时调试代码无残留，这些都是不可逆或会外溢的后果。

> **禁止 git 提交（强制）**：本步产出只写入工作区，不得 `git add/commit`。

## 11.5 数据核对（只读 SQL 取证）

> **何时做**：①AC 的预期含**具体数值 / 条数 / 聚合结果** —— 抓完 XHR **当场**核库；
> ②🔴 **这条 AC 的结果在库里留了痕**（同步 / 迁移 / 批量写入 / 定时任务 / MQ 消费 / 权限可见性 / 列表计数）—— 实机验证只是**单账号抽样**，必须补一次**按账号/租户分组**的全量核对，否则「你登的那个账号正常」会被当成「所有账号正常」；
> 实机验证被跳过（定时任务 / MQ 消费 / 批处理）但仍需验证落库结果时，独立执行本节。
> **只比对 XHR 不算验证通过**：接口返回什么就是什么，证明不了这个数是对的。

🔴 **完整规则见 `references/data-reconciliation.md`**（只读门禁、可用连接、绩效查询硬约束、
SQL 必须从既有 mapper 推导、口径对齐、取证落盘、对不上怎么逐层二分、禁止事项）。
**本节的只读门禁是强制前置，无例外** —— 开查之前先把那份读完。

**→门控**：数据核对结论写入各 AC 的 `RESULT.md`；11.4 有执行时在其报告中增加「H.数据核对汇总」表（G 表已是用例状态与窗口归属），11.4 被跳过时单独出《Step 11-数据核对报告.md》

## 11.6 证据终验（终验，不重跑浏览器）

> **何时做**：本需求所有 AC 都跑完、证据都采集完之后（11.4 收尾 + 11.5 数据核对都完成）才进本步。
> **只做一件事**：核对**证据内容是否支撑它的结论**。不重跑浏览器、不重跑测试、不重新抓包。
> 解决的正是「有证据文件」≠「证据真能证明这条 AC」——截图是拍了，但画面里根本没有 AC 要的那个值。

### 逐条核对什么（每条 AC 都要看，不许跳）

| 维度 | 要看出来的东西 |
|---|---|
| 存在性 | `evidence/` 非空、文件能打开、非 0 字节、文件名与报告 D/E 表对得上（**未留证 = 未测**） |
| 证据↔结论 | 截图/录屏里**真能看到** AC 声称的结果；抓包/日志的值与 `RESULT.md` 写的一致，不是「看起来像」 |
| 证据↔AC | 这份证据确实是这条 AC 的、是这个环境/账号/时间的（别拿别的 AC 的截图顶） |
| 具体值 | AC 预期含具体数值/文案/条数时，**证据里必须能读到那个值**（如「Views at 50%」就要求截图里真有 50%） |
| 内部一致 | 同类 AC 的证据不互相矛盾；`RESULT.md` 结论与 Checklist 回写口径一致 |
| 降级审查 | 走了「走读证据」/「部分」/模拟数据的，降级理由是否写清、有没有被当成「通过」用 |

### 怎么做（登记 + 判定）

```bash
# 0) 登记文件不存在 / 为空时先建（否则 final 直接停）：按已有 RESULT.md 回填最省事
py scripts/verify_state.py init --dir <需求目录> --from-result
# 1) 认领终验（可批量认领，但只能批量置「终验中」）
py scripts/verify_state.py final --dir <需求目录> --ac ALL --session s1 --status 终验中
# 2) 逐条出结论（每条都得真看过证据，不许批量打钩）
py scripts/verify_state.py final --dir <需求目录> --ac AC-01 --session s1 --status 终验通过 --note "截图里能读到 50%"
py scripts/verify_state.py final --dir <需求目录> --ac AC-07 --session s1 --status 终验不通过 --note "截图只有列名，没有该行数值"
```

- 终验状态：`未终验` → `终验中` → `终验通过` / `终验不通过` / `豁免`，**独立于验证状态、不改变 `status`**
  - `豁免` **仅限用户明确放行**（证据不足仍收口）：Checklist 置 `[waived]`（不是 `[done]`），`--note` 必写放行范围 + 用户原话 + 风险，证据验收报告要有点名该 AC 的「风险接受记录」；AI 不得自行豁免
- **只有已完结的 AC 才能终验**（待验证/验证中/修复中会被跳过并提示）
- 🔴 **终验通过 ≠ 可以改 Checklist**：Checklist 仍只按 `status` 回写（只有「通过」→ `[done]`），终验是另一条线索
- 🔴 **终验不通过按「发现问题」处理**（接 11.4.2 边验边修同一条链）：先看证据缺什么 → 补证据 / 修业务代码 → 必要时才重新做实机复验 → 再重新终验
- 🔴 **已完结的 AC 要重验/改判，必须带 `--force`**，且顺序是「先 claim 再 finish」：
  `py scripts/verify_state.py claim --dir <需求目录> --ac AC-01 --session s1 --window tab:1234 --force`
  → 状态回到「验证中」→ 改完再 `py scripts/verify_state.py finish --dir <需求目录> --ac AC-01 --session s1 --status 通过`。
  两个必知点：① `claim` 对 `通过/失败/阻塞/部分/走读证据/跳过` 这类已完结状态不加 `--force` 会**拒绝**（exit 1）；
  ② `finish` **不认 `--force` 改状态** —— 它要求当前状态是「验证中」，对已完结状态直接拒绝，别照抄 `finish … --force`。
- 改判已终验的结论必须 `--force`（结论是「有人真看过证据」才下的，不能被随手冲掉）
- 看板实时显示终验：明细「终验」列 + 按终验状态筛选 + 总览「证据终验」卡片 + 风险（不通过=高风险，「已完结但未终验」聚合为低风险）

**→门控**：🔴 **阻塞** —— 汇报「已完结 X / 终验通过 Y / 不通过 Z / 未终验 W」+ 每条不通过的**缺什么证据** + 看板已刷新 → **暂停等确认** → 进入 Step12。
> 未终验的必须在汇报里列出来（可带条件放行，但不能装作没有）；**存在「终验不通过」时禁止进入 Step12**。

**本步总产出物**：全部 Pass 的后端单测 + 编译通过模块 + 《Step 11-业务逻辑自检报告》 +（可选）《Step 11-浏览器验证步骤》+《Step 11-浏览器实机验证报告》 +（涉及数据核对时）各 AC 的 `{AC-NN}-db-query.sql` / `{AC-NN}-db-result.txt`（命名见 `data-reconciliation.md` §7）与 `RESULT.md` 的「数据核对」节 + **`tests/AC-NN/`（每 AC 的用例 / `script/` 或 `REPLAY.md` / 证据 / RESULT）+ `tests/README.md` 索引** + **终验记录**（`tests/.verify-state.json` 的 `final_status` 与看板「终验」列）**（前端不写测试代码）
