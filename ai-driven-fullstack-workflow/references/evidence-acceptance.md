# 证据验收（验收测试专员）

> **时机**：交付门禁步（fullstack Step 13 / backend 第十二步），全局一致性审查 A ~ E 做完之后、请用户确认提交之前。
> **产出**：`Step 13-证据验收报告.md`（fullstack）/ `Step 12-证据验收报告.md`（backend），与其他产出物同目录。
> **职责**：以验收测试专员身份，**判定每条 AC 的证据能不能通过验收** —— 结论只有「验收通过 / 验收不通过」两种。
> **门禁**：只有「验收通过」的 AC 才能置 `[done]`；「验收不通过」的 AC 必须补证 / 重测，或由用户明确放行。`validate_step.py` 最终步会检查本报告。

## 一、为什么要单独一个角色

代码、单测、证据、`RESULT.md` 结论、自检报告、AI Review **全是同一个 AI 产出的**。
它们共享同一套误解：需求看错了，证据也会按错的那样拍，结论照样写「通过」。
前面所有审查问的都是「文档之间是否自洽」，没人问过「**这份证据真的证明了这条 AC 吗**」。

验收测试专员是整条流程里**第一个只看证据原件、不信任何结论**的角色：它不评价代码，只回答一个问题 —— **凭这些证据，这条 AC 能不能验收通过？**

真实发生过的三类问题（均出自 CP-58252，前面的审查全部放过）：
- 整页截图里判定点只占一小条，不看文字说明根本看不出证明了什么
- 页面内存补丁没清，补丁构造的空表被写成了「真实数据」
- 返工改了版式，证据却还有返工前拍的

## 二、怎么做

### 执行者

- 🔴 **用独立 subagent 执行**，不继承开发会话上下文。主会话只负责派发与汇总，**不得自己代做**
- subagent 拿到的输入：Checklist（GWT 原文）+ `tests/AC-NN/` 目录路径 + 本文件；**不给**自检报告、AI Review、一致性报告

### 两遍法

**第一遍：盲审（不读 `RESULT.md`）**
只读 `case.md`、`REPLAY.md` / `script/`、`evidence/` 原件。对每条 AC：
1. 把 Then 拆成**单个可判定的断言**（一个断言一行）
2. 对每个断言，在证据里找**能直接指认的依据**（哪张图的哪个位置 / 哪个响应字段 / 哪条单测断言）
3. 找不到就记「无证据」，**不得**用「应该是」「代码里写了」补

**第二遍：对账（再读 `RESULT.md`）**
拿第一遍的判断和 `RESULT.md` 的结论逐条比，找**结论比证据说得多**的地方：证据只证了一部分却写「通过」、构造的写成实测、走读的写成通过。

### 检查点（逐 AC 七项，任一不过即「验收不通过」）

| # | 检查点 | 不过的典型 |
|---|---|---|
| C1 | **逐断言对应**：Then 的每个断言都有证据指认；机器可读证据须**验内容**（字段值 / `pass` / 前后对比 / 计数），**禁止**只因 `evidence/` 里有文件或截图存在就过 | Then 有 3 个断言，证据只覆盖 2 个；或 JSON 里 `pass:false` / `missing` 非空却写「有文件=通过」 |
| C2 | **看得出**：不看文字解释，能从图中指出通过依据（标注图规则见 `browser-verification-playbook.md` §4.1） | 只有整页截图、判定点没框 |
| C3 | **证据类型标对**：实测 / 构造（内存补丁）/ 走读证据 三类不混（§4.2、§6.1） | 补丁在场时的结果写成真实数据 |
| C4 | **可追溯**：环境、账号（只写身份，不写凭据）、数据对象、日期范围、接口与状态码齐 | 看不出是哪个素材、哪段日期 |
| C5 | **时效**：证据产生于最后一次影响该 AC 的代码改动之后 | 返工前拍的图证明返工后的行为 |
| C6 | **走读证据在边界内**：只限「路径同一 / 入口不存在 / 失败分支」，附 `file:line` 与「判断错了会表现为什么」 | 用走读证明布局或上游数据行为 |
| C7 | **原件未被篡改**：标注图另存（`-annotated`），原图保留；单测证据可复跑；按约定删除的原件（如真实客户下载文件）须留解析脚本 + 去标识化逐行产物 + md5，能复算 | 在原图上直接画框覆盖；文件删了只剩一段摘要 |

> 🔴 **测试方开测前就按这七项准备证据**：`browser-verification-playbook.md` §4.0「首测即过」把每个检查点翻成了测前动作。验收员是最后一道，不是第一道。

C5 的取证方式：对比证据文件时间与 `git log -1 --format=%ci -- <该 AC 涉及文件>`（未提交时用文件修改时间）。

### 判定

| 判定 | 条件 | 后续 |
|---|---|---|
| **验收通过** | Then 的每个断言都有可指认的证据，C1 ~ C7 全过 | AC 可置 `[done]` |
| **验收不通过** | 任一断言无证据，或 C1 ~ C7 任一不过 | AC 保持 / 退回 `[open]`，按原因处理（下表） |

「验收不通过」必须写明原因类别，决定怎么处理：

| 原因 | 对应检查点 | 处理 |
|---|---|---|
| **缺证** —— 结论可能对，但证据缺 / 看不清 / 追溯信息不全 | C1（部分断言无证据）、C2、C4、C7 | 补证据后复验；补不了交用户放行 |
| **证据不实** —— 证据与结论对不上、类型标错、已过期、走读越界 | C1（证据与断言相反）、C3、C5、C6 | 🔴 重测或改结论，不得仅靠补材料翻案 |

拿不准时判「验收不通过」。**宁可多补一次证，不可放过一个假通过。**

## 三、产出格式

```
# Step <N> - 证据验收报告（<需求号>）

验收概要: AC 总 X | 验收通过 X | 验收不通过 X（缺证 X / 证据不实 X）| 执行者: 独立 subagent（盲审 + 对账）

| AC-NN | 断言数 | C1 | C2 | C3 | C4 | C5 | C6 | C7 | 判定 | 原因 | 问题与处理 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| AC-01 | 4 | ✅ | ✅ | ✅ | ✅ | ✅ | - | ✅ | 验收通过 | - | - |
| AC-05 | 2 | ✅ | ❌ | ✅ | ✅ | ✅ | - | ✅ | 验收不通过 | 缺证 | 只有整页图，补标注图后复验 |

## 对账发现（结论比证据说得多）
| AC-NN | RESULT.md 写的 | 证据实际能证的 | 处理 |

## 修复追溯
| AC-NN | 第几轮 | 改了什么 | 复验判定 |
```

- 每条 AC 一行，**行首必须是 `| AC-NN |`**（门禁脚本按此识别）
- 「判定」列只能填 `验收通过` / `验收不通过`；不通过时「原因」填 `缺证` / `证据不实`
- 不适用的检查点填 `-`（如无走读证据时 C6）
- 🔴 **复验轮次追加在同一文件时，门禁按每条 AC 最后出现的 `| AC-NN |` 行取判定**：追加的轮次小节里，凡以 `| AC-NN |` 开头的行都必须是该 AC **当前**的判定（旧轮次结论写进「修复追溯」或正文，别再起一行 `| AC-NN |`）；复验通过后若前面小节还有不通过的 `| AC-NN |` 行，要在其后补一行通过的（CP-58252 因此多失败两次）
- 正文（含 Checklist 的「状态回写」行）里别把状态标记和 AC 号写在同一行（如「AC-17 … 保持 `[open]`」）—— 门禁逐行找「`[open]` + AC-NN」，会把说明文字当成未回写
- 用户放行（证据不足仍收口）：判定列保持「验收不通过」，另起「风险接受记录（AC-NN）」段写放行范围、用户原话、风险；Checklist 置 `[waived]`（不是 `[done]`），`verify_state.py final --status 豁免 --note …`

## 四、修复循环

1. 主会话按「问题与处理」补证据 / 重测 / 改结论
2. 只对改动过的 AC **再派一次 subagent 复验**（同样两遍法），回填「修复追溯」
3. 最多 2 轮；第 2 轮仍「验收不通过」→ 列清单请用户放行或介入，不得自行改判

## 五、subagent 派发模板

```
你是验收测试专员。你的唯一职责：判定每条 AC 的证据能不能通过验收（验收通过 / 验收不通过）。
你不是来确认它通过的；证据不能让你独立得出「通过」，就判不通过。

输入：
- Checklist：<路径>（只用 GWT 原文）
- 证据根目录：<路径>/tests/
- 规则：<skill>/references/evidence-acceptance.md（按其中「两遍法」「C1~C7」「判定」执行）

步骤：
1. 第一遍盲审：不要打开任何 RESULT.md。逐 AC 拆 Then 断言，在 evidence/ 原件里找依据；图片要真的打开看
2. 第二遍对账：再读 RESULT.md，找结论比证据说得多的地方
3. 按「三、产出格式」输出报告全文

禁止：读自检报告 / AI Review / 一致性报告；修改任何证据文件；替开发补证据。
```
