### L2. EXISTS 子查询必须含软删条件（第五步）
| 项 | 内容 |
|---|---|

### L4. 新增接口一切随大流：method、结构、命名都先 grep 现状（第六步）
| 项 | 内容 |
|---|---|
| **触发条件** | 新增任何接口（尤其筛选 / 分页列表 / 详情等通用型） |
| **约束动作** | ①**HTTP method**：先 grep 现有分布，少数派（<10%）不要用。②**返回结构 / 字段命名**：先 grep 同类接口，能复用现有 View 就不新建。③二者都以「项目现状」为准，不以个人偏好或 RESTful 教条为准 |
| **示例** | `@PutMapping → 9`、`@DeleteMapping → 6`、`@PostMapping → 130+` → 写操作一律 POST；filter-options 直接参考 `ShareFilterOptionsView` |
| **搜索词** | `getFilters` / `filterOptions` / `getAssociatedProducts` / `getAppliedProfiles` 等 |
| **为什么** | 风格不一致的代价是长期的：调用方要记两套约定，后来者不知道该跟哪个 |
| **来源** | CP-52023（原 L4 + L5，2026-09-29 合并 —— 两者都是「先看现状再动手」的同一件事） |

### L7. 真源一致性：写之前先 grep 现状，写之后反查全仓（第九步→第十步 + Step12）
| 项 | 内容 |
|---|---|
| **触发条件** | 命中以下任一场景：①涉及**枚举 → DB 列**的映射字段，且有多个候选属性（aiName/dbName/displayName/code）；②字段适用性**矩阵/映射表/常量字典**在多处维护；③编写 **MyBatis Mapper XML**（表名、字段名、key） |
| **共同根因** | 同一个事实在代码里存了**两份**，而没有任何机制保证它们相等。两份一开始是对的，之后只改了一处——**不报错、不红灯，只是从某一刻起结果开始不对** |
| **约束动作** | 🔴 **写之前先 grep 现状**（别凭名字猜）＋ 🔴 **写之后全仓反查一致性** ＋ 🔴 **禁止维护副本**。三个场景的落法：<br>**①枚举存储值**：grep 既有写入代码（`grep set<FieldName>(`）确认实际存的是哪个属性，读取/展示侧对齐写入侧<br>**②单一真源**：枚举即真源，禁止在 Service 维护私有矩阵；查询统一走 `Enum.getByCode(xxx)`；要缓存就从枚举派生，不手写；XML 的 key 与 `getCode()` 对齐<br>**③XML 表名**：写前 grep 实际表名（DDL / 已有 XML / Entity `@TableName`），写完全仓 grep 一遍，不一致立即修正 |
| **检查** | ①本次改动涉及的"同一事实"在几个地方存着？②每一处是**派生**出来的，还是**另抄**了一份？③写入侧与读取侧用的是同一个属性吗？④全仓 grep 过一遍没有？⑤写入侧本身就不一致时**暂停问用户**，不要自己选一个 |
| **来源** | 均来自 CP-52023，三处表现：<br>· `ad_type` 误用 `dbName`、实际存 `aiName`（对齐 `AssetManager.setAdType(adType.getAiName())`），全链路返工<br>· Service 私有矩阵 key `"WalmartSB"` 与枚举 `aiName` `"SB"` 漂移，匹配失败<br>· XML 全局写 `campaign_asset`、实际表名 `creative_asset`，53 处错误<br>**合并说明（2026-10-02）**：原为三条（本就按「真源族」1 条计入膨胀控制），合并为本条；原编号**空缺不复用** |

## 五、编码步骤经验

### L11. Controller 入参白名单 + 互斥必填校验（第六步 + 第十步）
| 项 | 内容 |
|---|---|
| **触发条件** | Controller 入参含枚举值字段或互斥必填字段 |
| **约束动作** | Controller 层：①枚举值白名单校验，非法值返回 `ResultVO.fail`；②互斥必填空值校验；③不污染 Service |
| **来源** | CP-52023 groupMode 未校验合法值、detail 端点 uuids/productKey 都空 |

### L13. 面向用户的文案必须英文（第六步 + 第十步 + Step12）
| 项 | 内容 |
|---|---|
| **触发条件** | Controller/Handler 返回给前端的 `ResultVO.fail(msg)`、抛出的异常 message、任何用户可见的校验提示文案 |
| **约束动作** | 所有返回给客户端的文案一律英文（如 `Invalid pageSize, must be >= 1`）；代码注释可保留中文，但 msg 字符串禁止中文。第六步 API 文档的错误码/提示示例同样用英文 |
| **自检时机** | 第六步 API 文档错误响应示例；第十步 Controller/Handler 校验编码后；Step12 维度 E/F |
| **检查** | grep `fail\("` 与 `throw new .*Exception\("` 的 msg 是否含中文（`[\x{4e00}-\x{9fff}]`），有则改英文 |
| **来源** | CP-52023 orderBy/groupMode/pageSize 等校验报错原为中文，前端可见文案要求只能英文 |

### L14. 须注入 visibleUserIds + profile 数据权限（第十步）
| 项 | 内容 |
|---|---|
| **触发条件** | 列表/详情/写/筛选项涉及带 `profile_id`（或 `create_by`）的业务表，且项目有 `queryAssetDataPermission` |
| **约束动作** | 调权限拿 `visibleUserIds` + 授权 `profileIds`：①`visibleUserIds` 空 → full permission，两维都不强制；②非空 → 列表/筛选项同时 `create_by IN (visibleUserIds)` 与 `profile_id IN (授权 profiles)`；③前端未传 profileIds → 注入授权集，传了 → 与授权集取交集；④写操作先按授权 profile 剔 uuid。禁止仅 `client_id` 隔离 |
| **自检时机** | 第十步 Handler 编码后；Step12 维度 E/F |
| **检查** | ①未传 profile 时是否仍注入授权集？②`visibleUserIds` 非空时 create_by 是否过滤？③写操作是否剔无权限 uuid？④list/detail/write/filter 口径一致？ |
| **来源** | CP-52023 creative-asset 初版 page 未注入 profile/visibleUser，前端不传可越权看全 client |

### L17. 前端测试 / 调试代码不得进仓（第十步 + Step12 + Step13）
| 项 | 内容 |
|---|---|
| **触发条件** | 前端编码与联调过程中加过任何"只为看一眼"的东西 |
| **约束动作** | 交付前逐项 grep 清除：`console.log` / `debugger`、临时 mock 数据与写死的 id（profileId / clientId / 测试账号）、指向本地或测试环境的 URL、被注释掉的旧接口调用、为绕过报错临时加的 `try{}catch{}` 空吞、`// TODO 记得改回来`。**前端不写单元测试（用户约定），所以没有测试会替你发现这些** |

## 七、流程与验证经验

### L18. 门禁规则必须为每条执行路径留下可满足的产出形式（流程设计 + 各步收尾）
| 项 | 内容 |
|---|---|
| **触发条件** | 设计或修改任何"缺 X 即判不合格"的强制门禁（产出物齐全性、证据归档、覆盖率反查等） |
| **约束动作** | 定门禁时逐条走查**所有执行路径**：每条路径都要有**能真实产出**的形式。某路径按约定产不出该形式（如"前端不写测试代码"→ 永远产不出 `script/`），必须**给等价替代**（如 `REPLAY.md`）或**显式豁免**，禁止留下"必然不达标"的条款 |
| **为什么** | 必然判 fail 的门禁只有两种下场：要么每次都 fail 被当噪音忽略，要么被整体跳过——**两种都等于门禁失效**，比没有门禁更糟（给了虚假的安全感） |
| **自检时机** | 新增/修改门禁条款时；Step11/12 发现某门禁"从来没人满足过"时 |
| **检查** | ①列出所有执行路径（自动化/人工、A/B/C 分流档）；②每条路径能产出该形式吗？③产不出的有等价替代或显式豁免吗？④替代形式同样可被客观核验吗？ |
| **补充一（2026-09-29）** | 🔴 **门禁的判定规则通常是近似的（正则 / 目录存在性），必须假设它会误判两个方向**：①**漏检** —— `AC-{n}` 构造的正则匹配不到补零的 `AC-01`，前 9 条重复检测长期失效；②**误放行** —— 正文写「在确认前不得判 PASS」，其中的 `PASS` 落在 `R-7` 之后被当成结论，一条明确未闭环的回归项被判通过。**误放行比不检查更危险**，因为它给出虚假的绿灯。收到门禁结果时先问「它是真的验了，还是只是匹配到了字符串」；发现误判**修规则，不要改文档措辞去迎合规则** |
| **补充二（2026-09-29）** | 🔴 **门禁只有「过 / 不过」两态时，会逼着人去改措辞迎合规则**。实例：`R-7` 依赖仓库外资产（Loki/Grafana 告警规则），流程无法自证；人工决定风险接受放行，但如实描述「风险接受」的句子绕不开「非 / 若 / 未」—— 而这些正是否定守卫词，连改 3 次措辞都过不了。**连续两次改的是措辞而非事实，就是规则缺一态的信号**。对策：加第三态 `WAIVED`（须配书面「风险接受记录」，否则仍 FAIL），且豁免项**单列显形、不计入已验证**。另：**改完门禁脚本必须用已知样例自测每一态，绿灯也要验** —— 本次新增正则的 `\b` 被 heredoc 吞成退格符，函数永远返回 False，却因另一行巧合含结论词而跟着放行，第一次跑出来是假绿灯 |
| **来源** | 本仓 skill 演进：`tests/AC-NN/script/` 对人工验证类 AC 必然为空，导致"四件齐全"门禁架空 → 改为 `script/` 或 `REPLAY.md` 二选一 |

### L19. 后端日志须可被检索与归因（第十步 + Step11.4 + Step12）
| 项 | 内容 |
|---|---|
| **触发条件** | 写任何 `log.info/warn/error`，尤其是 catch / 兜底 / 降级分支 |
| **约束动作** | ①每条业务日志带**可定位业务键**（账号 / 批次 / 对象 id），无键的日志在日志平台等于噪音 ②🔴 **兜底与降级路径禁止把不同根因塌缩成同一句固定文案**，必须带出最内层 cause 的「类名: message」并限长后落库/落日志 ③异常**作为参数**传 logger（`log.error("...{}", id, e)`），禁止 `+ e.getMessage()` —— 后者丢掉整条 `Caused by` ④关键短语写成**固定可搜串**，别把变量拼进关键词 ⑤批量操作收尾打一行**计数型总结**；同批次带统一前缀标识以便串联整条链路 ⑥预期内失败用 WARN 不打堆栈，真异常才 ERROR 带堆栈 ⑦**永不打印凭据**与带签名的 URL |
| **自检时机** | 第十步每写完一个 catch / 降级分支即自检；Step11.4 实测排查时回看「日志是否够用」 |
| **检查** | ①只凭一个业务 id，能否在日志平台搜到该行并看懂发生了什么？②不同根因的失败在日志里**能否区分**？③catch 分支有没有把 cause 丢掉？④有没有打印 token / 密钥 / 预签名 URL？ |
| **来源** | CP-57337：`AopHandler` 把所有异常吞成 `"Touch hystrix fallBack!"`，11 条失败据此被误判为「全部上游未授权」，逐条翻日志后实际只有 3 条是 |

### L20. 实机验证：账号要选对，浏览器操作只读（Step11.4）
| 项 | 内容 |
|---|---|
| **触发条件** | 需要开浏览器做实机验证、或需要挑选验证账号时 |
| **约束动作** | ①🔴 **浏览器操作默认只读** —— 只浏览 / 筛选 / 翻页 / 切账号 / 截图 / 抓包；**禁止删除、修改、上传、分发、改名、提交任何表单**。唯一例外是用户对**该具体动作**单独授权，且授权**不跨条目、不跨会话继承** ②🔴 **默认只用内部账号** —— 测试库常含真实客户数据，且**数据最丰富的客户往往正是真客户**；挑账号先按内部域名过滤。内部确实没有所需数据时，**须用户在本次任务里明确同意**才可用真实客户账号：全程只读、截图裁掉无关客户数据、文档标注「真实客户账号，用户 YYYY-MM-DD 同意」 ③🔴 **超管验不了否定型验收** —— 「无权限看不到」「跨客户不可见」必须用受限普通账号，超管天然可见，结果是**假绿灯**，比 NOT_RUN 更危险 ④查账号表**只取身份与权限列**，**禁读** `pwd`/`salt`/`token` 等凭据列，且不得写进任何文档 ⑤**AI 不代输凭据**，登录由用户完成 ⑥找账号**先定数据、再按平台账号库映射到用户**（各平台库表不同，见 playbook §10），两类账号都找不到时**如实记 NOT_RUN 并写明缺什么数据、查过哪些库表**，禁止用超管凑数 |
| **自检时机** | 写《浏览器验证步骤》文档时（账号一节）；每次切账号前；每次要点一个不确定是否写数据的控件前 |
| **检查** | ①这个账号是内部的还是客户的？②这条 AC 是肯定型还是否定型？③本条涉及的写操作拿到**单独**授权了吗？④证据截图里有没有客户 PII？ |
| **补充（2026-09-29）** | 🔴 **「用户给了可用账号」不等于「写操作被授权」**。账号解决的是能否登入，不是能否写。每一次删除/修改/上传/分发/提交**都要单独问**，问的时候必须带齐**动作 + 账号 + 具体对象 + 会写什么 + 是否可逆 + 影响面**，否则用户无从判断风险。「这是测试账号」「测试环境写坏了无所谓」「这条 AC 本来就需要写」「上一条你同意过」「你说了帮我验证」**全都不构成授权**。只要没有明确的「可以」，就当作没授权；拿不准算不算写操作时，按写操作处理 |
| **补充（2026-10-01）** | 🔴 **截图证据必须让人一眼看出判定点**：整页截图配一张「裁剪 + 放大 + 标注」版 —— 框出判定点，**每个框边贴「编号 + 文字说明」**（只有框和序号不够，那逼着复核者来回对照），图顶再写一行这条 AC 验什么；原图保留、标注图带 `-annotated` 后缀并在 `RESULT.md` 登记。🔴 **说明文字过长会被静默截断、图却照样生成**，所以一条说明只讲一个判定点、过长显式断行，并且**产出图必须自己打开看过**才算证据。判据：不看文字解释，审阅者能否从图里指出通过依据？细则见 playbook §4.1 |
| **补充（2026-10-01）·内存补丁** | 🔴 **页面内存补丁用完立即整页刷新清除**；任何「真实数据」结论落盘前先读补丁标记确认已失效，补丁在场时得到的结果只能写「构造」。补丁首次未命中不代表没装上（组件可能读缓存），未命中也要先刷新清掉。细则见 playbook §4.2 |
| **补充（2026-10-01）·走读证据** | 实测不了时可用代码走读作**降级证据**，但只限：①与已实测场景路径同一 ②入口不存在（应改写 AC / 标不适用）③浏览器构造不了的失败分支（以单测为主）。**不能**替代外部数据行为、视觉布局、权限否定型验收。状态单独标「走读证据」，附 `file:line` 与「判断错了会表现为什么」，AC 保持 `[open]` 交用户放行。细则见 playbook §6.1 |
| **补充（2026-10-01）·证据验收** | 🔴 交付门禁前由**独立 subagent 以验收测试专员身份**做证据验收：先盲审（不读 `RESULT.md`，只看证据原件、逐断言找依据），再对账（找结论比证据说得多的地方），逐 AC **判定证据能不能通过验收**（验收通过 / 验收不通过），只有验收通过的 AC 才能置 `[done]`。主会话不得代做。细则见 `references/evidence-acceptance.md` |
| **补充（2026-10-01）·点击落点** | 🔴 真实鼠标点击点的是坐标：每次点击前用 `elementFromPoint` 核对落点就是目标（或其后代），对不上不点；禁止纯坐标点击；抽屉 / 弹窗先轮询到状态稳定再点。点错后先确认有没有触发写操作再如实报告。细则见 playbook §3 第 4 条 |
| **补充（2026-10-02）·找账号 / 换账号 / 页面可见** | ①缺数据的 AC 反着找：AC 要什么数据 → 业务库里找到对象拿 profileId（DSP 为 advertiserId） → 平台账号库映射到用户 → 按「内部优先、客户须同意」挑人后报给用户登录。不同平台账号库表不同（Amazon / DSP 单独库 / Walmart），首用先查 `INFORMATION_SCHEMA` 核实列名；🔴 只列身份与权限列、禁止 `SELECT *`，别对大表做无条件聚合（会堵死没有超时的 MCP） ②换账号登录后先核对身份再取证、整页刷新清掉上个账号的缓存，逐 AC 记录所用账号 ③🔴 CDP 驱动前与截图前先确认 `document.visibilityState === 'visible'`，hidden 时页面被节流、操作不推进，易误判为代码 bug。细则见 playbook §10、§3 第 5 条 |
| **补充（2026-10-02）·提速** | 慢的大头是返工、一步一调用、大列表翻页、等用户。🔴 证据当场采齐（时间 / 身份 / URL / 请求体 + HTTP 状态码 / 筛选状态，后端启动时间与前端文件时间进场即记）；🔴 请用户登录前先在库里预演该账号会看到的数据（含平台 / profile 配置不为空）；一条路径一个带断言的脚本；按排序规则算页码直接跳；Chrome 带防节流开关、被遮挡时最小化再恢复；验收 subagent 与下一条测试并行。细则见 playbook §11 |
| **来源** | CP-57337 Step11.4：素材最多的 5 个客户，超管全部是真实客户账号；全库内部超管只有 3 个且素材类型不全 |

> 📖 **操作细则见 `references/browser-verification-playbook.md`** —— 工具选型、Step 0 数据指纹、驱动 UI 的五个高频坑、取证的 context 成本、以及 FAIL / BLOCKED / PARTIAL 的判定区别。

### L21. 交付前必须反查 AC 是否仍描述当前行为（Step13）
| 项 | 内容 |
|---|---|
| **触发条件** | 交付收尾；或实现过程中**有意改变了某个既有行为**（含为修缺陷而改） |
| **约束动作** | 逐条回读 Checklist：这条 AC 描述的，还是代码现在真正做的事吗？实现演进后**AC 会悄悄过期**——它不会报错，测试也不会红，只是从此描述了一个不存在的行为。发现过期立即改写 AC 并注明「原文描述的是 X 时期的行为，因 Y 改为 Z」 |
| **为什么** | AC 是验收与回归的唯一基准。过期的 AC 有两种害处：照它验收会把**正确实现判成 fail**；照它回归会**长期保护一个已经废弃的行为** |
| **自检时机** | Step13 全局一致性审查；以及任何一次「我们决定改掉原来的做法」之后 |
| **检查** | ①本次是否有「故意改变既有行为」的改动？②受影响的 AC 找出来了吗？③改写后是否注明了原文、变更原因与时间？ |
| **来源** | CP-57339：AC-31 原文写「素材分析服务不可用时**整批中断**并在次日恢复」，而实现已改为「单条跳过、其余继续」——AC 描述的正是被我们刻意改掉的行为，直到交付前逐条回读才发现 |

## 八、自进化机制（CRITICAL）

**触发时机**：①人工 review 反馈通用问题；②AI 自检发现通用不规范点；③Step12 AI Review 发现可复用经验。

🔴 **完整规则见 `references/lesson-harvest.md`** —— 准入四问（代价闸 / 抹名测试 / 落点选择 / 动作化）、
查重并入、容量与淘汰、提名门控、写入规范。执行经验沉淀前必读，别只照下面三条要点做。

三条要点：

1. **默认结论是「本次无新增经验」** —— 没有实际发生的损失就没有条目，禁止预测性立法
2. **经验不一定落在本文件** —— 落点由「执行到它该生效的那一刻，AI 正在读哪个文件」决定：
   浏览器手法进 `browser-verification-playbook.md`、检查项进 `bug-hunting-checklist.md`、
   某步做法进该步 `step-NN-*.md`；本文件只收**跨步骤的原则**和**必须讲清「为什么」**的条目
3. **本文件硬上限 20 条**（同族按 1 条计）；满了要新增必须**同时提名一条淘汰或合并**，由用户裁决，
   禁止静默挤占。项目级事实不进本文件，进仓库 `AGENTS.md`

**自检集成**：每步执行前对照 lessons-learned.md 该步相关 lesson；Step12 AI Review / Step13 全局一致性审查增加 lessons 合规检查。
