# 第十三步：全局一致性审查与交付收尾

> ⚡ **子 agent 加速**（先过 `subagent-acceleration.md` §1 三问，判断不了就不派）：全局一致性：证据验收**必须**独立子 agent 盲审；跨文档一致性可按文档对并行拆分。

> 本步是交付前的**最终质量门禁**。Step12 已验证"代码符合需求"，本步验证"所有产出物彼此自洽"，确保文档链与代码链一致性，通过后统一交付。

**输入**：Steps 1~12 全部产出物（所有文档 + 全部业务代码 + 全部测试代码（后端单测；前端不写））

**动作**：对所有前置步骤的产出物进行跨步一致性审查，发现不一致时修复，最后统一提交。

## 六维审查（A ~ E 一致性 + F 证据验收）

### A. 文档链一致性（Spec ↔ Checklist ↔ 技术设计 ↔ DDL ↔ API ↔ 前端设计 ↔ 测试矩阵）
逐对检查文档间是否存在矛盾：
- **Spec vs Checklist**：Checklist 每条场景是否都能在 Spec 找到对应 Capability？Spec 声明的 Capability 是否都有 Checklist 覆盖？
- **Checklist vs 技术设计（后/前）**：Checklist 业务规则在技术设计中有无对应伪代码/方案说明？
- **技术设计 vs DDL**：DDL 表字段是否覆盖技术设计涉及的全部持久化字段？类型是否匹配？
- **DDL vs API 文档**：API 请求/响应字段与 DDL 字段命名是否一致（按项目蛇形/驼峰规范校验）？
- **API 文档 vs 前端设计**：前端设计中的每个 API 调用是否都在 API 文档有对应端点？字段名/枚举/分页结构一致？
- **API 文档 vs 测试矩阵**：测试矩阵中每个 API 调用是否在 API 文档有对应端点定义？参数一致？
- **Checklist 两版一致（CRITICAL）**：`Step 3-Checklist-Jira.txt` 与 `Step 3-Checklist.md` 的条目数、`AC-NN`、顺序、前缀、状态标记、GWT 文本逐字一致；纯净版中不得出现任何标题/表格/说明性内容
- **AC 编号闭环（CRITICAL）**：以 Checklist 全量 `AC-NN` 为基准集，核对每个编号在 Step8 两份测试矩阵、Step9 tasks.md、Step11 自检报告、Step12 AI Review A 表中**四处均有出现**；任一处缺席判 ❌
- **AC 状态门禁**：Checklist 中所有条目应为 `[done]`；存在 `[open]`/`[blocked]` 时，逐条列出 `AC-NN` + 原因 + 用户是否同意放行，未放行不得进入交付收尾
- 🔴 **AC 时效性反查（L21）**：逐条回读 Checklist —— **这条 AC 描述的，还是代码现在真正做的事吗？**本次若有「有意改变既有行为」的改动（含为修缺陷而改），受影响的 AC 会**悄悄过期**：它不报错、测试也不红，只是从此描述了一个不存在的行为。过期 AC 有两害——照它验收会把**正确实现判成 fail**，照它回归会**长期保护一个已废弃的行为**。发现过期立即改写并注明「原文描述的是 X 时期的行为，因 Y 改为 Z」。🔴 **改写 AC 时必须同步改掉所有内嵌了该条原文的 `tests/AC-NN/case.md`**（`grep AC-NN tests/`）—— 漏改会留下两份互相矛盾的「原文」。**存在未改写的过期 AC、或 case.md 与 Checklist 不一致，不得判 PASS**
- **Jira 同步一致性（若已同步）**：文首 `AC-NN ↔ Jira Issue Key` 映射表与 Jira checklist 实际内容一致；本轮新增/改号的条目已同步更新 Jira
- **非功能映射表落地检查**：Step4 两份映射表中所有落点（DDL/后端代码/API/前端代码）是否在实际产出物中全部找到？

### B. 代码文档一致性（文档 ↔ 业务代码）
- API 文档端点路径/Method/参数/响应结构与 Controller 代码逐一比对
- DDL 表名/字段名与 Entity/Mapper XML 的 SQL 片段比对
- 技术设计声明的复用点是否在代码中实际调用了既有方法（非重复实现）
- 技术设计声明的非功能落点（@Transactional/@Cacheable/@PreAuthorize/乐观锁/前端性能方案）在代码中是否存在
- 前端设计文档的组件树/复用清单与实际组件、API 调用层一致

### C. 测试代码一致性（后端矩阵 ↔ 后端单测；前端矩阵为人工验证清单）
- 后端矩阵中每个 Checklist 条目的 4 个分支（正向/边界/异常/业务约束）在后端单测中是否都有对应测试方法
- 后端单测的 Mock 设置是否与被 Mock 接口的实际签名一致（参数类型/返回值类型/字段名）
- 测试基础数据是否与 DDL 表结构/字段类型一致
- 前端矩阵（人工验证清单，**前端不写测试代码**）：Step11.3 自检报告是否逐条覆盖其分支
- 🔴 **回归终检**：《Step 8-回归验证清单》全量 `R-NN` 结论是否均为通过；Step12 A4 标出的 🔴 Unverified Regression 是否已清零。**存在未验证回归项不得判 PASS**
- 🔴 **破坏性变更终检**：Step6「既有端点变更」表中 🔴 项的调用方是否全部适配；兼容期方案是否在 Spec 记录了旧字段清理时间点与责任人
- **零臆测终检**：Step12 维度 F 标出的 🔴 Unverified Assumption 是否全部已补取证或已获用户确认；文档链（Spec / 技术设计 / API 契约）中是否还残留"待确认 / 应该是 / 按惯例"字样未收敛（见 L8：决策必须回写文档）。**存在未收敛项不得判 PASS**
- **证据归档门禁**：每条 `AC-NN` 的 `tests/AC-NN/` 下 `case.md` + （`script/` **或** `REPLAY.md`）+ `evidence/` + `RESULT.md` 是否齐全，`tests/README.md` 索引是否与目录实际一致；**缺证据的 AC 判未测**
  - 🔴 **`case.md` 必须内嵌 Checklist 该条 GWT 原文**，且与 `Step 3-Checklist.md` **逐字一致**（内嵌是副本，会随 Checklist 改动漂移）；不一致判不一致项，必须修
  - 🔴 **作为判定依据的截图必须有标注版**（`-标注`，文件名内容用中文，框 + 编号 + **框边文字说明**，原图保留）；缺标注版判**证据不完整**，与缺证据同等对待。降级形式（zoom 裁剪图 / 录屏标时间点）须在 `RESULT.md` 写明降级理由
  - 🔴 **落库类 AC（同步/迁移/批量写入/定时任务/权限可见性）必须有覆盖面声明**：`RESULT.md` 写明「浏览器验证账号：X（1 个） | SQL 覆盖：N 个账号 / M 条 | 差异账号：…」。只有单账号实机验证、没有分组全量核对的，判**覆盖面不足**，与缺证据同等对待
- **11.4 收尾门禁**（若执行过浏览器实机验证）：验证报告 **E 表**中所有遗留脏数据是否已标记"已清理"——**存在未清理脏数据不得判 PASS**；**F 表**是否逐仓确认无残留调试代码（L17），提交前再复核一次 `git status`

### D. 自动化一致性检测
- 若项目存在一致性检测脚本（Python/shell），运行并捕获输出
- 若不存在，AI 对上述 A~C 维度的关键项执行自动化逻辑检查（如正则匹配 API 路径、字段名交叉对比）
- **任何自动化脚本产出的报告必须复制到 docs 目录**，命令格式：`Step 13-{报告名}.{扩展名}`

### E. 修复与追溯
- 发现 `❌ 不一致` 项时记录到报告并修复（修改文档或代码，视不一致方向而定）
- 修复后标记该轮修复的文档/文件清单
- 修复若涉及跨层改动（改 DDL/API 契约/Controller 签名/前端公共组件），按 Step12 变更影响重新评估流程处理

### F. 证据验收（验收测试专员，CRITICAL）

A ~ E 查的是「产出物彼此是否自洽」，查不出「**证据是否真的证明了 AC**」—— 代码、证据、结论都出自同一个 AI，会共享同一个误解。
本维度由**独立 subagent** 以验收测试专员身份执行，**先盲审（不读 `RESULT.md`）再对账**，逐 AC **判定证据能不能通过验收**：`验收通过` / `验收不通过`（不通过须注明原因：缺证 / 证据不实）。

- 规则、检查点、派发模板：`references/evidence-acceptance.md`（必读）
- 产出：`Step 13-证据验收报告.md`
- 🔴 只有 `验收通过` 的 AC 才能置 `[done]`；`验收不通过` 的 AC 按该文件「修复循环」补证 / 重测，或交用户放行
- 🔴 主会话不得代做、不得改写 subagent 的判定；对判定有异议时写进报告「对账发现」并交用户裁决

## 产出物格式

`Step 13-全局一致性审查报告.md`：

```
审查概要: 总检查项X | ✅ 一致: X | ⚠️ 轻微不一致: X | ❌ 不一致: X | 已修复: X | AC: 总X [done]X [open]X [blocked]X | AC缺席X | 证据验收: 通过X 不通过X 豁免X

A.文档链一致性:
  | 检查项 | 左文档 | 右文档 | 状态 | 不一致说明 | 修复动作 |
A2.AC闭环与状态:
  | AC-NN | 测试矩阵 | tasks | 自检 | AI Review | 状态 | 放行说明 |
B.代码文档一致性:
  | 端点/表/组件 | 文档定义 | 代码实现 | 状态 |
C.测试一致性:
  | Checklist条目 | 端侧 | 正向 | 边界 | 异常 | 说明 |
D.自动化检测:
  | 脚本 | 运行结果 | 报告文件 |
E.修复追溯:
  | 文件 | 修复前 | 修复后 | 涉及步骤回退 |
F.证据验收（独立 subagent，明细见《Step 13-证据验收报告.md》）:
  | AC-NN | 判定(验收通过/不通过) | 不通过原因(缺证/证据不实) | 补证轮次 |
```

> **前序步骤复检**：交付门禁会按当前产出物重跑前面每一步（不写状态）—— **Spec / 问答记录文首用 `跳过 StepN：理由` 声明过的步不重跑**（B/C 分流，见 `step-01` §0；Step3 与 Step13/14 声明了也不生效）。`.workflow-state.json` 的绿灯只代表登记那一刻通过，之后改过 Checklist / 矩阵 / 问答记录，旧绿灯不会自己变红；复检报 FAIL 就修好并补跑该步 `--record`。另查「用例状态 vs RESULT」「回归清单汇总 vs 各行」「交接文档时效」，回写规则见 `browser-playbook-parallel.md` §12.7。

> **交付门禁 tasks 完成度**：`validate_step.py` 本步要求 tasks.md **全部任务**（含回归任务组）已勾选——回归单测、质量门禁、只读 SQL 结论、前端回归项写进《测试交接文档》都在本步之前完成。

## 交付收尾与代码提交

> ⚠️ **前置硬约束回顾**：Step10/11/12 全程**禁止 git 提交**，所有代码只在工作区。本节是整个工作流**唯一允许提交的环节**。

**前置条件**（全部满足）：
1. A~E 检查全部 ✅ 或 ⚠️ 且已修复
2. 变更影响已处理完毕
3. 用户明确确认"可以提交"
4. Step11.3 自检报告全部 ✅
5. Checklist 全量 `AC-NN` 闭环无缺席，且非 `[done]` 条目已获用户明确放行
6. 《证据验收报告》中 `[done]` 的 AC 全部 `验收通过`；`验收不通过` 的 AC 已补证复验通过或获用户放行

**多仓提交规范（本工作区，详见 doc-output-and-context.md §二）**：
1. **前后端分别提交**：后端只在 `creative-management/`；前端只在 `vuen-crossretail/`（及必要时嵌套仓 `packages/creativehub/`）；跨仓同一需求 = 多次独立 commit
2. **提交前先读对应仓库 `.gitignore`**；**只 add 相关文件**（业务代码/测试/docs），**禁止 `git add .` / `-A`**；外层不要误提交 `packages/creativehub`
3. **提交信息**：前端 `feat: CP-xxxxx 描述`（header ≤72，husky 校验）；后端 `feat:CP-xxxxx 描述`；正文含涉及模块 + Checklist 覆盖数（前端 X / 后端 X）+ 审查结论 + 关联文档目录
4. **DDL 单独提醒**：代码提交 ≠ DDL 已执行，需显式提醒"需手动执行 ddl.sql（及回滚脚本）"
5. **推送**：仅 feature 分支，禁 push main/master/release；禁 `--force`；有冲突先 `pull --rebase`

**提交后**：汇报各仓 commit hash，提醒后续（前端联调/部署/PR）。

## 审查终止条件
- **所有检查项 ✅** → 进入交付收尾（提交）
- **存在 ❌ 项** → 修复后重新执行本步（重新审查 + 再提交）
- **证据验收存在 `验收不通过`** → 补证 / 重测后，只对改动的 AC 再派 subagent 复验（最多 2 轮）
- **循环限制**：最多 2 轮修复，第 2 轮仍有 ❌ 则输出完整缺陷清单请求人工介入

**→门控**：🔴 **阻塞（唯一允许 git 提交的环节）** —— 落盘报告 → 汇报审查结论 → **暂停等用户明确说「可以提交」** → 才提交 → 汇报提交结果 → **进入 Step14（AC↔Subtask 匹配与提测）**

> 🔴 **阻塞门控**：必须**暂停等待用户明确确认**，未获通过禁止进入下一步。
> 之所以阻塞：**提交不可逆且对外**：代码进了仓、推了分支，撤回成本远高于多等一次确认。同批还要产出《测试交接文档》交给 QA。
> 经验沉淀改到 **Step14 提测终态之后**（见 `step-14-ac-subtask-handover.md` + `lesson-harvest.md`）。
