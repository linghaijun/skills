# 页面笔记规范（PAGE-NOTES 怎么写）

页面级的操作事实与**本仓特有**可复用脚本。**目的只有一个：下次开浏览器时不用重新摸同样的东西。**

> 每个项目一份 `projects/<项目>/PAGE-NOTES.md`（页面事实 / 口径 / 坑 / 测试数据），与同目录的 `README.md`（操作脚本）配套。
> 2026-10-10 起取代工作区 `docs/browser-notes/`（用户要求这类内容不放项目目录、不进 git，统一在 skill 里随分发同步）。
> 通用方法与坑写 `references/SCRIPTS.md`，不要在 PAGE-NOTES 里再抄一份。

## 分层对照（写/读落点）

| 层 | 位置 | 「下次换需求还能跑吗？」 |
|---|---|---|
| L0 全局 | `scripts/` + `references/SCRIPTS.md` | 能 → 通用手法、坑、通用工具（含标注 `annotate*.py` / `compose.py`） |
| L1 页面级 | `projects/<项目>/README.md` + 脚本 + **`PAGE-NOTES.md`** | 同项目同页面能 |
| L2 一次性 | `tmp/` 或 `docs/develop/<需求>/` | 不能 → 不沉淀 |

## 🔴 第一条规则：过期的笔记比没有笔记更糟

UI 改版比什么都快。一条写错的「点这里」会让下次按旧路径走 → 走不通 → 然后去**怀疑环境或代码**，
排查成本比从头摸还高。所以：

1. **每条带最后验证日期 + 当时分支/环境**，没有日期的条目视为不可信
2. **按记录走不通时，先怀疑记录过期，不是怀疑环境** —— 先按 playbook 从头探一遍，再回来改记录
3. **用到就顺手刷新日期**（用到才刷新 = 没人用的条目自然沉底，不必专门清理）
4. 发现写错的，**当场改掉或删掉**，不要留着"以后再说"

## 记什么

| 内容 | 为什么值得记 |
|---|---|
| 页面背后是**哪个后端 / 哪个库** | 每次验证的第一件事，不记就每次重扒 |
| **入口路径**：从哪进、要先选什么它才出现 | 纯路径知识，不随改版全废 |
| **哪个操作触发哪个 XHR 端点** | 取证时最花时间的一步 |
| **异常态怎么造**：空 / 错 / 权限不足 / 边界 | 每次都要重新想一遍 |
| **已知的坑与慢点**：必须等什么、什么会"假成功" | 踩过一次就不该踩第二次（通用坑优先写进 CDP SCRIPTS.md） |
| **测试数据在哪**：哪个账号、哪条记录有这个场景 | 配合账号选取规则（内部账号；否定型验收不能用超管） |

## 不记什么

- ❌ **CSS selector / 坐标 / DOM 结构** —— 每次重新拿更快更准；若必须固化，放 L1 `projects/<项目>/` 脚本并标最后验证
- ❌ 一眼能看出来的东西（按钮长什么样、页面有几个 tab）
- ❌ **一次性的业务数据**（本次需求的具体记录 id）—— 属于本次 `docs/develop/<需求>/`
- ❌ **任何凭据**：用户名、密码、token、cookie、预签名 URL。账号只记**登录名与它能看到什么**
- ❌ 通用浏览器方法论 / 已进 CDP L0 的脚本 —— 不要在这里再抄一份

## 单份笔记的模板

见 `references/PAGE-NOTES-TEMPLATE.md`。开始验证前先读对应模块那份；**没有就复制模板新建一份**，验证过程中边做边填。
收尾：本轮新坑 → 优先回写 `references/SCRIPTS.md`（跨项目）或该项目 `PAGE-NOTES.md`（仅本项目）；脚本复用 ≥2 次再升 `scripts/`。
