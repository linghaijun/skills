# 本 skill 定期自检（self-review）

> skill 是一次次「出事 → 补一条规则」长出来的。只加不审，半年后就是：规则互相矛盾、脚本名改了文档没改、
> 同一条经验写在三处且说法不同、早已修掉的坑还在占篇幅。**执行时读到过时规则，比没有规则更糟** —— 它会被照做。

## 什么时候做

| 触发 | 做什么 |
|---|---|
| 用到本 skill 时，`REVIEW.md` 显示**距上次 review ≥ 7 天**（或没有 `REVIEW.md`）**且（本 skill 被改动过、或本次有坑 / 脚本待沉淀）** | **当前任务收尾后**做一次（不打断主任务），回复里一句话说明 |
| 距上次 ≥ 7 天，但 skill 没动过、本次也没有要沉淀的东西 | **只抽查**本次碰到的文件 + 在 `REVIEW.md` 刷新「上次 review」日期，并在该节写明「本次无变更，仅刷新日期」—— 不要为凑周期重读全部文件（自检成本会超过主任务） |
| 距上次 ≥ 7 天，但 `REVIEW.md` 里还挂着「待确认」项 | 只处理 / 复核那些待确认项，不必全量重审 |
| 用户说「review / 体检 / 整理某 skill」 | 立即做（**全量**，不适用上面的抽查） |
| 一轮任务里给本 skill 补了 ≥ 3 条规则 / 坑 | 收尾时顺带做一次，重点查新旧规则是否打架 |

看到期情况：读本 skill 根目录 `REVIEW.md` 开头的「上次 review：YYYY-MM-DD」，距今 ≥ 7 天即到期（没有 `REVIEW.md` 也算到期）。

## 怎么做（逐项，不跳）

1. **通读**：SKILL.md + 全部 references + 脚本头注释。大 skill 可按文件分批，但每个文件都要读到
2. **找问题**，每条记下 `文件:行` 与证据：
   - **失效引用**：提到的脚本 / 文件 / 小节 / 坑编号 / 命令参数不存在或已改名（用 Glob / Grep 实查，`--help` 实跑）
   - **过时事实**：环境、路径、默认值、版本、「目前 / 暂时」类说法 —— 能查就对照当前代码 / 配置验证；查不了的标「待确认」，不改
   - **矛盾**：两处规则说法不一致（常见于新规则补丁没回头改旧规则）
   - **重复**：同一规则多处全文复述 → 保留一处全文，其他处留一句硬提醒 + 链接（**使用点的提醒不能删**，执行时 agent 只读它正在看的那个文件）
   - **可优化**：索引与正文不一致、结构难找、过长段落、该脚本化的人工步骤
3. **改**：
   - 失效引用、矛盾、明确过时 → 直接改
   - **删除任何规则 / 经验 / 坑：必须在 REVIEW.md 逐条写理由**（已被哪条取代 / 对应机制已删除）；拿不准就保留并标「待确认」
   - 经验默认**迁移不删除**（挪到更合适的位置）
   - 两个 workflow skill 共享文件（`validate_step.py` 的 `SHARED_FILES` 列表）必须两边一致；lessons 编号各自独立，**不要跨 skill 复制 `LNN` 引用**
4. **自检**：workflow 跑 `scripts/validate_step.py --self-check`；改了脚本跑 `node --check` / `python -m py_compile`（删掉生成的 `__pycache__/`）
5. **记录**：在本 skill 根目录 `REVIEW.md` 顶部追加一节（格式见下），更新「上次 review」日期
6. **分发**：`distribute-agent-skills`，报告真实数字

## REVIEW.md 格式

```markdown
# <本 skill 名> Review 记录

上次 review：YYYY-MM-DD（下次到期：+7 天）

## YYYY-MM-DD（review 人 / 会话）

- 范围：读了哪些文件（N 个）
- 已改：<文件:行> 问题 → 怎么改的
- 已删：<条目> —— 理由（被谁取代 / 机制已删）
- 待确认：<条目> —— 为什么不能直接改、需要谁确认
- 自检：<命令> → 结果
```

## 红线

- 🔴 不为「变短」而删 —— 删的是失效和重复，不是篇幅
- 🔴 不改别人的项目代码；skill 里描述的项目事实对不上时，以代码为准改 skill，并在 REVIEW.md 写证据
- 🔴 review 只读到一半就写「已 review」= 没做
